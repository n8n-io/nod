## What changed in the evaluation

The production metering wrapper previously dropped the fourth upload argument, the selected account ID. The old fixture bypassed that wrapper, so it could pass while normal application uploads failed. This new version uses the real wrapper around both actual Composio providers. After the first two preparations, it recreates one service while retaining its saved session, prepares for a different account, and asserts an actual `restore_session` plus that account ID on the signed upload. It then deletes the original preparation session and executes all three prepared actions through fresh account sessions.

The [portable runner](cp05.v2.runner.mts) also requires an exact freeze ID, validates each materialized input against its frozen size/MD5/SHA256, checks the collision pair before action, scans response headers with an injected-header control, and fails on unsuccessful cleanup. Earlier frozen records remain unchanged. No attempt failed during this new freeze; the owning implementation's prior focused regression remains separate red evidence in the [review follow-up](review-followup.md).

## Reproduction and limits

Use Node 24.21.0, dependencies matching each checkout's lockfile, the companion proxy checkout at the frozen revision, the exact Otto source hashes, and a disposable PostgreSQL service at the frozen test address. From the Otto repository root, with provider credentials removed from the environment:

```sh
node --experimental-transform-types docs/testing/composio-proxy/cp05.v2.runner.mts \
  --mode run --freeze-id CP05.v2-a01 \
  --proxy-root /path/to/otto-composio-proxy \
  --output /path/to/new-cp05-result.json
```

The output path must not exist. The runner selects no “latest” freeze, derives Otto paths from its own repository location, and rejects changed frozen inputs or source. It uses fresh random SQL schemas and task-generated installation keys; it never reads a normal Otto profile. Model judgment is not used, and no provider/model cost was incurred by this fixture.

The original [CP05.v1 evidence](cp05.v1.results.json) still contains the separate real empty-session storage prerequisite and 15 MiB workerd check. Those are historical checks, not new live results. The original storage run recorded all four file deletions and four session deletions as HTTP 200; its evaluator could swallow a future deletion failure, so only those actual successful receipts support the old cleanup claim. The unchanged Worker permits reuse of the earlier storage contract and size evidence, while this new run establishes the current metered app path with synthetic receiving fixtures. It does not prove live Gmail delivery, OAuth consent, a newly repeated provider cleanup, or Composio's 24-hour retention policy.
