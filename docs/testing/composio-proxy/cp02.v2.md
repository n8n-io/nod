# CP02 reconnect after a provider change

**The reconnect contract passes.** All 74 final related tests pass on Node `24.21.0`, including 19 replacement variants. They use the production integration service, ordinary owned API routes and disposable PostgreSQL schemas. [Frozen inputs](cp02.v2.inputs.json) and [results](cp02.v2.results.json) retain fingerprints, individual attempts, preserved failures and evidence limits.

| Scenario                                          | Observed result                                                                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Old saved account before consent                  | Execution, polling and queued-event dispatch remain fenced; saved data is retained.                                       |
| Verified original email                           | One connected row keeps its original local ID and watch preference. Obsolete cursor, trigger and queued work are cleared. |
| Two accounts in one service                       | Each reconnect selects and preserves its own local row.                                                                   |
| Cancel, failure, wrong identity or foreign target | Original row and queued work remain intact. Unknown identity requires an explicit separate Add account flow.              |
| Superseded, expired or disconnected target        | Cannot replace the target. A newly completed owned orphan is removed; old remote grants remain untouched.                 |
| Duplicate callback                                | Only one consumes the provider token and completes. The losing callback cannot clear the winning attempt.                 |
| Interrupted callback and restart                  | Persisted admission prevents replay of an uncertain attempt. Explicit fresh consent succeeds.                             |
| Database pool with one connection                 | Managed reconnect and actual direct Linear OAuth success/cancel complete without a held admission lease.                  |

The first preserved baseline failed because reconnect created a second local row. The general fix keeps a temporary attempt pointing at the original owned connection and replaces it atomically only after ownership, service and original email checks. It preserves references to the original connection ID and does not reuse or revoke the old remote grant.

Later holdouts exposed callback races and orphan cleanup gaps. Durable admission is now stored on the existing local attempt; parsing and encrypted-vault operations hold no pool connection. Cleanup accepts only the exact claimed attempt and an authoritatively verified account. Final source inspection checks the account before the persistence transaction, so supersession during token exchange cannot leave a newly completed owned grant behind.

The full suite found three older fixtures that retried the same failed callback. Their final-source red is retained. They now require replay to expire, then start explicit fresh consent and retain the original account-isolation and successful setup-receipt assertions. No production change was made for those fixture corrections.

This is contract evidence, not live Composio consent or native installation acceptance. Managed provider state is synthetic. The direct OAuth regression uses the actual provider and encrypted vault with intercepted synthetic HTTP. Composition/settings secret checks belong to [CP03](cp03.v2.md); this service-only evaluator marks that applicability as absent rather than claiming it from a fake provider. Native replay, the final full suite, build and commit evidence are recorded separately by the coordinating task.

The later isolated native upgrade demonstration exposed a UI regression: the original account was Connected after focus refresh, but its pairing notice remained. That observation and the reproduced renderer red are retained in `pairing_ui_followup` in the results. Apps now reconciles the exact owned setup-link receipt on focus/visibility and before timeout. The renderer holdouts pass for an already-connected first account, a different receipt, delayed completion of a superseded attempt, exact focus/visibility completion and completion before expiry. This follow-up does not relabel the earlier native recording as a final-source UI pass.
