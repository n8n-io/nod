# App connections

Saved website sessions are browser paths. Chat account work on a website uses the Vault login flow first. `browser_connection connect` is a fallback when the browser is not supported, sign-in is blocked, or the owner asks Otto to keep a website session. It opens an account page, checks for login fields and one clear login control, then places a secure sign-in link in chat. Apps has Connect website for a supplied address and keeps its query string. A pending Apps row can issue a new link and invalidate the old one. The owner can use the checked private form or control Otto's browser for a site-specific step. The browser profile keeps cookies under one owner and one connection ID. A later task calls `browser_connection use` with that ID and a URL on the saved origin. Reuse opens the page and requires the task to check account access. An expired login gives that task a new private sign-in link. Disconnect removes the profile and saved browser screens. A failed removal stays visible for a retry. A Vault login is optional and separate; saving a browser session does not save its password. A session row does not prove account access or permission for a write. Site policy and site-side browser blocks still apply.

Otto shows connected services and available services in **Apps**. A connected card shows the service name and **Manage**. The Manage dialog shows its accounts, access path types, disconnect controls, and **Add account**. An available card shows **Connect**. In chat, `manage_apps` can show accounts and start the same connection flow. When a chat task starts a connection, Otto puts one secure link in the conversation. For a discovered token path, that link opens the private Apps setup dialog. The user enters the key there, then the same task resumes. The callback returns to chat and queues that task again if its owner, conversation, and revision still match. A repeated callback can reuse the verified token exchange if account inspection failed before the app saved its account row. The provider can still require a sign-in or consent click. A prior grant can make that step shorter.

For a service outside the fixed catalog, the model can research official access methods with public web search and the task browser. Search returns source links; the browser can open exact pages when the result text is not enough. It should compare the required read and write actions and choose one path that covers the full task when it can. When paths cover the same actions, it should prefer an OAuth link over a token form. `manage_apps propose` saves one to four public HTTPS MCP or HTTP API paths, or installed CLI paths. A discovered MCP path can use OAuth or a bearer token; an HTTP API path uses a bearer or `X-API-Key` token. OAuth uses one MCP path per account. The model can give a short setup step and a public HTTPS setup URL. Apps shows that guidance, each service address, and the exact HTTP GET address used to check a token. OAuth asks for one sign-in action, or a public client ID if the service requires its own registered app. This flow does not accept a client secret. A token path asks for one token and an account label in a private form. The model receives neither token. The server validates an HTTP GET test path for HTTP access before it opens the token form. It checks MCP tools, the HTTP path, or the saved CLI read command with the token. It then saves one account and resumes the waiting task. Apps shows the service card; its Manage dialog shows the account and its path types. The model can propose changed paths, which need a new sign-in or token check. A check does not prove every write grant.

`apps SEARCH_TOOLS` returns the saved path IDs and current MCP tools that match the query. A service-name query also returns up to 200 tool names, so the model can search for an exact tool schema next. `CONNECTED_MCP_CALL` uses an exact tool name and input. `CONNECTED_HTTP` uses an HTTP method, a path under the saved API address, and optional JSON. `CONNECTED_CLI` uses the saved program and an argument array. The model can mark a checked CLI read with `readOnly:true`; the server accepts only listed read verbs and rejects common write verbs and flags. Other CLI calls use account review. The model must check the CLI behavior before it marks a call as a read. This check is not a proof that an arbitrary CLI has no side effects. A leading slash still stays under a saved API prefix, such as `/v1`; encoded traversal and encoded separators are rejected. GET requests and MCP tools with a read-only hint and a read name can run as reads. Other calls use the existing task, account, and one-use chat action review. The review shows a bounded, redacted request body or tool input. API errors and uncertain writes do not trigger automatic replay. The trusted adapter checks public DNS addresses on each request, pins the resolved address, uses HTTPS, rejects redirects, and limits transfer size. It sends a token only to a reviewed service address. Vault stores the encrypted token or OAuth grant, including refresh data, in `vault_app_grants`. Connection rows hold path and account metadata with an empty legacy ciphertext field. Startup moves existing saved grants to Vault. New pending OAuth state also stays in Vault until the callback or expiry. Secrets stay out of the model, browser client after entry, and ordinary workspace shell. For a CLI call, the server sends the Vault token only to the selected program in a separate computer user. It runs the program from a private directory with a temporary home, and removes that home after an acknowledged call. A CLI can still receive, send, or save its token during that call, so use trusted programs. Disconnect deletes the saved grant.

Saved Vault website logins appear in Apps as browser paths. Each exact website origin has a distinct browser app identity, so unrelated domains cannot share one card. The task browser can reuse the selected login through the existing exact-origin broker. Removing a browser path in Apps removes its Vault login. Website session cookies remain in the private browser profile and are not Vault grants. The ordinary workspace shell has no Vault access. The model can install a trusted CLI in that computer before it proposes a CLI path. Local Docker and the optional hosted E2B computer have a separate user for connected CLI calls. The selected Cloudflare computer adapter cannot accept CLI proposals yet. One token applies to all paths in one token-based account, so paths that need different grants need separate connections. Token account labels come from the user; OAuth accounts use the service name until a verified identity method exists. A provider can still deny a specific repository, operation, or scope after connection. Vault does not yet show app grants on its page.

The direct Notion and Linear packages use [Agent Plugins v1](https://agent-plugins.org/specification) `plugin.json` and `mcp.json` files under `plugins/`. Each package declares one fixed Streamable HTTP MCP endpoint. The direct provider loads and checks those files. Otto manages OAuth discovery, dynamic client registration, PKCE, callback checks, encrypted tokens, refresh, account state, and tool calls. The package files contain no credentials. This implementation loads the two bundled MCP packages. It does not load arbitrary packages or CLI servers.

Notion uses its [hosted MCP server](https://developers.notion.com/guides/mcp/overview). Linear uses its [read-only MCP endpoint](https://linear.app/docs/mcp) and the `read` OAuth scope. Otto permits Notion search and page reads, and Linear project, issue, team, and status update reads. The direct adapter has no write or watch action. It checks the live MCP tool list when an account is connected and advertises only mapped tools that the server returns. Composio remains the provider for Google and Slack services and their supported events, including page-content watches on existing Composio Notion accounts. Existing Composio Notion accounts keep their provider ID and continue to work; new Notion and Linear accounts use the direct provider. When both Notion providers have an active account, Otto lists the direct account first and selects it for an action without a stated account. If the direct account is inactive, an active Composio account can serve the request. The tool catalog selects native actions for an active direct account and removes Composio-only actions from the general search; a stated connection ID still selects its saved provider. Tokens and account IDs do not move between providers.

`src/server/integrations.ts` owns the catalog, account selection, consent attempts, callback state, and read policy. It accepts extra provider adapters and routes each saved account by provider ID. It passes only active saved account IDs to direct tool discovery. If one account fails, discovery checks the other saved accounts. `src/providers/direct/oauth.ts` owns direct OAuth exchange and refresh. Vault owns its encrypted grants and pending PKCE state. `src/providers/direct/mcp.ts` owns MCP transport. `src/providers/direct/integrations.ts` maps approved actions to live tools. `src/server/composition.ts` selects the adapters. Local mode uses a Keychain key on macOS or a configured environment key. Hosted tenant mode uses its derived private key and tenant SQL namespace. Direct OAuth tokens and pending PKCE data are encrypted with AES-256-GCM in `vault_app_grants`; `direct_oauth_accounts` keeps account and callback metadata. Startup moves older encrypted direct grants to Vault and clears their old ciphertext. Tokens stay out of the browser client, model, logs, and workspace. Disconnect deletes the saved token; a user can also revoke the grant at the provider.

Disposable database fixtures cover callback state, encrypted token storage, token refresh, provider routing, account selection, and chat callback handoff. They use substitute provider responses and do not prove a real grant or MCP read.
