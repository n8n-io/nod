# Otto system guide

Updated **2026-09-28**. This is the living product and technical reference for the current repository. Update it when behavior, dependencies, boundaries, or validation changes. [Verification](verification.md) records test evidence; configuration alone is not proof that a provider works.

Full account/environment erasure follows the [operator reset procedure](environment-reset.md), covering authentication, tenant SQL data, files, computer state and owned remote connections. The in-app conversation reset preserves historical and saved data. A recording reset leaves the environment at sign-in until the authorized signup journey begins; subsequent test/demo activity is recorded separately.

Otto runs as either a local, single-owner assistant or an authenticated hosted service. One chat holds messages, replies, attachments, and reactions. Internal tasks supply durable execution, independent browser sessions, workspaces, action confirmations, and continuation. Pi runs the model/tool loop; trusted server services control credentials, connected accounts, storage, and background work. Ordinary local mode binds to loopback without app sign-in. Hosted mode adds Google sign-in and a separate account runtime for each user.

The hosted implementation includes Google sessions, an authenticated gateway, account profile and appearance settings, onboarding app consent, owned webhook routing, private PostgreSQL roles and schemas, runtime leases, Cloudflare/E2B computer adapters and durable private files. Startup configuration selects providers and models; users connect their accounts without choosing a computer provider or supplying operator API keys. Computer views and controls require developer authorization.

The public `/privacy` page reads `{content:string|null}` from anonymous `GET /api/privacy`. Operators supply reviewed UTF-8 Markdown through the gateway-only `OTTO_PRIVACY_NOTICE_FILE` setting, bounded to 128 KiB and 32,000 characters at startup. Omitting the setting has no default policy and does not prevent deployment; a configured unreadable or invalid file prevents startup. Before sharing signup, customize the [privacy template](privacy-notice-template.md) into `public/privacy-notice.md`, verify the signed-out page and configure its URL in Google OAuth. The build includes the intentionally public file at `dist/web/privacy-notice.md`. The notice must describe the actual operator, providers, retention and deletion process. Account deletion remains an operator procedure across storage and provider resources; starting a new chat or disconnecting an app does not erase historical data.

Otto's Google client requests only `openid`, `email` and `profile`. Google's External Testing exception for these identity-only scopes removes the tester-list, unverified-warning and seven-day authorization-expiry restrictions; it does not remove Otto's configured seven-day login session. A personally known small pilot can qualify for Google's verification exception, while broader public release has separate branding requirements. Composio's Gmail/Calendar permissions have their own scope requirements. [Production setup and checked Google sources](production.md#privacy-and-google-sign-in).

The gateway bounds webhook bodies to 256 KiB and private channel-control bodies to 4 KiB. Channel-control authentication precedes database lookup and retains current-lease and replay checks. Saved channel configuration has a durable account-claim journal, so a failed claim release can recover after restart without reverting a committed settings change. [Trust boundaries](security.md) and [channel recovery](channels.md) describe these guarantees and limits.

The ordinary local infrastructure consists of the host Node process and three Docker services: PostgreSQL, the Linux workspace and the trusted browser. `Dockerfile.browser` installs Chromium and the private desktop tools inside the image; no host Chrome install or launch is required. The launcher generates a private local PostgreSQL password and rotates the existing role before starting browser/workspace services; it preserves data rows. Redis and an external object store are not required for this mode. [Composition](../src/server/composition.ts), [container configuration](../compose.yaml).

Hosted composition uses `OTTO_MODE=gateway` for session handling and private `tenant` processes for application work. Each actor receives an immutable owner ID, its restricted database connection and a derived Vault key. `COMPUTER_PROVIDER=cloudflare` selects separate owner-bound browser and workspace containers; `e2b` selects one sandbox per owner with separate browser and workspace Linux identities. Ordinary computer environments contain no service credentials. A connected CLI call receives one Vault token for that call. Cloudflare computer requests carry the immutable runtime generation and role; storage requests also carry the generation. The Worker derives account authority from trusted platform identity and the active grant. Actors never receive global R2 credentials. Development and production use separate provider projects, authentication settings and storage. [Hosted configuration](../deployment/hosted.env.example).

Tenant deployment drain pauses new HTTP work, queue consumers, channel polling, integration maintenance and Vault retries. Accepted tasks and background callbacks finish naturally; deployment pause does not cancel model or tool work. A successful signed receipt includes the exact runtime generation and drain nonce after all accepted work finishes before the deadline. Deadline failure leaves the tenant paused until the matching resume; queued tasks remain durable. HTTP disconnects cannot make a still-running handler disappear from the count. Lease renewal continues throughout. This Node receipt is only one deployment gate: the coordinator must separately confirm clean computer checkpoints and stopped runtimes. Disposable PostgreSQL, actual pg-boss and synthetic provider fixtures cover these boundaries; no live production deployment result is implied.

The Cloudflare gateway persists its deployment admission barrier separately from the Node process. Computer drain requires exact owner/generation authority, non-forced browser quiescence, successful checkpoints and confirmed physical stops. Resume revokes its prior computer proof before reopening work and remains retryable after a lost acknowledgement. After a lost gateway journal, read-only recovery requires every tenant and both roles to be clean and stopped; unknown work or unsettled native startup keeps admission closed. Automated fixtures cover these cases; a live deployment drain remains a separate acceptance gate.

Tenant process shutdown retains the runtime lease watchdog while application and database cleanup run. Cleanup that hangs cannot disable the existing exit deadline after lease expiry, and repeated process signals do not extend it. Successful cleanup closes the lease timer immediately before exit. This process safeguard does not prove a stopped VM or replace the deployment coordinator's independent stop checks.

`scripts/start-hosted.mjs` automatically starts local Wrangler/Docker/R2 emulation for Cloudflare, or private Node child processes with PostgreSQL object storage for E2B. Both use the development Google callback on localhost:4330. Cloudflare serves built web assets, so frontend changes require a rebuild. The browser image contains Chromium and the private worker; the workspace image contains Python/Node CLI tooling. Both run unprivileged under `tini` with fixed read-only helpers and internal readiness checks. CI builds three images, and deployment pushes every selected role image before Worker activation.

The local Cloudflare launcher uses the existing signed drain protocol for Ctrl-C and SIGTERM. It stops Wrangler only after accepted work finishes, computer checkpoints commit and exact generations stop. A private installation identity and operation journal bind the next startup to the same clean-stop recovery; `--resume` can explicitly reopen a refused operation against the still-running stack. Repeated signals never force termination. External kills and watched-source rebuilds bypass this handshake, so stop cleanly before editing runtime sources. See the [local shutdown and recovery instructions](development.md#hosted-mode-on-your-computer).

## How one chat becomes durable work

1. The server accepts an owned message, attachments, and optional `replyToMessageId`. Before ordinary persistence and routing, it checks whether a four-to-eight-digit reply matches a pending OTP request. That trusted path stores a masked receipt and passes the code to the broker without model processing. Other messages validate their reply target and use ordinary task routing; the UI does not expose those internal task choices.
2. A PostgreSQL transaction persists dispatch state and a pg-boss job. Four workers can run independent tasks. Each task has a revision, a private transcript reference, and a workspace/browser identity.
3. The runtime supplies bounded context and explicit tools to Pi. Provider keys are injected into trusted adapters, not model prompts. Tool calls route through capability interfaces and server policy.
4. Typing and deltas show live work. The agent can send a concrete progress update when useful; elapsed time never inserts a generic promise. Background work stays silent unless it has a useful result or needs an answer. Text deltas use a distinct stream ID per model message. Persisted messages reconcile those IDs so a late refresh cannot erase another message's stream.
5. An ordinary question, secure credential step, or action approval pauses execution. The appropriate server path records the answer/outcome and schedules continuation. Task revisions reject stale jobs and forms.
6. Cancellation stops further accepted work. Already accepted external actions can finish. Recovery treats interrupted external outcomes as uncertain instead of silently replaying them.

Explicit replies carry a bounded quote in the message DTO, including when the original is outside loaded history. A same-channel reply resumes an eligible target waiting for an ordinary answer or already succeeded; inputs to running or queued tasks wait behind their active work. Failed tasks and recovery waits refuse continuation, including an older reply target whose outcome has newer blocked work. Cancelled targets create new internal work while retaining the quote. Password and manual-control waits use their dedicated private paths. Matching OTP replies use the trusted chat broker path. Action confirmations use yes/no replies in the same chat, bound to the exact pending action. An implicit short answer follows only the latest visible assistant question in that channel; other messages start internal work without showing a task picker.

User reactions accept one Unicode emoji on assistant messages, including joined sequences, flags and skin tones; legacy `like`, `dislike` and `heart` values still render and deduplicate. The agent can occasionally react to a visible owned user message in web chat. The server permits one reaction per message and at most one new reaction per five minutes, with owner, channel, generation and active-segment checks. Removing a reaction does not reset those limits. Telegram, WhatsApp and background runs skip this tool until provider reaction support exists. A changed, non-null user reaction can start one quiet event task when the main model is configured; repeating or removing it does not. Agent reactions do not wake another task. Reactions are feedback, never action authorization. [Task routing](../src/server/tasks.ts), [runtime](../src/runtime/index.ts), [wire contract](api-contract.md).

## Vault and action confirmations

Website passwords use AES-256-GCM with a random 96-bit nonce and authenticated owner/origin/record binding. The master key lives in macOS Keychain, or an explicitly supplied 32-byte base64 `OTTO_VAULT_KEY`; it is not stored with database ciphertext. Channel settings use the same key source with a distinct owner/channel binding.

Vault is the default path for supported website sign-in. Before the agent suggests manual browser sign-in, the runtime requires a fresh trusted login inspection. Reachable identifier/password fields produce a secure link in chat. Verification fields use the trusted code flow below. Navigation or inspection failures request bounded recovery and cannot be presented as a confirmed browser-security rejection.

Each saved login has a user-defined name and an exact website origin. The manual form accepts a domain such as `example.com` and stores `https://example.com`; subdomains, schemes and ports remain separate. Multiple named logins can share an origin. Secure forms show the fixed destination and collect a name, identifier and password together, including when the website initially shows only its identifier field. If several saved accounts match, the owner chooses one in Vault. The broker keeps the selected account through staged sign-in; OTP entry never saves a login.

The private Vault list shows full login usernames and exact websites. Add to Vault offers Login and Payment card. Rows open directly as editable forms, with Save changes shown only after an edit. There is no row-level delete action, and deletion requires a separate confirmation inside the modal. Passwords, card numbers and optional security codes remain hidden until Show or Copy; separate owner-bound requests return each secret. Copying while hidden does not reveal it. Closing or leaving the view clears secret state and rejects late responses. Passwords, full card numbers, security codes and code-presence flags never enter the page cache, chat, agent tools or Inspector. The system clipboard is used only for an explicit copy action.

The form edits Name and login or card fields while keeping a login's website fixed. Where available, the saved website label identifies the login field; otherwise it says Username. Saved secrets start masked. Change opens a required empty replacement field; Cancel change restores the unchanged state without retrieving the secret. Card security codes also support Add and Remove, with removal applied only on Save changes. Cancel changes restores saved nonsecret values and clears replacements. The trusted server locks and rechecks the owned record, retains its encryption binding and returns masked metadata only. The list updates after an accepted save; replacement input is cleared on submission and when the window is hidden. These edit boundaries have focused UI and disposable-database coverage; real website acceptance of changed credentials is a separate check.

Secure forms use a random token whose hash is stored, expire after ten minutes, and bind to the task revision. The broker observes identifier, password and OTP stages and rechecks the current origin/fields before entry. Observed method choices stay in chat and can start a website OAuth or verification flow; that does not prove login or establish a Composio connection. For staged login, the broker holds the supplied password encrypted under the same owner, origin, revision and original expiry, then consumes it before filling the freshly observed password field. Broker restart does not require another password form. Rejected or uncertain attempts require fresh input. Secure injection locks observations, and the model receives no plaintext credential result.

For OTP, a trusted message asks the user to reply with only four to eight digits in the originating chat. The server matches one pending request, or an explicit reply target, before ordinary persistence and model routing. It stores “Verification code received securely.” while injection is pending, then “Verification code sent securely.” with the final submission status. Neither receipt proves the website accepted the sign-in. Matching uses owner, channel, current conversation, revision and expiry; attachments and `forceNew` cannot bypass an applicable OTP request. A keyed HMAC fingerprint derived from the Vault key rejects changed-code retries without storing the code, while exact retries return the existing receipt without reinjection. Missing fingerprint or key data fails closed.

No matching request means an ordinary number remains ordinary chat. For Telegram and WhatsApp, numeric classification and ordinary inbox persistence commit together under task-row locks that also protect Vault request insertion. A new OTP request cannot enter the former gap between those operations. Browser inspection and injection run outside that transaction. External chat providers still receive and may retain the original message. Passwords remain private-form input.

For an email code, the broker first tries one narrow lookup in the exact matching connected Gmail account. The website must display the full recipient; it must match the encrypted selected login and one active Gmail connection. Accepted credential entry must be within five minutes. A lookup has an eight-second budget and considers at most five messages from the authentication window. Gmail-authenticated sender and recipient checks, a same-registrable-domain rule and one unambiguous code limit automatic use. It does not fetch attachments or expose mail to the model. Origin, revision, selection and account state are checked again before injection. Missing, ambiguous, masked-recipient, cross-domain or unavailable results fall back to chat. Codes and mail remain absent from local history, request storage, Inspector and logs. [Detailed boundaries](vault.md).

A fresh visible rejection detected within two seconds consumes the old form and returns a new Vault URL with the original expiry and revision. The UI clears rejected values and shows the retry form; the task stays waiting and no rejected password is saved. Unknown or later website responses remain submitted, not authenticated, and require the agent to inspect the current page.

The trusted server and destination website necessarily handle plaintext. Encryption does not hide it from a compromised host or a cloud operator controlling the authorized decrypting service. Cloud KMS alone does not change that limitation. Key rotation, cloud envelope encryption and operator-resistant execution are not implemented. Payment cards use a separate AES-GCM table with an owner/record/type binding. Card lists show name, brand, last four digits and expiry; explicit details add the cardholder and a security-code presence flag. Separate no-store reads reveal the number or optional three/four-digit CVC/CVV. Cards cannot match website-login queries. A visible group of four to eight single-digit verification boxes can receive one private code when the group is unambiguous. The trusted broker checks its fields again before entry. Card autofill, TOTP seeds, cross-origin iframe login, passkeys and hardware-key flows are not supported. [Vault details](vault.md).

Known ordinary app and personal actions can execute directly when the current owned user instruction requests that operation and scope. Draft requests do not authorize sending. Unknown, destructive or unmatched actions ask one specific question in the same chat, showing the saved action details and account. A yes or no binds to that owned confirmation and execution revision. The worker executes the saved snapshot once, outside the message transaction. Credential and manual-control resumes can retain a known ordinary app request only through a server-marked exact revision and its original owned source message. Personal facts and generic resumes do not inherit this authority. Completed action snapshots are not executed again after a resume. Uncertain outcomes are not retried automatically. External content, onboarding, generic background events and reactions cannot authorize writes. A scheduled run can execute a known ordinary app action only when its immutable saved user instruction and operational prompt both authorize it; draft/no-send and cross-app mismatches remain blocked. Source-checked personal self-statements retain their existing quiet-save path.

Goal create/update and schedule create/update/cancel are validated reversible local actions. They run within the exact owned current user segment without a natural-language phrase gate or an extra confirmation. The model is instructed to use reads for review-only requests, respect no-change and draft-only requests, and ask when the intended change is unclear. These instructions are not a semantic or prompt-injection guarantee. External app writes retain the conservative operation, scope and catalog checks. Goal and schedule rows also offer Delete with one local confirmation; deleting a schedule cancels future jobs and retains execution history.

The hosted storage path uses a server-selected `PrivateObjectStore`: a tenant-scoped private R2 broker for Cloudflare, PostgreSQL byte storage for local hosted child processes, and explicit S3 or filesystem adapters for custom hosting. PostgreSQL keeps owner/key identity, bytes and conditional versions in one atomic database write. Artifact bytes are stored durably before acknowledgement; metadata retains an opaque owned key. Actor-local directories are caches in this mode. Uploads are transferred to the selected workspace through a bounded binary transport before execution. Sessions and artifacts each have a 15 MiB cap. The filesystem adapter uses exclusive lock files and requires operator recovery after a process dies while holding one; it is not the default for cloud-style restart tests. Storage-provider changes require explicit byte/metadata migration; they do not silently reinterpret legacy paths. Conditional R2 cleanup can leave a private orphan after a failed metadata insert, requiring operator reconciliation. The restart, ownership and uncertain-action fixtures pass locally; live R2/container restart proof remains separate.

For the optional Cloudflare computer provider, checkpoints are separate private R2 archives, bounded to 256 MiB total, 64 MiB per file and 20,000 entries including the root. Browser profiles live under `/data/<owner-namespace>`; workspace files and CLI tools share `/home/node/state` through fixed symlinks. The helper verifies file/archive hashes and restores modes, executable bits and safe internal relative symlinks atomically. Workspace terminal acknowledgement waits for process-group drain and durable checkpoint completion. Browser idle quiescence can decline active holds or native sign-in; a normal stop may close sessions before checkpointing. Filesystem recovery does not preserve live DOM/process state or justify retrying an unfinished external action. Dirty recovery, lost acknowledgement or uncertain checkpoint/stop outcomes quarantine the role instead of automatically replaying work.

A shell command that finishes with a nonzero exit code returns its code and bounded diagnostic output to the model after its completed action receipt is saved. The assistant can correct an ordinary command error without treating it as an interrupted action. Cancellation, timeout/output limits, unknown execution outcomes and failed receipt writes still stop the segment and preserve the unresolved-action fence. Local real-supervisor/Pi regression tests cover recovery and these failure boundaries; production acceptance remains separate.

Published artifacts use owner-checked local download URLs, not public signed links. Supported raster images, audio, video and PDFs can open in the attachment viewer. Other files, including active HTML, download under restrictive headers instead of executing as an app preview. There is no separate safe HTML preview origin yet. Keep files, transcripts and profiles private; vault encryption does not encrypt every message/file.

Goals persist progress, status, target date and next action. Browser onboarding saves its detected IANA timezone in preferences; tasks use that saved zone, with Europe/Lisbon as the explicit default when no preference exists. Each execution starts with the current UTC time and local ISO timestamp, including its UTC offset and IANA zone. Every runtime prompt refreshes that clock, including secure continuation and resumed sessions. The runtime uses that context for relative dates and schedule requests rather than the host timezone. Preferences and source-backed facts enter bounded task context; history search retrieves previous work. This is explicit stored context, not a verified general memory-consolidation system.

Schedules persist a prompt and either an exact one-off timestamp or a recurring cron/timezone. Each next occurrence has a durable delayed job. One-off schedules disable after firing; recurring schedules keep wall-clock time across DST. Updates and pauses invalidate stale jobs. Execution history retains due time, title and actual execution status after schedule deletion; it does not prove the user objective was completed. If the service was offline, one overdue occurrence runs on restart and recurrence advances to its next future date.

Goals separates Active and Completed. Paused goals sit under Active and expand when there are no active goals. Schedule separates Upcoming and History; paused schedules expand when there is no upcoming work. Both pages keep saved data visible during background reads. A failed read offers Try again without clearing that data. Each action has a label that identifies its goal or schedule. Common recurring times use readable labels, such as Every 5 minutes, and History labels a successful execution Finished. Creation and changes open chat drafts; sending a direct pause, resume or concrete change request applies it without an extra confirmation.

A schedule created from a verified channel message retains that exact conversation. The server binds the accepted user message to its original inbox receipt; the model cannot supply a recipient. Every occurrence uses that saved route. Editing a schedule preserves its destination, including web schedules edited from Telegram. Delivery rechecks the current channel account, allowed sender and provider reply window. A timer does not extend that window. Uncertain sends are not replayed. The schedule service can inherit a parent route, but the existing action policy still prevents background agents from creating follow-up schedules; this change does not enable that behavior. These paths have synthetic transport and PostgreSQL coverage, including a real due-time dispatcher; this does not prove live Telegram or WhatsApp delivery.

The hourly heartbeat uses the cheap relevance classifier before starting main-agent work. Default quiet hours are 22:00–08:00 in Europe/Lisbon; saved user settings override them. They suppress automatic event and hourly-review task starts, but do not defer explicitly requested schedules. Triage permits at most two automatic event/review wakes per hour. Background runs suppress automatic prose and progress, sending only an explicit useful result or necessary question. Quiet/digest decisions can be revisited; a scheduled digest is not guaranteed. Polling, reviews and schedules require the local app and Mac to stay running, or the hosted pilot's gateway and tenant runtimes to remain available; hosted work does not require an open browser tab. [Personal service](../src/server/personal.ts), [triage](../src/server/triage.ts).

## Inspector, costs and evidence

Inspector capture stores masked tool arguments/results, fixed errors, timing and normalized assistant model usage. Payloads are bounded to 16 KiB and retained for seven days. Capture uses bounded persistence waits so unavailable inspection does not indefinitely hold execution. In ordinary local mode, `DEV_INSPECTOR=false` blocks access and new Inspector capture. Hosted capture requires both `DEV_INSPECTOR=true` on the operator configuration and the account's immutable user ID in `OTTO_DEVELOPER_IDS`; ordinary users and opted-out developers receive disabled capture. The gateway and actor independently deny computer and Inspector endpoints to non-developers. Existing records are not immediately erased when capture is disabled. These remain sensitive account diagnostics, not telemetry. Production builds expose the enabled Inspector through More; development also has a direct sidebar button.

Conversation-routing failure metadata has a narrow exception: strictly validated `relevance/conversation_route` operations with failed/cancelled status and no task/tool references retain a fixed code, optional HTTP status and bounded model/timing/usage fields even with Inspector disabled. No prompts, outputs, raw errors, causes or keys are captured. Recording remains private, nonblocking, limited to 128 pending writes and retained for seven days; Inspector endpoints stay gated. [The dated routing investigation](testing/results/2026-09-28-routing-diagnostics.md) separates the observed production refusal from the diagnostic change and its validation status.

The inspector starts with all owner activity. Screen follows the most recent actual browser activity, prioritizing a browser under manual control. Opening a text-only execution or inspecting an older message does not change the current screen. A failed metadata/screen refresh clears the stale frame and disables input until a fresh capture arrives. Open browser window opens the local `/browser` view with the same protected screen and take-control/resume controls, without the sidebar or other tabs; it does not navigate the user's browser to the visited website. Take control, fullscreen and Open browser window share one compact row. Narrow panels shorten the popup action to a labelled icon. Secure-capture pauses leave these controls available without a screen-hidden notice or empty placeholder block. Embedded screenshot polling pauses while that named window remains open, with a normal link fallback if a popup is blocked.

Activity starts with active outcomes and requests, including current waits and queued follow-ups, followed by saved upcoming schedule times and actual hourly-review registration. It shows the latest eight background decisions from the last 24 hours with full counts. It does not list every historical message as new work or copy raw heartbeat/event prompts. Paired execution history is visible directly below current work. Tools opens recent calls, with By tool for full retained counts and Available tools for descriptions and schemas. Models has a separate view of assistant requests, token categories and SDK estimates. Call payloads and schemas remain collapsible. Inspect from a message applies an optional execution filter to Activity, Tools, Models and Prompts. Costs remains owner-wide. The six labelled tabs wrap into two rows on a narrow panel and support arrows, Home and End.

The Costs tab groups visible operation/model summaries under each provider; only detailed metrics require expansion. Its visible subtotal comes only from the provider ledger, which includes assistant responses, Pi-reported compaction/cache warming and metered adapter operations. It is never added to the overlapping assistant-response subtotal. Async context links provider operations to the exact accepted tool call; Tools shows only those direct costs. Main-model charges are not divided arbitrarily among tools. Unknown prices remain unavailable, while partial rows show how many operations have prices. All totals cover the retained seven-day window and can be incomplete. Hosting and provider invoices are excluded; operation counts are not billable network request counts. Coverage metadata remains in the API for diagnostics, but the UI does not show a coverage inventory.

Prompts shows each snapshot's title, provider, model and session metadata directly, with separate disclosures for system instructions and the latest instruction sent to an agent session. A resumed session also receives its saved provider transcript; that transcript and image bytes are not copied into prompt snapshots. Snapshots use a separate private store with ownership/revision checks, known-secret and structured-secret redaction, bounded strings, at most eight pending writes and seven-day retention. Capture is best effort and does not block the agent. Structured masking includes JSON embedded in prose and nested serialized JSON, with bounded inspection and omission of incomplete or oversized structured sections. Startup and hourly prompt cleanup run even when capture is disabled; older snapshots are masked again on read. Titles and displayed metadata are redacted too. This is sensitive diagnostic data, not telemetry or a guarantee that arbitrary user text cannot contain secrets. A production build alone provides no authorization; hosted access depends on the authenticated gateway and actor checks. Event classifier prompts are not captured in this view.

The voice lives in `src/runtime/personality.ts`: calm, warm, brief and practical, with no em dashes or en dashes in its own prose, canned praise, repetitive progress filler or forced follow-up questions. Exact quotations, code and source material retain their punctuation. These are model instructions, not a destructive output-rewriting filter. Provider keys and secure Vault values are excluded from model inputs. Internal implementation disclosure is constrained by instructions and bounded output checks, not a guarantee against every prompt-injection attack.

## Replacement and next priorities

`src/ports` defines the capabilities. `src/runtime` owns agent policy/tools; `src/server` owns product state and authorization. Only [composition](../src/server/composition.ts) selects concrete `src/providers` adapters. `Agent`, `Computer`, `Workspace`, `IntegrationProvider`, `RelevanceClassifier`, `SpeechProvider`, `CredentialKeyStore` and messaging ports can be replaced independently, with explicit migration of transcripts, accounts, profiles, files or ciphertext. PostgreSQL/job replacement is a data/execution migration, not merely a factory change. [Replacement map](replacing-modules.md).

1. Expand the passing acceptance cases into ongoing regression scenarios. Include ambiguous same-site requests, preference corrections and multi-step secure waits; preserve credential and revision locks. The tested combined workflow now passes, but semantic routing is not guaranteed.
2. Verify the configured provider paths individually: connected-account actions/events, optional models and actual channel delivery. Keep fixture and live evidence separate.
3. Measure end-to-end latency, failed/unknown outcomes, complete provider costs and retention before optimizing or expanding scope.
4. Complete the hosted release gates: real Google and integration consent, signed event delivery, remote execution and profile restoration, private file recovery, Telegram delivery, live account isolation and deployment/rollback drills. The implementation already includes identity, actor isolation, private storage and leases; operational key rotation, backups, migrations, cost limits and abuse controls still require explicit validation before broader rollout. General desktop control, payment autofill and iMessage remain separate projects. [Production requirements](production.md).

Run focused tests during changes, then the checks described in [development](development.md). Record actual results in [verification](verification.md); update this guide and the owning `AGENTS.md` when an entry point or behavior changes.

## Visual identity

Otto uses primary pink `#ff91ac`, plum text `#1b1924`, accent `#bc3666`, warm canvas `#fefdfc`, sidebar `#fbf9f5`, and selected surface `#fceaec`. These are Otto theme tokens, not the older public n8n brand guideline colors.

Light and dark themes share semantic tokens for text, surfaces and action states. Light, Dark and System choices live in the account menu and Appearance settings; the mobile navigation menu exposes the same choices. System follows the operating system, and an explicit account preference persists on the server. Dark mode uses a plum canvas `#18171c`, light text `#f4f1f7`, lavender primary actions `#d5c4f3` with dark text `#281c3e`, and raised outline controls `#302b3b` with light text `#eee8f8`. Pink `#ff9fba` remains the selected navigation accent. Images and documents keep their original colors. [Earlier UI and contrast checks](testing/results/2026-09-25-themes.md) cover desktop and mobile samples; hosted account persistence has separate fixtures.

Albert identified **EK Baumer** as the new brand typeface in the team's 2026-09-14 design discussion. Baumer files were not found in the available checkouts or local font folders. The current bundled fallback is Manrope, with its SIL Open Font License. Replacing it with Baumer requires the font assets; do not label Manrope as n8n's new brand typeface. [Typeface source](https://erkinkaramemet.com/baumer-info/).

Otto can explain its nonsecret capabilities and setup when the owner asks, using only trusted available context. Unknown model/provider versions remain unknown.
