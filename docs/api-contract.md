# Internal API contract

Local mode uses a fixed development account. It restricts `Host` and any supplied `Origin` to supported HTTP loopback aliases at the configured port; ordinary local routes allow an absent `Origin`. Account mutations and hosted browser mutations require the exact configured `Origin`. Hosted mode uses the Google-authenticated gateway to select an isolated tenant runtime from the verified session, with HTTPS required for public origins. JSON errors have `{error: string}`. Forwarded-host headers do not change the accepted host or tenant identity.

## Authentication and account settings

`SessionResponse` is defined in `src/shared/account.ts`: `{auth:{mode,googleAvailable},user,settings,capabilities:{developer}}`. The public user contains only ID, display name, email and the private avatar route. Google OAuth tokens and upstream avatar URLs remain server-side. `/api/account` edits the app account presentation; `/api/profile` remains the separate personal context the assistant uses. Other authentication-provider routes are not exposed. Completing onboarding waits for the same preparation as `/api/account/prepare`, then rechecks the session before saving. A failed preparation leaves onboarding incomplete and does not undo the Google identity. Preparation uses the immutable tenant owner and never returns provider credentials or sandbox IDs.

`/privacy` is a public web route available before sign-in. The gateway loads the optional `OTTO_PRIVACY_NOTICE_FILE` UTF-8 Markdown file at startup, bounded to 128 KiB and 32,000 characters. The API returns only its public text, not the path or gateway environment; neither configuration nor text is forwarded to a tenant. Omitting the setting permits startup with `content:null`; a configured unreadable or invalid file fails startup. The operator must configure and review the notice before sharing a hosted signup link. [Operator template](privacy-notice-template.md).

Hosted private requests use the session cookie. The browser also sends `X-Otto-Account` as an expected-account fence: a stale value returns 401 and cannot select another tenant. Native image and event requests include the expected account in their guarded URL instead. SSE requires `/api/events?account=UUID`, is checked again after runtime startup and closes after session revocation is detected. Private responses are `no-store`, except owned raster avatars with a short private cache. Runtime responses cannot set browser cookies.

The gateway and tenant both restrict `/api/browser*` and `/api/inspector*` to the operator-assigned developer capability. An ordinary user cannot gain it by sending headers, query parameters or request body fields. The operator selects the computer provider at startup; no user-facing provider selection endpoint exists.

Tenant-only `POST /api/runtime/drain` and `POST /api/runtime/resume` require the signed `deployment` capability. Both accept exactly `{nonce:UUID,targetRelease:40-character lowercase commit SHA,deadline:epoch milliseconds}`. Drain accepts a deadline up to ten minutes ahead, pauses new work without aborting accepted work, and returns `{ok:true,nonce,targetRelease,generation,drained:true}` only after consumers and admitted work finish. A missed deadline or failed drain returns a fixed error and leaves the pause in place; new ordinary requests receive 503. Resume must match all three fields and returns `{ok:true}`; its latest successful request can be retried after a lost response, but a stale request cannot reopen a newer drain. Lease renewal remains available while paused. These routes do not accept browser sessions. E2B receipts add `computerPaused:true` only after its same-owner computer acknowledges a non-forced pause; resume must safely reopen that same allocation before consumers restart. Cloudflare computer checkpoint and stop evidence remains separate.

Cloudflare operator-only `POST /api/deployment` accepts at most 2 KiB of exact JSON `{action:'prepare'|'status'|'activate'|'abort'|'complete',nonce:UUID,targetRelease:SHA,previousRelease:SHA,deadline:epoch milliseconds}`. `X-Otto-Deployment` carries a short-lived, replay-protected HMAC envelope derived for this purpose and environment from the gateway master key; it binds the method, target and body. A Google session or runtime secret does not authorize it. The fixed gateway Durable Object stores the operation identity and phase before invoking the Node coordinator. Responses are `{ok:true,state}`; `status` may return `state:null` before initialization, while a stored state includes the immutable identity, phase and owner/generation receipts. Failures return fixed errors. Prepare drains tenants and requires clean computer/tenant stop receipts; activation requires a prepared unexpired operation, and completion requires the target release. Abort is limited to the previous release before activation and never clears uncertainty. A closed barrier rejects ordinary ingress with 503 while permitting its authenticated control and exact anonymous release smoke routes. See the [rollout and recovery runbook](../deployment/cloudflare/README.md#rollout-and-verification).

Web routes: `/` chat, `/goals`, `/schedule`, `/vault`, `/apps`, `/channels`, `/vault/:id` secure form (`/credentials/:id` remains an alias). `/browser` shows the shared current browser screen/control view without requiring the inspector flag. `/dev` opens chat with the inspector; `/you` is a compatibility route to chat. Channels has secure setup forms; model provider setup uses server environment configuration. Do not show fixtures as live results.

Channel `webhookStatus` is `registered`, `manual_setup` or `registration_pending`. Telegram webhook setup saves the encrypted desired configuration before local activation and remote registration. An incomplete activation returns HTTP 503 with fixed recovery guidance and retains `registration_pending`; startup retries that same saved configuration after creating the channel transport. The Channels page offers Finish setup guidance and a direct confirmed Remove channel action. Disconnect removes the pending ciphertext. Polling and WhatsApp setup keep their existing save behavior.

`GET /api/schedule-runs` and `GET /api/schedules/:id/runs` accept `limit` (1–100, default 20) and an opaque `cursor`, returning `{runs,nextCursor}`. History remains available after a schedule is deleted and returns only owned execution rows.

Vault detail, password, card-number and security-code reads accept a saved entry UUID and an empty JSON object. They resolve the owner on the server, preserve the type-specific authenticated encryption binding, and return fixed errors for missing or unreadable entries. All use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Private Vault lists include full login usernames and masked card metadata; broker login lists and secure account choices retain masked username hints. Login metadata includes optional `identifierLabel`: a normalized observed field label, bounded to 80 characters and retained through staged saving and edits. New manual entries infer Email only for a valid email address, otherwise Username. Legacy private detail/list reads infer that fallback without changing ciphertext. Clients cannot override this metadata. No agent or Inspector tool can call these reads.

Vault updates accept a UUID, a nonempty trimmed name up to 100 characters, a username up to 320 characters and an optional password up to 8192 characters. Unknown fields, including origin and owner overrides, are rejected. An omitted or empty password preserves the latest encrypted password. Updates lock and recheck the owned record after key access, preserve its exact origin and ID, and return only masked metadata with the same no-store/no-referrer headers. Full login usernames may be held in the private Vault page cache; passwords, full card numbers and security codes are excluded. Closing or navigating away fences late edit responses; cancelling an HTTP request does not undo an update already accepted by the server.

Card creates require `kind:"card"`, a name up to 100 characters, cardholder up to 200 characters, card number up to 40 input characters and numeric expiry month/year; optional `securityCode` accepts three or four digits. Numbers normalize spaces/hyphens to 12–19 digits, reject repeated digits and require Luhn. Expiry ranges from the current month through 30 years ahead. Card updates use `VaultCardUpdate`; omitted `cardNumber` preserves the latest locked value; a supplied blank or whitespace-only number is invalid. Unknown fields, including owner and origin, are rejected. An omitted or blank `securityCode` preserves the latest locked value; `null` explicitly removes it. Details return only `hasSecurityCode`; neither lists nor create/update replies contain code presence or value. Cardholder, number and security code are encrypted together. Create/update replies never include the cardholder or full number. Cards live separately from website logins and cannot be used by secure login selection or automatic fill.

See `src/shared/contracts.ts` for response types. Attachment-only messages are accepted; empty messages without attachments are rejected. `Message.streamId` associates a persisted reply with its transient stream. Action confirmations are ordinary `/api/messages` yes/no submissions. They bind to the latest owned pending confirmation in that channel, or its explicit reply target. The saved action, account and arguments execute once in a durable worker segment; there is no approval HTTP endpoint or separate approval page. Paused schedule records remain editable; DELETE removes the schedule but retains its run snapshots. `Schedule` includes `kind`, nullable `cron`/`runAt`, `revision`, exact `nextRun` and `lastRun`. One-off `runAt` must include a UTC offset and be in the future when created or resumed; the saved timezone remains available for display. `ScheduleRun` includes title, schedule ID, execution task ID, due time, timezone, creation time, status and fixed task error. Status describes execution, not inferred user success. Revision checks reject stale jobs after edits, pauses or deletion. Already dispatched executions continue independently.

`/api/state` task metadata and chat history contain only the current owner's web conversation. Live deltas require that same owner and the exact `web` channel at both publication and SSE delivery; routing identity remains internal. Telegram and other channel replies never enter the web event stream. Background web results appear through persisted messages and refresh signals.

Messages belong to one visible conversation per channel. A short answer follows the latest visible assistant question. An explicit `replyToMessageId` must reference an owned message in the same channel; it resumes idle work, queues a related input behind active work, or starts new work for a cancelled session. When configured, bounded semantic routing can associate other follow-ups with a new or existing owned outcome. Related inputs can wait behind credential/approval/manual steps without resuming those steps; password waits retain their private-form requirement, while a matching pending OTP request uses the trusted chat path below. The response includes the internal task ID, but there is no task picker or ambiguous-task response. Credential and manual-control waits require their dedicated broker path; OTP replies enter that path through `/api/messages` before ordinary routing. Confirmation replies use the same message route with owner, channel, generation and revision checks. `Message.replyTo` includes a bounded quoted preview; `Message.reactions` contains user and assistant reactions. A changed user reaction can wake one quiet event task; repeating or removing it does not. Assistant reactions target only visible owned user messages in an active direct-user web segment and never wake another task. Each message permits one reaction, with a durable five-minute cooldown between new reactions; unsupported channels skip the operation. Message history uses the oldest message's timestamp and ID together to avoid duplicate or omitted rows at timestamp ties.

Implementation ownership and change guidance live in the area's `AGENTS.md`, linked from the root guide.

`clientMessageId` becomes the persisted user message ID and lets the client reconcile an optimistic bubble with HTTP or SSE updates. Omit it to receive a generated ID. An identical retry returns the original accepted message and execution without enqueuing work again. Changed text, ordered attachments, reply target, owner, channel or conversation generation return 409; reset never permits replaying an archived message ID into the new conversation. Accepted user execution failures publish one concise, fixed assistant reply through the normal channel path. Stale, cancelled and background executions do not publish that failure reply.

`AppState.verificationRequests` contains at most 50 current owned web OTP requests as `{id,taskId,expiresAt}`. It contains no code, recipient, form token or saved login. A `/api/messages` reply containing only four to eight digits can match a pending request in the same channel/current conversation. `replyToMessageId`, the internal `taskId` or `verificationRequestId` can narrow the match. Several matches or a not-yet-ready request return 409. A reply target outside the owned current conversation or an unavailable `verificationRequestId` also returns 409. The legacy `taskId` alone does not require OTP handling: if it selects no current OTP request, ordinary numeric routing can continue. A code-shaped reply with attachments or `forceNew` returns 409 when an OTP request applies; those options cannot bypass private handling. Without a pending match, ordinary numeric messages keep ordinary message behavior.

A matched OTP reply is handled before ordinary text persistence and model routing. `SubmitMessageResponse.verificationStatus` is `"pending" | "submitted" | "rejected" | "unavailable"`. An in-flight duplicate returns `"pending"` and `messageText: "Verification code received securely."`; the persisted receipt uses the same text until the broker finishes. Completed submissions return `messageText: "Verification code sent securely."` with the final submission status. Clients must use the authoritative text; `pending` does not mean the code was applied, and `submitted` does not prove website authentication succeeded. The frontend masks a code-shaped pending bubble, including one with attachments, and does not retain the code for retry or restore it as a failed draft.

Idempotency stores a masked receipt, submission status and a keyed HMAC fingerprint. The fingerprint uses a distinct key derived from the existing Vault key and binds the code to owner, channel and client message ID. Exact retries return the existing receipt without reinjection; a changed code or incompatible retry payload returns 409. Legacy receipts without a fingerprint also return 409. Key access occurs only after a stored verification receipt or matching pending code request is found. If its key is unavailable, that verification submission returns a fixed 503. Ordinary numeric messages do not require a Vault key. Raw codes are never retained for comparison. Submission checks the task revision, exact origin and freshly observed OTP fields through the same broker as secure forms.

Telegram and WhatsApp run the same interception before writing a verified owner message into the local inbox. Numeric classification and an ordinary receipt commit together under conversation and task-row locks. Vault request insertion takes the same task-row lock, so an OTP request cannot appear between that classification and receipt persistence. A number accepted before the OTP request remains ordinary input. Browser inspection and code injection run outside this classification transaction. Provider-side message retention is outside this API.

Inspector response types live in `src/shared/inspector.ts`. Observation cursors require both timestamp and ID. Each unfiltered page contains at most 100 combined tool and model records, newest first, with a cursor for earlier records. `tool` selects that registered name's tool-call pages. Summary totals and `toolUsage` counts cover all retained records for the owner or optional owned task, independent of the current page/filter. The UI has Screen, Activity, Tools, Models, Costs and Prompts tabs. `costUsd: null` means unavailable, not free. Selected-task assistant response costs are SDK estimates, not invoices or per-tool charges. The catalog is available before the first task and does not execute tools. All inspector endpoints return 404 when disabled and use the same local access checks as other API routes.

`GET /api/inspector/work` takes no scope/query arguments and returns `InspectorWorkResponse` from `src/shared/inspector-work.ts`. It contains up to 12 current owned active outcomes/requests with pending input counts, eight enabled schedules with persisted next times and queued state, actual review registration and the latest eight decisions from the last 24 hours. Each list includes its full total. Active executions are grouped by owned outcome and filtered to the current conversation generation. Labels/reasons are redacted and bounded; raw task prompts/event summaries are excluded. Review status is null when unavailable and never invents a next occurrence. It is read-only and no-store.

`src/shared/provider-usage.ts` defines provider summaries and coverage rows. The wire field `requests` counts adapter operations, not billable network requests; internal SDK calls can differ. Rows include failure/cancellation counts, duration, nullable metrics, `costUsd`, `pricedRequests` and `pricing` (`reported`, `sdk_estimate`, `mixed` or `unavailable`). Pi-reported compaction/cache-warming usage appears here separately from assistant-response totals. Speech seconds/prices, SDK-internal requests, hosting and invoice data remain incomplete or unavailable, as coverage rows state. Ordinary recording requires enabled Inspector. Strict `relevance/conversation_route` failures/cancellations without task/tool references also retain a fixed failure code, optional HTTP status and existing bounded model/timing/usage fields while Inspector is disabled. All recording stays private with seven-day retention and at most 128 pending nonblocking writes; provider arguments, outputs, raw errors/causes, keys and manual input text are excluded. Inspector endpoints remain disabled with the flag; this exception adds no public diagnostic response. `droppedEvents` signals incomplete capture and old activity is not backfilled.

`src/shared/link-preview.ts` defines `{url,title,description?,siteName?,imageUrl?}`. Image URLs are only `/api/link-preview/image/<UUID>`, never a caller-supplied proxy URL or remote source. Metadata and images use public-address validation, pinned DNS resolution, bounded redirects/size/time and no browser cookies or page JavaScript. Known local, sign-in, consent, Vault, approval and token-bearing URLs are excluded; arbitrary public URLs can still contain private text unknown to these heuristics. The client requests at most two previews per persisted message near the viewport and keeps original links when metadata is unavailable.

Connections return one row per saved account, plus a disconnected service row when no account is saved. `connectionId` is the local account selector; `accountName` and `accountEmail` come from the provider. Google tool arguments may include `connectionId`; multiple accounts require a selection, and write approvals retain it. The server removes this selector before calling the provider. Watches are always requested for supported services. `triggersActive` and `triggerStatus` distinguish actual subscriptions from pending or unavailable delivery configuration. Legacy service-only disconnect and trigger endpoints reject ambiguous accounts. Onboarding offers connection links in chat and can read connected data, but cannot create a connected-data write approval or execute a write.

Discovered accounts use the same `Connection` rows, with `accessPaths:[{id,kind,endpoint}]`. Token `accountName` is the label entered in the private form; a generic OAuth account uses the service name. `GET /api/apps/discovery/:id` returns the pending service name, optional setup step and URL, reviewed path addresses and the HTTP GET test path, and the exact callback URL when the user must register a client ID, without a secret. A token path uses `POST /api/apps/discovery/:id/complete` with `{accountName,token}` and returns `{ok,continued}` after an access check and a one-use save. An OAuth MCP path uses `POST /api/apps/discovery/:id/authorize` with `{clientId?}`. It returns a service sign-in URL. The OAuth callback uses `/api/apps/callback`, checks the hashed state and pending grant, then saves the account and resumes its task. Each proposal uses the fixed owner and expires after 15 minutes. Standard account disconnect accepts a discovered connection ID under its exact service slug. `manage_apps propose` takes `{service,name,connectionId?,setupUrl?,setupText?,paths:[{kind,endpoint,auth?,testPath?,scope?,clientIdRequired?}]}`. A proposal has one to four paths; `kind` is `mcp` or `http`, and an HTTP path needs a GET test path. OAuth uses one MCP path in a proposal. `apps SEARCH_TOOLS` adds a `discovered` list with account IDs, path IDs, and matching MCP tools. A service-name query also returns up to 200 tool names and the full tool count. `CONNECTED_MCP_CALL` takes `{connectionId,pathId,tool,input}`. `CONNECTED_HTTP` takes `{connectionId,pathId,method,path,body?}`. Write requests return the current `requiresApproval` result before the trusted adapter runs them.

Manual browser control uses a 30-minute lease. The `workspace` path starts an owner-bound standalone session without creating a task. Finished tasks retain their profile and use a separate control revision bound to their unchanged terminal status and task revision. Active tasks use the exact paused task revision. Every input and completion rechecks ownership and the lease. Start waits up to ten seconds for runtime actions to drain; failure leaves active work paused. New standalone and terminal leases use a process-random revision sequence so restart cannot reuse a prior lease. Expired leases require reacquisition. Manual inputs are not stored in messages, events or observations. The input contract is `BrowserInput` in `src/shared/browser-input.ts`: bounded normalized click coordinates, text, allowed key/modifier combinations, scroll direction or bounded wheel deltas. The client forwards input from the focused browser image, including paste and composition text; Shift-Escape leaves that focus. It serializes a bounded input queue, drains accepted input before completion and drops unsent input on blur, hiding or a session change.

`POST /api/credential-requests/:id/refresh` re-inspects the current login page without entering credentials. It locks the owned task and pending request, checks its revision, status, expiry and exact origin, and returns updated field and method metadata. Stale requests cannot refresh.

Pending non-OTP `CredentialRequest` responses can include `savedEntries` metadata and a `selectedEntryId`. Entries must match the owner, exact origin and any staged identifier. They contain names and masked username hints, never passwords or full usernames. Saved selection uses the same one-use token, revision lock, fresh page inspection and continuation path as direct entry. A new login does not overwrite another entry on the same website.

Identifier-step submissions accept `{label,username,password}` so one secure form can cover a staged login. Only the identifier enters the first observed page; an encrypted, expiring server-side selection supplies the later password step once after fresh inspection. It survives broker restart and is cleared before password injection. OTP input uses the trusted chat path and is never persisted as a raw code. The compatibility credential endpoint still accepts `code`. Sign-in and verification methods are chosen in chat before requesting credentials.

Before creating an OTP request, the server may attempt a trusted matching Gmail lookup. There is no model-facing email-code endpoint. The observed full recipient, encrypted selected login and one active Gmail identity must match. The broker limits lookup to recently accepted credential entry, five candidate messages and eight seconds, requires an authenticated sender in the website's registrable domain and one unambiguous code, and rechecks origin, revision, selection and account state before injection. Mail content, codes and trusted `emailCode` inspection metadata are omitted from model tool results and persisted request inspection. Failure falls back to the chat request.

Credential submission normally returns `{ok:true}`. A recognized fresh website rejection returns HTTP 200 with `{ok:false,retryUrl,error}`. The old token is consumed, the replacement `/vault/<token>` keeps the same owner, task revision and original expiry, and the task stays waiting without a model resume. Rejected passwords are not saved. The client clears entered values and loads the replacement form. Submission is not proof of successful authentication; delayed or unrecognized results still require browser inspection.

`POST /api/conversation/reset` with `{}` returns `{ok:true,conversationRevision}`. It archives the current web chat, cancels its active work and invalidates old waiting continuations. It preserves messages in storage, saved accounts, Vault entries, profile/memory, goals, schedules and other channel conversations. No restore button or permanent deletion is implemented. `AppState.conversationRevision` and SSE delta `conversationRevision` let clients reject old state and stream callbacks. Message submissions, history requests and onboarding accept an optional `conversationRevision`; a stale value returns 409. Reply targets and reactions cannot address archived messages.

Reaction values must be one Unicode emoji grapheme, including supported joined sequences, modifiers and flags. Legacy like/dislike/heart values map to their existing emoji and deduplicate against the equivalent emoji. Vault invitations name the broker-observed site and step; sign-in method choices stay in chat before an invitation. Arbitrary page labels and secret values are excluded.

`GET /api/inspector/prompts?taskId=&before=&beforeId=` returns bounded private prompt snapshots for the owner, optionally scoped to one owned execution, with combined timestamp/ID paging. Capture and access require the enabled Inspector. Its production-build menu entry does not override `DEV_INSPECTOR=false` or local-access checks. Responses are no-store; system/instruction text and titles are redacted. Images and saved provider transcripts are omitted. `GET /api/inspector` also exposes owned `currentBrowser` metadata from actual browser activity independently of a diagnostic task filter. Tool observations accept no taskId for an owner-wide view and return direct provider-operation counts and cost per tool/call; overall cost comes only from `/api/inspector/providers`.

Native sign-in uses the same revision-bound takeover lease. Input requests in `sign_in` mode go only to the private container desktop adapter. Its dedicated frame route rechecks ownership, revision and expiry after capture and never retains pixels. Ordinary screen capture returns 423 while native sign-in is pending, including after a restart. Expiry, cancellation and reset close the owned window without restoring automation. Explicit continuation waits for its process to exit and preserves the pause on failure. In local mode, core browser routes are available without `DEV_INSPECTOR`; Inspector-prefixed aliases and diagnostics remain flag-gated. Hosted mode additionally requires the signed developer capability for every browser and Inspector route.

## Hosted service ingress

Composio posts signed raw bytes to `/api/webhooks/composio`. The gateway verifies the signature and event owner before selecting an existing tenant; the tenant verifies the owned account and active subscription before accepting the event. Body/query owner hints cannot select a different tenant.

Hosted Telegram and WhatsApp use `/api/webhooks/{provider}/{opaqueToken}`. The environment-specific token resolves only a registered tenant and is not sufficient to authenticate a message: the tenant must also verify the provider secret or signature. WhatsApp permits its verified GET challenge; Telegram permits POST only. Local single-owner mode retains `/api/webhooks/telegram` and `/api/webhooks/whatsapp`. Unknown hosted owners are acknowledged without creating a tenant. Webhook payloads are bounded to 256 KiB.

Only these exact callbacks bypass browser Origin checks, and cookies/authorization headers are not forwarded to providers or tenant ingress. The private `/api/internal/channels/claim` and `/release` routes require a signed current-generation runtime envelope and an active SQL lease, checked atomically with the channel claim. Browser sessions cannot call them. `/api/runtime/*` is never a public gateway capability.

`POST /api/apps/:slug/connect` accepts optional `{returnTo:'apps'|'onboarding',connectionId?}`; `returnTo` defaults to `apps`. A discovered account ID selects its saved path template, including when the service slug is in the native catalog. Its new proposal returns to Apps unless it belongs to a chat task. For native consent, the server stores `returnTo` with the expiring, owner-bound attempt, and the callback returns to that screen on the configured app origin with a status. It never trusts an arbitrary redirect URL. A chat tool can start the same attempt with a trusted `chat` destination and a task revision. A successful callback queues that task only if its owner, conversation, status, and revision still match. The onboarding screen starts consent directly and renders one compact connected state per app. Apps retains account management and shows connected and available services.
