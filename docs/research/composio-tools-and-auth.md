# Composio tools and authentication research

Research date: 2026-10-07. Evidence combines public documentation, repository inspection, dashboard and read-only account/auth metadata, configuration matching, local UI checks and user-initiated sign-in. Provider identity lookups are used for account labels; this research requests no mailbox, repository or issue content and no app writes. Released-code references use commit `ed66ff0b64d48f890ebedb840b63c0ea26c984c5` (desktop 0.1.8). The local implementation now includes main `7a1b839` and is assessed separately below; onboarding changes were explicitly reverted. Hosted health reported `8d71636` during this research, so source inspection is not proof of the deployed implementation.

## Recommendation and current state

**Keep Otto's own Google OAuth app for signing into Otto. Prefer Composio-managed authentication where it works, with explicit custom configs for apps that need them. Replace the fixed app list with a searchable server-side Composio catalog.** Existing execution and connection infrastructure supports this; Composio's catalog needs no second generic MCP layer.

The current decision shares `otto_alpha_release` between active isolated development and the current release. Key-only users automatically select its existing custom Google configs during sign-in; explicit overrides remain supported. The older normal development profile remains unchanged to preserve its connections. Cloudflare work is explicitly deferred.

Before the local implementation:

- Auth-config IDs come from environment/configuration, while the app list is hard-coded. Changing Composio configuration alone cannot expose another built-in app.
- Both development and the saved Cloudflare configuration explicitly select custom OAuth for Gmail, Calendar, Drive, Sheets and Docs. Slack and Notion select managed configs. These are app grants, separate from Otto login.
- Otto already supports Tool Router search/execution, official Notion/Linear MCP connections, and agent-proposed remote MCP, HTTP and installed CLI connections.
- A shared Full access Composio project key is currently entered into desktop settings. Desktop users can reveal it. Unique owner IDs organize normal requests but do not isolate customers who possess the project credential.

Composio's production guidance permits managed auth. Custom credentials remain useful for scopes, consent restrictions, branding, dedicated quotas or customer requirements. Older direct-auth guidance recommends custom production credentials. [Current production guidance](https://docs.composio.dev/docs/production-readiness), [legacy direct-auth guidance](https://docs.composio.dev/docs/tools-direct/authenticating-tools).

## Local Apps behavior

The Apps page now groups exact native and `_mcp` variants under one app card, including Linear, Notion, Calendly, Canva, ClickUp, Monday, Sentry, Stripe, Supabase and Todoist. Display names omit the trailing MCP label. Saved accounts retain their original provider, toolkit slug and connection ID; grouping does not migrate them or change their permissions. The preferred available base integration handles new connections, with an available MCP fallback. Adding an account preserves an existing variant when the family has no base account.

Connected cards retain the app description. Truncated descriptions open a bounded popover on hover, focus or activation; Escape and Tab release focus, and arrow/page keys scroll longer text. Search and categories stay pinned while browsing, with the category picker above the toolbar. All and Connected tab counts show total app families independently of filters. Empty results offer a neutral clear-search or clear-filters action; loading and catalog errors have separate states. The quieter Ask Otto in chat action carries the current search into guided custom setup. Catalog Connect buttons stay neutral. Manage uses compact account rows, heading focus and a quieter Done button; disconnect remains bound to the original account and confirmation. Closing a mouse-opened dialog restores focus without a lingering outline. Keyboard interaction retains the visible focus indicator.

Account labels use Composio's bounded `state.val.displayName` without treating it as a verified email or changing account ownership. GitHub's live label was verified through this path. Sentry's token-response user name was literally `REDACTED`, so it is excluded along with other redaction placeholders; the existing account-bound profile mechanism instead uses `SENTRY_VALIDATE_CREDENTIAL`. Only the returned user's name/email are retained, not its auth metadata. Missing metadata falls back to the app's name, and previously saved redaction placeholders are hidden. [Composio identity guidance](https://docs.composio.dev/docs/authentication/manually-authenticating#identify-the-connected-account), [Sentry toolkit](https://docs.composio.dev/toolkits/sentry).

Chat connection buttons use the same logo component as Apps. Their branding comes from owned, unexpired setup-link metadata, matched by a link hash or discovery proposal ID. Labels cannot select an arbitrary brand or image. Completed links remain hidden; unknown or expired links use a neutral icon. The existing pending Notion button was visually verified with its bundled logo at desktop and 375px widths, without starting another sign-in or model turn.

Replacing the direct adapters needs a separate capability decision:

- **Linear:** Otto's official MCP connection uses both a read-only endpoint and read-only OAuth scope. Composio's native Linear toolkit supports broader issue/project/comment workflows and triggers, making it a candidate for new connections that intentionally grant broader access. Neither Composio variant has been verified as an equivalent read-only replacement. The current default and existing connected account remain unchanged. [Linear access contract](https://linear.app/docs/mcp), [Composio Linear](https://docs.composio.dev/toolkits/linear), [Composio Linear MCP](https://docs.composio.dev/toolkits/linear_mcp).
- **Notion:** retain the direct official MCP default for now. Native Composio Notion has selected-page integration semantics; the MCP path provides user-oriented search, including connected sources where available. Otto already implements the required `notion-get-tool-access` check, which is absent from Composio's current public MCP tool list. Verify that parity before replacing the direct adapter. [Notion supported tools](https://developers.notion.com/guides/mcp/mcp-supported-tools), [Composio Notion](https://docs.composio.dev/toolkits/notion), [Composio Notion MCP](https://docs.composio.dev/toolkits/notion_mcp).

These findings compare documented capabilities, not authenticated Composio Linear/Notion execution. Dynamic client registration avoids manually creating an OAuth app, but does not imply identical scopes or tool coverage.

## Dynamic app catalog design

The desired flow is: **search an app or capability → show supported connection methods → consent once → resume the task with the selected account**. Users should be able to browse available apps before connecting anything.

The local implementation uses a cached server-side catalog from Composio toolkit metadata, exposing eligible apps and their display metadata through Otto's API. Apps and agent discovery share this catalog. The curated featured list supplies navigation and fallback entries rather than limiting execution. The runtime needs Toolkit read permission; a future broker could supply the catalog without exposing a project key. Auth-config administration remains operator setup. [Toolkit catalog API](https://docs.composio.dev/reference/api-reference/toolkits/getToolkits), [key permissions](https://docs.composio.dev/reference/authenticating-to-composio/project-api-key-permissions).

The local implementation retains these explicit registrations:

| Location                                 | Purpose                                                                                                     |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `src/shared/integrations.ts`             | Eight featured apps, tailored names/descriptions and fallback entries                                       |
| `src/web/components/service-logo.tsx`    | Bundled logos for those apps; other apps use validated catalog logos                                        |
| `src/server/composition.ts`              | Seven named auth-config environment overrides                                                               |
| `src/providers/composio/integrations.ts` | Dynamic catalog, seven legacy fallbacks/version pins, four event subscriptions and identity/file exceptions |
| `src/providers/direct/integrations.ts`   | Explicit direct Notion and read-only Linear action mappings                                                 |

Adding an eligible Composio catalog app requires no new featured entry or action mapping. Subscription support and special handling remain separate capabilities.

Original design considerations, with links to the inspected released baseline:

1. Replace the fixed service union and schema/toolkit validators with validated catalog IDs. The released enum rejects toolkits outside the eight-item list, even if Composio supports them. [Provider validation](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/providers/composio/integrations.ts#L15-L35), [execution routing](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/server/integrations.ts#L872-L879).
2. Prefer managed authentication with verified consent, retaining explicit custom exceptions. Persist auth-config IDs in operator configuration; avoid a new environment variable per app. Existing mixed projects need deliberate selection because omitting an ID can choose an existing custom config.
3. Create new sessions with the relevant catalog/toolkits. Keep existing saved sessions and their account routing intact for this isolated rollout. Current persisted sessions are restored when a fixed configuration version equals `3`. [Session restoration](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/server/integrations.ts#L304-L335).
4. Preserve account ownership, selected method, secure consent, cancellation, files and continuation. More tools within an existing Composio toolkit already work through generic schema search/execution.
5. Verify action classification before widening the catalog. The inspected baseline infers effects from names/methods and allows unknown effects in read-only turns. New toolkit names and generic MCP actions need regression coverage; catalog metadata cannot substitute for authorization. [Effect classification](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/shared/action-effect.ts#L77-L97), [trust decisions](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/server/trust.ts#L138-L169).

## Managed Google and Google Super

Composio advertises managed OAuth for [Gmail](https://docs.composio.dev/toolkits/gmail), [Calendar](https://docs.composio.dev/toolkits/googlecalendar), [Drive](https://docs.composio.dev/toolkits/googledrive), [Sheets](https://docs.composio.dev/toolkits/googlesheets) and [Google Super](https://docs.composio.dev/toolkits/googlesuper). Check `composio_managed_auth_schemes` and approved scopes for every selected toolkit. [Managed-auth catalog](https://docs.composio.dev/toolkits/managed-auth).

Google Super is worth a prototype for one “Connect Google” flow: one connection can cover supported Workspace services with appropriate scopes, using `GOOGLESUPER_*` tools. Existing separate-toolkit accounts do not automatically become one Google Super grant. [Google Super guide](https://docs.composio.dev/kb/guide/toolkits-googlesuper).

Managed consent displays Composio branding and shares provider quotas; managed polling triggers have a 15-minute minimum. Custom scopes cannot exceed the managed app's approved permissions. Scope changes generally require existing users to reconnect. Gmail settings actions can need scopes beyond ordinary mailbox access, such as `gmail.settings.basic`. [Managed/custom tradeoffs](https://docs.composio.dev/docs/authentication/custom-app-vs-managed-app), [scope controls](https://docs.composio.dev/docs/authentication/controlling-scopes), [Gmail constraints](https://docs.composio.dev/kb/guide/toolkits-gmail).

Google's external testing limits—100 listed test users and ordinarily seven-day authorizations—apply to testing OAuth apps, not automatically to Composio's managed production apps. Restricted scopes can require verification/security assessment; Workspace administrators can block third-party apps. Validate Otto's intended scopes and production arrangement rather than assuming every operation is covered. [Google audience settings](https://support.google.com/cloud/answer/15549945?hl=en), [restricted scopes](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [Workspace controls](https://developers.google.com/identity/protocols/oauth2/production-readiness/google-workspace).

## MCPs, CLIs and discovery beyond Composio

| Surface                      | What it means for Otto                                                                        |
| ---------------------------- | --------------------------------------------------------------------------------------------- |
| MCP-backed Composio toolkit  | Ordinary catalog tools; expand the catalog/auth support, not the transport stack              |
| Composio session MCP         | Alternative transport for the same session; does not unlock a different catalog               |
| Composio Custom MCP          | Imports a public remote server as a custom toolkit; experimental lifecycle and authentication |
| Direct external MCP/HTTP/CLI | Existing Otto proposal/setup path; expand discovery and compatibility as needed               |

Examples include [Granola MCP](https://docs.composio.dev/toolkits/granola_mcp), using DCR OAuth, and [GitHub MCP](https://docs.composio.dev/toolkits/github_mcp), using API-key auth. Native DCR toolkits can have an empty `composio_managed_auth_schemes` list while advertising `DCR_OAUTH` in `auth_schemes`; the catalog includes that case because registration happens during consent without Otto supplying a static OAuth app. API-key-only and custom imported toolkits are not automatically included. Session MCP headers can contain privileged credentials; SDK execution modifiers do not apply to direct hosted MCP calls. [Sessions via MCP](https://docs.composio.dev/docs/sessions-via-mcp).

Custom MCP imports/proxies rather than hosts servers, supports public HTTPS with no auth/API key/DCR, and requires later resyncs for schema changes, with a 500-tool maximum. New user-private/project-wide access controls remain in pilot; confirm the available lifecycle before depending on them. [Custom MCP guide](https://docs.composio.dev/docs/extending-sessions/custom-mcp), [custom-toolkit API](https://docs.composio.dev/reference/api-reference/toolkits/postCustomToolkits).

Otto already proposes remote MCP with bearer/API-key/OAuth, HTTP with bearer/API-key, and installed service CLIs with a Vault grant injected per execution. Generic OAuth is currently MCP-only. Remote MCP uses Streamable HTTP over public HTTPS; local stdio MCP is not implemented. The ordinary private workspace can install trusted CLIs through npm or pipx. Connected CLI setup uses an installed service command and does not install it automatically. [Access paths](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/server/discovered-connections.ts#L16-L38), [transport](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/providers/discovered/remote.ts#L112-L154), [CLI execution](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/server/composition.ts#L661-L675).

Search Composio first, then curated official MCP Registry entries, then known CLI packages. Registry namespace verification is not a safety review; retain source/version and setup requirements. Its read-only API can feed the same cached capability catalog. [Registry overview](https://modelcontextprotocol.io/registry/about), [aggregator API](https://modelcontextprotocol.io/registry/registry-aggregators).

Composio's agent plugin/CLI can improve developer workflows, including catalog, auth-config and log inspection. Composio discourages building production runtime dependencies on its CLI; released Otto should retain SDK/API execution. [Agent plugins](https://docs.composio.dev/docs/agent-plugins), [CLI guidance](https://docs.composio.dev/docs/cli).

## Desktop credentials and isolation

Desktop generates a persistent UUID in its local profile; normal development uses `local-development`. Those IDs are passed to Composio and local queries are owner-scoped. They are distinct from API credentials. Sharing a project across trusted server tenants is compatible with this model; distributing its privileged key to independent desktop owners is not an equivalent boundary. [Profile identity](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/desktop/main/main.mjs#L579-L592), [runtime owner](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/server/config.ts#L10-L15).

Keys are encrypted using Electron safeStorage, then decrypted into the engine environment. The Settings UI deliberately supports revealing the key. At-rest encryption therefore does not hide an Otto-owned project credential from the desktop owner. [Encryption](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/desktop/main/settings.mjs#L90-L107), [runtime delivery](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/desktop/main/main.mjs#L858-L897), [reveal interface](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/src/web/components/desktop-settings.tsx#L267-L282).

At the released baseline, normal desktop key entry supplied no auth-config overrides, while `OTTO_DESKTOP_IMPORT_ENV` could import seven IDs into encrypted settings. Ordinary shell variables were not inherited. The current candidate closes the Google selection gap by deriving the eligible custom config from the entered key's project during authorization; users need no extra setup fields. Explicit imported or environment overrides still win. [Historical import behavior](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/desktop/main/main.mjs#L987-L1000), [stored configuration](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/desktop/main/settings.mjs#L203-L245).

For a later multi-user distribution, retain the project key in an authenticated broker that derives owner identity and mediates discovery/connect/execution. Customer-owned project keys remain a local option. A Composio `userApiKey` is an organization-member credential, not an attenuated Otto end-user token. Consumer-project headers select a project without establishing a white-label customer-token contract. [Authentication reference](https://docs.composio.dev/reference/authenticating-to-composio), [consumer agents](https://docs.composio.dev/docs/consumer-agents).

Composio Connect supports personal MCP-client login and consumer keys, but its For You accounts are separate from developer-project accounts. Prototype this as an alternative personal connection model, not as a transparent swap for Otto's project key. [Connect](https://docs.composio.dev/docs/composio-connect), [consumer boundaries](https://docs.composio.dev/kb/guide/consumer-project-boundaries-and-auth-selection).

## Current local scope

The candidate contains the Apps and integration changes on main `7a1b839`. At the user's explicit request, `src/web/pages/onboarding.tsx` and `src/web/components/models.css` are byte-identical to that base. SetupNotice only adds catalog refresh after a key is saved. Optional-app onboarding, additional navigation guards and callback changes from the earlier experiment are reverted and are not release features or current acceptance evidence.

- Apps and `manage_apps discover` share a cached, paginated managed/DCR catalog, including toolkit slugs with underscores. Discovery metadata is treated as untrusted input. Existing selected-account ownership and provider routing remain intact.
- Catalog entries are validated independently: malformed items are skipped and optional display metadata is normalized. Pagination and transport failures remain errors. A typed, fixed-message permission error retains Toolkit read guidance for Composio 403 responses; unrelated failures receive neutral retry guidance. Existing connections remain available when catalog access fails.
- Google authorization without an explicit override reads project auth configs for the exact toolkit and binds the unique eligible custom OAuth2 config before opening consent. The five eligible apps are Gmail, Calendar, Drive, Sheets and Docs. Existing sessions, account execution and other managed/DCR flows do not perform this lookup.
- App families, categories, logos, descriptions, total tab counts and empty-state recovery use the behavior described above. Initial app-list failures expose Retry. Add-account failures stay associated with the originating app, including when a different Manage dialog opens before the request fails.
- Account identity and setup-link logos use bounded, owner-scoped metadata. Featured IDs and bundled-logo membership derive from the shared display manifest; Composio legacy fallbacks derive from provider version pins. Event subscriptions and special identity/file handling retain explicit provider limits.
- Apps and chat can reconnect an existing Composio account by its exact `connectionId`, using the original provider and auth config. The saved account, connection ID and watch preference remain intact until replacement consent confirms the same verified email, remote owner and auth config. Failed, cancelled, expired or replaced callbacks cannot swap the saved account. Success resets obsolete sessions and watch cursors, then retires the old provider account. `canReconnect` identifies provider support for renewing a saved account; reconnect verifies cached identity or recovers it from owned provider metadata before starting consent. `reconnectRequired` also exposes expired Gmail history when app access remains active. If trustworthy identity cannot be recovered, the user must add an account separately. Live reconnection remains unverified.

The isolated review at `http://localhost:4318` uses separate PostgreSQL, workspace/browser containers and local data, with only the existing alpha Full access key for Composio. The five Google auth-config overrides were removed after a private backup. The remote alpha project is shared with the current release. The original checkout, normal development project and connected accounts remain unchanged. The ignored `.local/composio-review/start.mjs` launcher is specific to this configured worktree and does not reset databases or rotate keys.

Users can supply their own Composio project key. Otto retains seven legacy auth-config overrides and has no general auth-config editor. Automatic Google selection requires **Auth configs → Read**, which the existing alpha Full access key covers. The provider reads bounded pages without caching, accepts only the exact toolkit's enabled custom `OAUTH2` config with `is_enabled_for_tool_router:true`, and updates the fresh consent session while preserving its other auth-config bindings. Multiple eligible configs fail safely; enabled custom OAuth2 configs with no router-eligible option also fail. If no enabled custom OAuth2 config exists, the project default remains in effect. This uses metadata, not key or auth-config fingerprints. [Auth-config listing](https://docs.composio.dev/reference/api-reference/auth-configs/getAuthConfigs), [session binding](https://docs.composio.dev/docs/configuring-sessions#custom-auth-configs), [permissions](https://docs.composio.dev/reference/authenticating-to-composio/project-api-key-permissions).

Native managed/DCR catalog discovery does not automatically include API-key-only or custom imported toolkits; remote MCP, HTTP and installed CLI connections retain their chat-assisted setup path.

Otto pins `@composio/core` 0.21.0 and dated toolkit versions, but Composio documents Sessions resolving latest tool versions. Direct execution has separate pinning semantics; do not assume direct pins constrain session execution. [SDK dependency at the released baseline](https://github.com/n8n-io/otto/blob/ed66ff0b64d48f890ebedb840b63c0ea26c984c5/package.json#L30), [version semantics](https://docs.composio.dev/docs/tools-direct/toolkit-versioning).
