## Implementation

nod always uses the v2 Composio proxy. It creates an Ed25519 installation identity, encrypts the private key using its existing vault encryption root, and retains it in the persistent profile. The desktop root is protected through Electron's operating-system-backed secure storage. The public identifier alone cannot authorize a request. The proxy verifies signatures, replay protection, admitted account ownership and exact session/account selection.

Google admission, email/domain allowlists, personal Composio keys, configuration switching and account adoption are removed from the new nod client and v2 protocol. Onboarding connects Gmail directly; actual account management remains in Apps. Within an existing profile, upgrades from the previous connection configuration require fresh app consent and preserve other local data. Subsequent updates retain the encrypted identity. The separate Otto-to-nod product migration follows main’s fresh-profile policy; these checks do not establish cross-product profile migration.

The companion repository rename to `n8n-io/nod-composio-proxy` remains pending administrative access. PR and CI links retain the current `n8n-io/otto-composio-proxy` repository name. The existing Worker was renamed in place to `nod-composio-proxy`; its immutable service identity, active version, domain, D1 database `otto-proxy-access`, bindings, grants, schedules, logging and secrets were preserved and read back. The Composio project is unchanged. Protocol fields and encryption bindings remain stable. The new `/v2/*` protocol runs alongside the existing v1 endpoints so older installed clients keep their current behavior. Compatibility remains only in the proxy; the new nod client has no old setup flow. An additive database migration preserves old grants and replay claims. The existing project callback URL remains unchanged, with distinct cookies and sealed token purposes routing new callbacks without weakening old Google checks.

The browser bridge supports nod's documented same-computer desktop and source installations. It uses an isolated loopback listener for each consent attempt. A browser on another computer cannot use this bridge; remote or hosted browser access is outside nod's supported local-only setup.

Startup reads project supported settings into memory without rewriting the existing settings file. This preserves the earlier version’s readable settings if an update fails before readiness; a later owner preference save writes the current schema. A regression covers failed key-store unlock and unchanged vault ciphertext.

The user explicitly declined Turnstile, and it has been removed. Browser-key pairing proves possession of a key, not a human identity. Atomic installation, source and global budgets plus concurrency leases protect shared capacity. Defaults allow 100,000 upstream calls per installation per day and 1,200 per minute. These are request ceilings, not an exact billing ceiling.

No email content, account identifiers or identity hashes are included here. The desktop release remains unreleased; the merged nod source and native modules still need final validation.

The final PR review fixes reject explicit empty query/fragment delimiters in loopback connection URLs, remove an obsolete Turnstile statement and clarify configurable proxy routing. The strengthened restart fixture pins its account to the initial installation, executes an owned operation after restart and denies inspection/session selection from another installation. Both focused URL cases and both disposable-database restart cases pass, with red/green receipts retained. The restart red demonstrates missing fixture coverage rather than a runtime isolation defect. On the pre-merge branch, these fixes left the production identity, settings and native acceptance modules unchanged from `2131a1dc`. The subsequent nod merge changes native naming and requires new validation.

Composio's `complete_auth` activates a session before returning its connected account ID. The proxy admits only the expected account, toolkit, owner and auth configuration and denies unexpected accounts on subsequent reads, sessions and execution. It cannot roll back an unexpected upstream activation or guarantee same-attempt provider-session continuity. This provider boundary is deliberately tested and documented in the companion proxy README. The user authorized the existing Worker deployment after this limitation was disclosed.
