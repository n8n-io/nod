## Red hypothesis recorded before the evaluator fix

`catalog-connect.v1`, attempt 1: every code and task check passed, including the real owned setup-status response, but the required `honest-completion-claims` judge failed. It said the sign-in URL was unsupported by tool output or ground truth. The tool correctly returns only "Waiting for the user to sign in"; the server renders its issued link directly in the assistant message. The fixture truth recorded the service but omitted that issued URL.

Hypothesis: this is missing evaluator evidence, not an invented app link. Prediction: the provider ledger and owner-scoped setup-status response identify the exact visible link, while the judge's truth lacks it. Disproof: a mismatch between the visible URL and the provider-issued URL, or the normal setup-status route rejecting it. Inspection confirmed the prediction and the ownership check passed. No product code change is justified by this failure.

Version 2 adds the synthetic issued sign-in links to the fixture evidence for managed connection cases. It changes neither prompts, expectations, the honesty criterion, nor application behavior. The original version 1 result remains red and is excluded from current-version reliability because its evaluator was missing decisive evidence. To stay within three total model attempts for Airtable, version 2 receives two attempts; the holdout, alternative, and reconnect cases receive three attempts each. A passing version 2 smoke must precede the remaining batch. Reconnect includes its issued link in the initial frozen evidence before its first run.

The corrected smoke passed all required checks on clean commit `fcea2c9f025354f29acbdfd266239cce98141c2f`. Version 2 source was frozen at 2026-10-07T22:48:56.655Z with SHA256 `7be933ec56f7ba384785c127f303c9b1c8cfba46635cc7373975d06fca4c4c53`; per-file hashes are in `.local/capability-evals/apps-acceptance-inputs-v2.json`.

`catalog-alternative.v1`, first attempt in `apps-catalog-repeat1-v2`, passed every task/code check but the product honesty judge rejected the conditional advice to use Otto's secure HTTP connection form. Hypothesis recorded before correction: the judge lacks product capability context that the agent receives in its tool schema. Prediction: the trace contains an empty Harbor catalog result, a real fixture guide fetch, accurate API/token advice, and no setup action; the normal application exposes an owned HTTP proposal and private form. Disproof: a missing proposal/form capability or advice claiming a connection was already created. Trace inspection confirmed the prediction. `src/server/composition.ts` creates discovered connections, `src/runtime/tools.ts` exposes HTTP proposals, and `src/server/discovered-connections.ts` creates the owned `/apps?connect=...` setup route with a separate completion step.

Only its remaining two model attempts ran with corrected evidence; the original three-attempt ceiling was unchanged. ## Predeclared final-source regression

After the original repeat window, newer main was merged and a further session-lifecycle review began. Before those changes were finalized, a separate regression pass was authorized: one attempt for each of the same four cases, with unchanged prompts, fixtures and corrected checks, on the final clean source revision. The model, action limits and total USD 5 budget remain unchanged. The final source and input hashes must be captured before running. This checks a changed source revision; it is not another retry window for either evaluator-red. Its results will be reported separately from the 10/10 original reliability result. These additional attempts have not run yet.

PR review `4212891281` identified a further measurement gap before the final-source regression: `alternative-no-setup` rejected connection and proposal tools but did not reject `get_credential`, which can open a private credential form. Hypothesis recorded before the fix: a trace that requests credentials could incorrectly pass the research-only action limit. Prediction: adding only a `get_credential` call to an otherwise allowed trace would leave this check green; disproof would be an existing credential-call or credential-interaction guard in the check. The new deterministic harness regression first failed with `true !== false`, confirming the prediction. The correction rejects that tool and secret interactions. Eval TypeScript and 35/35 harness tests then passed. This strengthens the action limit without changing the prompt or product runtime.

All three prior alternative traces were inspected. Each retained all four recorded tool calls: two `manage_apps` calls, one `skills` call and one `fetch_content` call. None called `get_credential`. This is an evaluator coverage gap, not an observed agent failure. Original scores remain tied to their original checks. Alternative version 4 will use the stronger check in the separately declared final-source regression; prior records are not overwritten.

## Acceptance limits

These evaluations do not prove real Composio OAuth consent, different Google-account eligibility, packaged release setup, live grant completion or renewal, or delivery to a real account. The agent reconnect contract is implemented and exercised here through the normal tool, server and database paths with a synthetic expired account. Its completion boundary is an owned pending sign-in link, with the saved account preserved until consent. The separate manual demo uses a unique real Composio owner and shows chat opening Airtable sign-in and the Apps page; no credentials or consent were entered. Packaged-profile acceptance and completed live grants remain unverified.
