# Trust and access

Default `local` mode binds to loopback and serves one development owner without login. Normal application requests reject foreign Host and Origin headers. Keep this mode private. Public hosting uses the separate `gateway` entrypoint and private `tenant` processes described below; a reverse proxy alone does not convert local mode into a hosted deployment. The signed Composio webhook endpoint has a separate policy when configured.

Never put provider keys in prompts, React configuration, task files, artifacts or logs. The model may use bounded tools; it does not receive a tool that reads arbitrary host files or reveals a vault value. Tool arguments and raw exceptions are not logged by the main server. This does not make conversation content non-sensitive: local messages, memories and task transcripts still need private backups and retention limits.

`web_search` sends the model's query to the selected Pi Web Access search provider. Treat the query and returned source text as public, untrusted data. The tool returns at most eight source links, short text, and a fixed error. It does not pass account grants to search or expose the Pi extension's file, command, or browser-cookie functions.

For discovered MCP and HTTP API connections, a user reviews each public HTTPS address before a token or OAuth grant is used. A CLI connection shows the selected installed program and verifies a read with the private token before it saves the account. OAuth starts on a service sign-in page, uses PKCE and a hashed one-use state, and saves the grant only after callback and tool checks. Vault stores each owner-bound encrypted discovered or direct grant and pending OAuth state. Startup moves older direct grant ciphertext into Vault, then clears the old field. The connection row holds path metadata and no new grant ciphertext. The trusted server refreshes expiring OAuth tokens and injects access tokens into outbound requests. It resolves and pins a public address for each request, rejects redirects, and limits transfer size. For HTTP and MCP, a model cannot supply an unreviewed destination when it uses the saved grant. A CLI can choose remote targets through its arguments, so the selected program must be trusted. HTTP paths reject encoded traversal and separators outside the saved API prefix. The token form shows each address or CLI program. It can show the exact read check in Connection details. Connected write confirmations show a bounded, redacted request summary. Generic MCP read status uses both the remote server's read-only hint and a read-style tool name; that hint is a claim by the remote server. The user must trust the chosen service address. Other MCP tools, HTTP writes, and CLI writes use the task-bound action review. The model can mark a checked CLI call as a read. The server accepts listed read verbs and rejects common write verbs and flags from this path. This is a conservative check, not proof that any installed program has no side effects. The user must trust the selected CLI. Saved website logins appear in Apps as browser paths; the trusted browser broker keeps exact-origin checks. A saved connection does not give the model a credential value or browser profile. Local Docker and hosted E2B run connected CLI calls under a separate unprivileged user from the ordinary shell. The Vault token enters only that call, through a bounded private command request. The call runs from a private directory with a temporary home. The supervisor removes that home after an acknowledged call. A CLI can still copy or send its token while it runs. The selected Cloudflare computer adapter does not offer this path. A provider can reject an operation after the initial access check. Vault does not yet show app grants in its page.

Provider selection and secret configuration belong in `src/server/composition.ts`. Interfaces in `src/ports` keep vendor SDKs and response parsing inside `src/providers`. Owner checks, approval decisions, quiet hours, event deduplication, and task revision checks remain in the application. Replacing an adapter does not grant it permission to bypass those checks. Most feature separation remains a code boundary in the trusted server. Browser execution has a separate container boundary from both the host runtime and the untrusted shell.

In local Docker mode, the trusted `otto-browser` container has no published port, provider keys, host Docker socket or host browser-profile mount. Its private `browser-data` volume holds profiles, captures and the control socket. The host uses a fixed Docker-exec command and bounded stdin protocol to that Unix socket; the untrusted workspace shares neither its mounts nor its network namespace. Chromium runs as an unprivileged user with container capabilities dropped, a read-only root filesystem and resource limits. Its internal sandbox is disabled, so the container is the operating-system boundary; this does not isolate a compromised browser from its trusted worker or other task profiles in that container. Existing host profiles are not migrated.

Local browser and shell traffic use the default Compose bridge with no Otto firewall, private-address deny list or IPv6 restriction. Docker and host routing determine reachability. The browser control socket and display stay private to its container, but network services on the bridge are reachable, including PostgreSQL with the local development configuration. The launcher generates a 32-byte random local database password, stores it in `.env` at mode 0600 and passes it only to trusted server/PostgreSQL configuration. Browser and shell containers receive no database credentials. Existing local roles are rotated through psql on the container’s Unix socket using a SCRAM verifier on stdin, with statement logging disabled and command output discarded. No data rows are recreated. Database authentication remains necessary because there is no network deny policy. Exact-origin credential checks and the separate public link-preview fetcher retain their own validation; neither limits arbitrary shell traffic.

Prompt instructions are not a secrecy boundary. The model receives operating instructions and can make mistakes about disclosing them or following hostile content. Keep secrets out of its context, constrain tools on the server, and derive write authority from the current owned user instruction. A fixed action policy checks intent and scope for known ordinary external operations. Five validated reversible local plan actions (goal create/update and schedule create/update/cancel) can execute in the exact owned current-user segment without phrase matching; the agent must still respect review-only or no-change requests. Unknown, destructive and unmatched operations require a specific yes/no question in the same chat, bound to the saved action, account, arguments and task revision. Background runs, onboarding, external content and reactions cannot grant that authority. Confirmed actions run once in a worker; uncertain outcomes are never replayed automatically. Explicit personal facts can be saved quietly when the server verifies their exact user-message source. This prototype does not claim complete prompt-injection resistance. An approved browser destination can receive typed values and observe actions; never treat all page content as trusted.

## Hosted account boundary

The gateway uses Better Auth Google login with database-backed sessions, verified email, a fixed callback and secure HTTP-only cookies on HTTPS. Google login authorizes the Otto account; app connections have their own consent flow. The gateway checks the canonical Host/Origin, requires the configured Origin on state-changing requests and resolves ownership from the authenticated session. User-supplied owner/account headers cannot select a tenant. Each request resolves the session once before dispatch. An event stream rechecks the session before its first byte and then revalidates it periodically. Avatar URLs are fetched through a bounded authenticated raster-image proxy.

Each user has one fixed-owner runtime process, SQL login and private app/jobs schemas. The gateway's provisioning role and auth/control tables never enter that runtime environment. Tenant roles cannot read another tenant's schema or assume its SQL role. The isolation model uses schema privileges, not a shared-table RLS policy. Provisioning revokes default public access and therefore requires a dedicated deployment database. Eight accounts are admitted by default; the configured ceiling and container capacity must agree. Database fixtures cover cross-schema and `SET ROLE` denial, but do not certify a particular provider's live grants.

Gateway-to-runtime HMAC envelopes bind owner, environment, lease generation, method, exact target, body hash, expiry, nonce, request kind and developer capability. Tenant uploads and audio transcription parse only fully authenticated body bytes, validate the complete multipart form and enforce file/field limits before storage or provider calls. The actor rejects unsigned, replayed, expired or altered requests. Runtime ownership is leased in PostgreSQL; renewals reach the actor through a signed endpoint, and an expired actor fences itself and exits. Replacement requires a confirmed stop. Unknown process state requires recovery rather than a second active generation. The local process transport assumes a trusted host; a process under the same operating-system account is not a hostile-code boundary.

On Cloudflare, public traffic reaches only the Worker and gateway. The gateway alone can use the runtime lifecycle broker. Tenant storage/control brokers derive the owner from trusted container identity, and the control endpoint also checks the HMAC and current database lease. Neither broker accepts an arbitrary owner prefix from a public request. Telegram/WhatsApp callbacks use opaque owner-bound routes and still require provider verification; Composio verifies the original webhook signature and owned account/subscription. Verified channel account IDs are claimed globally so one bot cannot be connected to two Otto owners.

Private channel-control ingress is limited to 4 KiB; provider webhook ingress is limited to 256 KiB. Both the HTTP parser and streamed-body reader enforce their limits. Channel-control signatures are authenticated before a database lease lookup, then checked against the current generation and replay cache before the claim changes. Each actor journals claim intent before contacting the registry. Claims no longer used by saved settings are released after a change or during startup recovery; an unavailable registry leaves a durable retry record. Per-account revisions and retained release tombstones fence delayed requests, so an old claim cannot restore released ownership and an old release cannot remove a newer claim. The registry serializes these transitions with the active runtime lease.

The gateway holds a stable `OTTO_MASTER_KEY` and separate authentication/provider credentials. HKDF derives environment/user-specific database passwords, runtime signing secrets and Vault keys; actors receive only their own derived values and the allowlisted provider configuration. Actors never receive the master key, Google client secret or provisioning connection string. The trusted runtime still holds the operator's shared model/integration/computer keys. Browser and workspace sandboxes receive neither those keys nor tenant database credentials. Keep development and production keys, databases and provider projects separate, and keep all environment files out of Git and logs.

The selected hosted path uses Cloudflare Containers with one private application runtime and separate browser/workspace containers per owner. The computer roles start on first use and receive no service keys. Private profiles, sockets and browser checkpoints stay outside the shell container; the private broker binds every request to its owner, environment, role and runtime generation. E2B is an optional, deferred adapter: its combined VM uses separate browser, shell and connected CLI Linux users with checked permissions, root-owned helpers and a local-network guard. That guard must pass on create/resume; unavailable enforcement fails closed. Its synthetic/fixture coverage is not live E2B proof or separate-VM isolation. Server startup selects providers and models. Ordinary accounts cannot access computer, browser-control or Inspector APIs; the gateway grants that capability only to account UUIDs in `OTTO_DEVELOPER_IDS`, and the actor checks the signed capability. This gate limits the human UI/API; the account's assistant can still use its configured computer tools.

This pilot admits eight total provisioned users and keeps application runtimes available for background work. Browser/workspace containers can checkpoint and stop while idle. The minute wakeup, fixtures and deployment smoke do not prove live Google consent, webhook delivery, provider isolation, disaster recovery or production availability. Follow [production acceptance](production.md) and the [Cloudflare runbook](../deployment/cloudflare/README.md) before inviting users.

## Private diagnostic observations

Inspector is an optional local diagnostic view, and hosted access requires the developer capability. Hosted capture is disabled unless the operator sets `DEV_INSPECTOR=true` and the owner is in `OTTO_DEVELOPER_IDS`. Ordinary accounts do not record Inspector prompt/tool payloads. With the inspector enabled, the server stores bounded tool inputs/results and model token/cost metadata in the owner's PostgreSQL schema. These records remain sensitive user content. Known configured provider keys, recognized secret fields, authentication headers and secure-form links are masked before storage; binary payloads are omitted. Each payload is limited to 16 KiB. Bounded JSON inspection also masks nested serialized secret fields in prompt and failure prose; incomplete or oversized structured sections are omitted. Pattern masking cannot identify every secret embedded in arbitrary prose or encoded content. Trusted credential injection stays outside model tool output; the inspector cannot read the vault.

Records expire after seven days and are pruned on startup and periodically during access. `DEV_INSPECTOR=false` stops Inspector payload capture and blocks inspector endpoints; it does not immediately erase existing records. One metadata exception retains strictly validated `relevance/conversation_route` failures or cancellations without task/tool references: a fixed failure code, optional HTTP status and existing bounded model, timing and usage fields. It captures no prompts, outputs, raw errors, causes or keys. This private owner-scoped recording shares the nonblocking queue limit of 128 pending writes and seven-day retention; it does not enable Inspector access. Private prompt snapshots are also pruned at startup and hourly while capture is disabled. Older snapshots are masked again when read. Task ownership and revision checks prevent foreign or stale tool results from being returned as current work. A changed segment is marked interrupted without replaying its action. The inspector has no tool execution endpoint. Payloads are rendered as escaped text and are never forwarded to a telemetry service or console. Historical tasks are not backfilled from raw transcripts.

## Vault

AES-GCM protects stored credentials. The encryption key lives outside PostgreSQL: Keychain or an explicitly provided environment key in local mode, and an environment/user-derived Vault key in hosted mode. The gateway master key is stored separately from the database and must survive redeployment. Replacing it without migration invalidates existing database passwords and encrypted values. KMS envelope encryption, automated key rotation and externally controlled key release are not implemented. The infrastructure operator controls the trusted service and can decrypt its data; neither environment keys nor ordinary cloud KMS conceal credentials from that operator.

The key-store interface returns key bytes only to the trusted Vault, channel-settings and private verification-receipt services. Model tools and agent browser APIs receive no key or plaintext credential response. The owner's private Vault list and details include full usernames; passwords are fetched only after Show or Copy. These separate POST routes validate the entry ID, enforce the runtime owner, retain authenticated encryption checks and return no-store responses with fixed errors. Hosted access also passes through the authenticated gateway. They are not agent tools. Passwords, card numbers and security codes stay out of list metadata, general page caches, chat, Inspector and logs; copying explicitly places a value in the system clipboard. This does not add OS reauthentication or protection from a compromised trusted process.

Secure forms are bound to a task revision; a stale or cancelled step cannot inject credentials. Retrying an expired form invalidates its earlier forms and requeues browser inspection without reusing a secret. Existing encrypted entries survive the module and revision migrations; changing the key itself requires a separate migration that is not implemented.

The broker inspects visible login fields before creating a form and again before submission. It supports separate identifier, password and one-time-code steps. A staged username and selected account remain bound to task, owner, exact origin, revision and expiry; durable continuation encrypts the identifier so the next password step retains the same account across restart. Saved password records contain encrypted username/password pairs. One-time codes and submitted values remain absent from credential-request records. Each form can be consumed once. Saved entries have a separate, single automatic attempt for the identifier and password steps; retries require fresh input.

Observed OAuth buttons and email, SMS, authenticator or backup-code choices are selected in chat before credential entry. The broker rechecks the exact origin, current method and task revision before clicking. This starts the website's flow; it does not prove authentication completed or create a managed Google connection. A new origin requires a new trusted credential request. The automated broker does not support device passkeys or hardware security keys. A separate user-controlled browser sign-in path is available; provider and device support still applies. The app supports manual control of the task browser and a private workspace desktop view for native sign-in; general desktop automation is not implemented. One unambiguous group of four to eight single-digit verification inputs is supported. The broker validates the complete group again, clears previous digits before retry and enters one digit per field; other ambiguous layouts require manual control.

A pending one-time-code request accepts a reply containing only four to eight digits in its originating chat. The server resolves the owned request before ordinary message persistence or model routing, stores a masked receipt and passes the code directly to the trusted broker. It checks the channel, current conversation, task revision, expiry and request identity. An ambiguous request requires an explicit reply target. Attachments cannot bypass private handling when an OTP request applies. Public message requests containing `forceNew` are rejected before verification, persistence or routing; the option remains internal to trusted onboarding. In-flight receipts say received and remain `pending` until the broker finishes; they do not claim successful submission or authentication.

A keyed HMAC fingerprint binds each verification receipt to the code, owner, channel and client message ID. Its key is derived for this purpose from the existing Vault key and is not stored in PostgreSQL. Exact retries do not inject again; changed codes and legacy receipts without a fingerprint fail closed. Key-store failure returns a fixed error instead of routing a possible code to the model. Raw codes are not stored. Ordinary numbers without a matching pending request remain ordinary messages. For Telegram and WhatsApp, classification and ordinary inbox persistence share a transaction and task-row locks with Vault request insertion, closing the gap in which a new OTP request could appear before the receipt. Browser inspection and code injection run outside that transaction. Passwords still require the private form. External chat providers receive the original message and have their own retention policies; local interception does not erase their copy.

For a freshly observed email-code step, the trusted broker can use the exact matching connected Gmail account before asking in chat. The visible full recipient must match the encrypted selected login and one active connected account. The lookup is bounded to recent mail, five candidates and an eight-second budget. It requires an exact recipient, a Gmail-authenticated sender in the website's registrable domain and one unambiguous code near verification text. It never follows email instructions or fetches attachments. The broker checks the task revision, selected login, exact origin and account status again before injection. Missing, late, ambiguous or unverifiable messages fall back to chat. Lookup content and codes remain outside model tools, Inspector, logs and local message/request storage. Composio and Gmail still handle their API traffic. Cross-domain mail senders and masked website recipients do not qualify for automatic entry.

Keeping secrets from the infrastructure operator requires a different architecture, such as a local user-controlled broker or attested confidential execution with externally controlled key release. This repository does not implement that claim. The website receiving a login and the trusted broker necessarily handle the credential. Composio holds the OAuth credentials for connections it manages.

The agent cannot have unrestricted shell access to the authenticated browser, its profile, CDP or the vault. Browser inspection is locked during secure entry. Trusted scripts mask protected inputs and known credential text, and text observations redact known values and common OAuth query parameters. These controls cover the tested DOM forms, not every hostile page, canvas, image or script behavior. The destination website receives entered values and can retain or transform them; exact-origin checks do not make a phishing site trustworthy.

Pending secure steps hold their browser session through the form expiry. Idle cleanup closes the browser but retains its last masked screenshot. These screenshots remain sensitive user content in the private `browser-data` runtime directory with mode 0600. Capture metadata retains its time and whether it is current or cached; the UI does not show a Last view badge. A restarted browser worker may reattach to an existing nonsecret daemon through its socket; reading the inspector never opens a URL or replays a credential. A recovered session that handled credentials serves only its cached image because its in-memory redaction values no longer exist. It needs an explicit reopen before further inspection or entry. Sessions without persisted screen metadata may have no recoverable image. Browser profiles retain website session data and need the same private storage and retention controls as other local content.

The private Vault can store payment cards in a separate encrypted table. Cardholder, number, expiry and optional security code use an owner/record/type-bound AES-GCM payload; lists expose only name, brand, last four digits and expiry. Full numbers and security codes require separate explicit no-store owner-bound reveal requests and never enter agent context or general page caches. Details expose only code presence. Card autofill and purchase capabilities are not implemented. This is local encrypted storage, not a claim of payment-processing compliance or protection against a compromised trusted host.

A confirmed discovered-app write keeps the original owned user message for the same task revision only. A later write still uses account preflight and a new confirmation. The confirmation reply and the provider result do not grant new action scope.

## Files

Uploads have a 15 MB limit. Artifacts are copied from a verified task workspace path into a private store; no-follow workspace reads and owned metadata checks apply before download. HTML and other active files download as attachments with sandbox response headers. Do not expose the whole workspace as static files. Keep `.env`, `.env.hosted.local`, `.local`, browser profiles and database volumes out of Git.

Local hosted actors store object bytes and versions atomically in their restricted PostgreSQL schema. Cloudflare actors use a private R2 broker with environment/owner prefixes derived from container identity. Neither storage exposes public object URLs. Artifacts are initially written only if absent; Pi checkpoint updates require the previous version. A durable pre-action journal blocks replay when an external action's outcome is unknown. Local actor directories are caches, and Cloudflare container disks are ephemeral. Conditional cleanup must not remove a newer value; the R2 broker rejects unsupported conditional deletion, leaving a private orphan for later reconciliation.

The optional filesystem adapter needs a private durable volume and operator recovery after a process dies holding its lock file. It is not the default hosted store. Database/object backups must preserve owner identity, ciphertext, key versions and checkpoint uncertainty together. Retention and account deletion across provider sandboxes, PostgreSQL and object storage require an [operator procedure](environment-reset.md); a successful deployment does not implement that lifecycle automatically. Full resets revoke inventoried integration callbacks and recorded sessions, clear the tenant registry, stop old runtimes and remove owned remote connections before reopening admission. Provider-side session inventory gaps and backup/log retention are separate boundaries.

## Manual browser control

Core browser control pauses the owned task, advances its revision, and drains in-flight runtime tools before granting access. It remains available with Inspector disabled in local mode; hosted access requires the developer capability independently of Inspector capture. The owner focuses the browser image to send clicks, typing, paste, supported key combinations and wheel input through the trusted browser adapter. Shift-Escape returns focus to the controls; ordinary Escape goes to the browser. Inputs are serialized in a bounded queue. Completion drains accepted input; leaving the window or changing the session drops unsent input, and an uncertain input failure stops the queue. Text travels over the private stdin/socket bridge to the browser daemon, outside CLI arguments, chat messages, model tools and inspector payload recordings. Typed values and protected fields are masked in later observations. The owner must explicitly resume the agent, which inspects the current page before continuing. A lease expires after 30 minutes; expiration or a restart does not silently resume work. Status checks release stale browser leases after cancellation, reset, lost ownership or a revision change. Release and reacquisition share one per-task queue, so old cleanup cannot release newer control. This is browser control, not general desktop access. The server operator and browser process still handle plaintext during entry.

Native sign-in stops the automation daemon before opening the task profile with the same `/usr/bin/chromium` inside the browser container. It launches a private Xvfb display with an authentication file and no TCP listener; no host Chrome process or normal user profile is involved. Its destination policy matches automated browsing: HTTP(S) without URL userinfo, with no private-address or port deny list. The native process has no debugging endpoint or automation flags. The model cannot launch this path, choose its URL, inspect its screen, inject credentials or export its cookies. The container browser opens the original task destination without query or fragment; the user completes the website sign-in flow through the private `/browser` desktop view. Only an exact active owned sign-in lease may request these no-store frames and bounded desktop input. Frame reads recheck ownership, revision and expiry after capture. Pixels never enter ordinary browser screenshots, Inspector records, artifacts or logs. The client revokes frame URLs and clears private text when its window loses focus, the tab hides or the session changes. Explicit continuation requests normal browser shutdown and waits for process exit before restoring automation and fresh inspection. A timeout keeps the task paused; forced cleanup cannot trigger continuation. This is a supported human handoff, not a promise that every website permits subsequent automated access.

The isolated task browser uses agent-browser’s basic password store and mock-keychain configuration in both modes so website session cookies remain readable across the handoff. Session restoration also retains session-only cookies. Browser profiles rely on private filesystem and device protection; they do not have the Vault’s AES-GCM/Keychain storage guarantees. Browser sync is disabled. These flags never apply to the user’s ordinary browser profile, and the handoff does not export cookies or promise to retain in-memory page state.

Saved website connections use a random profile ID under the owner browser root. Only the trusted server binds a task to that profile. One connection can have one active task claim. A saved profile accepts direct browser opens only on its stored origin; a redirect to another origin blocks model observation and file capture. The private sign-in page can accept fields on another HTTPS subdomain of the same registered site. It checks the current inspected origin again before entry. An external provider sign-in stays in the private browser control view. Form values and native sign-in frames do not enter the task model. The optional saved password uses Vault encryption; browser cookies do not. Disconnect removes the profile and its saved browser screens. A website can still reject the browser or change its login flow. An authenticated browser click can change data at the site; this connection does not add a separate write approval gate to generic browser actions.

The optional E2B computer preparation accepts no owner, provider, template or resource ID from the browser. Cloudflare has no preparation hook; its owner-bound browser/workspace containers start on first use. The gateway derives the owner from the session and rechecks it after preparation before saving onboarding completion. The combined E2B allocation uses durable versioned owner leases; legacy split rows, expired retained leases and uncertain provider state are not automatically adopted or replaced. Non-forced deployment pause follows natural work drain. A hosted shutdown acknowledgement is generation-bound and sent only after both capabilities finish disposal and provider pause is confirmed.
