# Connected apps through Composio

Checked against the official documentation and installed `@composio/core` 0.21.0 on 2026-09-25. The implementation uses Composio Platform sessions. It does not use the legacy `composio-core` package or build its own Google token refresh service. The TypeScript SDK requires ESM and Node.js 22.22.3 or later. [Quickstart](https://docs.composio.dev/docs/quickstart), [TypeScript sessions](https://docs.composio.dev/reference/sdk-reference/typescript/sessions).

## Setup

Use `public/otto-logo.png` for the O mark in each project's White Labeling settings, with app title `Otto`. Use the same asset for the matching Google OAuth project's Branding page. These are separate provider settings; deploying the web app does not update them. Google may require branding verification before displaying the saved logo on public consent screens.

1. Use separate Composio projects for development and production. Put the selected project's key in the server environment as `COMPOSIO_API_KEY`; keep its `COMPOSIO_WEBHOOK_SECRET` and auth-configuration IDs with that same environment. Never copy production credentials into `.env`, `.env.hosted.local`, fixtures or a local tunnel. Existing provider accounts and connected accounts in another Composio project are not automatically Otto connections.
2. Open Apps at `/apps` and use Connect or Add account on the required service. Gmail, Calendar, Drive, Sheets, Docs, Slack, and Notion use separate provider consent flows, with multiple accounts per service on the Apps page. Hosted onboarding has a compact connection state per app and starts consent directly. Local single-owner mode uses `local-development`; hosted mode uses the immutable authenticated user's UUID in that user's private runtime and database schema. A request parameter, Google email address or connected-app account ID cannot replace that owner.
3. For Google services, Composio provides a managed OAuth app by default. A custom app can be selected with `COMPOSIO_GMAIL_AUTH_CONFIG_ID`, `COMPOSIO_CALENDAR_AUTH_CONFIG_ID`, `COMPOSIO_DRIVE_AUTH_CONFIG_ID`, `COMPOSIO_SHEETS_AUTH_CONFIG_ID`, or `COMPOSIO_DOCS_AUTH_CONFIG_ID`. Slack and Notion can use `COMPOSIO_SLACK_AUTH_CONFIG_ID` and `COMPOSIO_NOTION_AUTH_CONFIG_ID`. Each override must belong to the selected environment's Composio project. The provider APIs, granted permissions, consent configuration, and required verification remain the app owner's responsibility. An active connection does not prove that the user granted every requested scope.

The operator supplies these keys and enables integrations at startup. Users supply only their account authorization, not a Composio project key. Hosted Google login uses the separate `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` identity flow at `/api/auth/callback/google`; it does not create a Gmail or Calendar connection. Use the [hosted environment example](../deployment/hosted.env.example) and [development setup](development.md#hosted-mode-on-your-computer) for the real local hosted stack at `http://localhost:4330`. The repository requires Node.js 24.21.0 or newer, even though the SDK's own minimum is lower.

The five Google toolkits list managed OAuth support: [Gmail](https://docs.composio.dev/toolkits/gmail), [Calendar](https://docs.composio.dev/toolkits/googlecalendar), [Drive](https://docs.composio.dev/toolkits/googledrive), [Sheets](https://docs.composio.dev/toolkits/googlesheets), [Docs](https://docs.composio.dev/toolkits/googledocs). Composio also documents [Google Super](https://docs.composio.dev/kb/guide/toolkits-googlesuper) for one consent flow across services. Its tools and trigger compatibility need separate validation before replacing these connections.

Slack and Notion also offer managed OAuth. Otto uses the Slack user toolkit, so actions run with the connected user's permissions; this does not install an Otto chat bot. Slack distinguishes user and bot scopes, and workspace policy can restrict installation or access. Custom Slack auth must use `user_scopes` for user-token operations. Notion exposes only the pages and databases granted to its integration, further limited by its read/insert/update capabilities. A second auth configuration is not necessarily a separate Notion page-access grant. [Slack toolkit](https://docs.composio.dev/toolkits/slack), [Slack OAuth](https://docs.slack.dev/authentication/installing-with-oauth/), [Notion authorization](https://developers.notion.com/guides/get-started/authorization), [Notion capabilities](https://developers.notion.com/reference/capabilities), [Composio Notion access](https://docs.composio.dev/kb/guide/toolkits-notion).

## Runtime boundary

`src/providers/composio/integrations.ts` implements the provider-neutral interface in `src/ports/integrations.ts`. It owns the SDK, hosted consent URL validation, callback decoding, account status mapping, trigger configuration, and raw webhook verification. `src/server/integrations.ts` owns account intent, user checks, the action approval policy, durable event delivery, and HTTP routes. `src/server/composition.ts` selects the adapter and supplies its credentials. Feature tests can replace the adapter without mocking the Composio SDK.

The backend creates or restores one task-execution session per application user with an explicit seven-toolkit allowlist and multiple-account support. Account selection is explicit. Remote sandboxes, premium tools, and in-chat connection management are disabled. The model gets tool schemas, owned account references, and results through the application broker, without a Composio project key or hosted MCP credential. Identity checks use separate short-lived sessions restricted to one account and one read tool.

Connect and Add account create a temporary consent session without connected-account overrides, then call `session.authorize(slug, {callbackUrl})`. Composio rejects a new link when that toolkit already has a pinned account in the session (HTTP 400, code 4309). Keep the saved execution session pinned to its owned accounts; never clear those pins to obtain consent. The temporary session retains the toolkit allowlist, configured auth overrides and multiple-account support. Otto attempts to delete it after obtaining the link or on failure. Deleting a session does not delete its connected accounts. [Manual authentication](https://docs.composio.dev/docs/authentication/manually-authenticating), [session lifetime and account scope](https://docs.composio.dev/kb/guide/mcp-tool-router-sessions).

The new account ID is stored as an owned attempt with a hash of random callback state, a ten-minute expiry and an allowlisted return destination. The provider's authorization URL is returned to the caller and is not stored in that attempt. Otto verifies the returned account against the attempt and asks Composio to confirm the account belongs to the same owner and is active for that service. The application callback is `/api/apps/callback` on `OTTO_PUBLIC_URL`. Connect accepts only `returnTo: 'apps' | 'onboarding' | 'window'`; the callback uses the stored destination and returns there with a connected, cancelled, failed or expired outcome. It cannot redirect to an arbitrary URL. The destination reloads connection status, so onboarding resumes on the same screen. Query parameters alone never establish ownership, and a callback under a different signed-in account cannot claim the attempt.

For hosted development the application callback remains on `http://localhost:4330`, while production uses the configured HTTPS application origin. The local webhook tunnel described below is only for background events; it does not host Google login or app consent callbacks. Retain the same Otto session while completing consent. Changing the master key, database, environment or owner mapping is not an account migration.

The runtime calls `execute(ownerId, 'SEARCH_TOOLS', {query})` for current connected-app action schemas and available account references. The exact read list in `src/server/integration-policy.ts` executes directly. Tool-name prefixes do not establish read safety. With several accounts, the caller must select a local `connectionId`; a single account can be selected automatically before review. Other actions in the supported toolkits return an approval containing the exact action, arguments, and selected connection ID. Preflight and execution recheck the binding. Old approvals without an account ID cannot fall back to a replacement account.

Search accepts an optional UUID `connectionId` for compatibility, but discovery covers the current owner's accounts and forwards only the query to providers. Invalid search arguments return a fixed `invalid_search_arguments` result before any provider call, allowing the model to correct them after the result is durably recorded. Provider-error handling is unchanged, and existing uncertain actions are never cleared or replayed by this validation path.

The broker calls `executeApproved()` only for its reviewed reads or an accepted action review. Tool prefixes outside the seven allowed apps and Composio meta execution are rejected. Do not give the agent direct access to this method or the project key. The adapter treats a non-null error or `successful:false` envelope as failure even when the SDK promise resolves. Execution failures stay uncertain and do not produce a success continuation containing raw provider errors. Provider permissions and API availability still limit actions. [Session search and execution](https://docs.composio.dev/reference/sdk-reference/typescript/session).

## File retrieval

`GMAIL_GET_ATTACHMENT`, `GOOGLEDRIVE_DOWNLOAD_FILE`, and `GOOGLEDRIVE_DOWNLOAD_FILE_OPERATION` are retrieval operations. They do not ask for a write review. The runtime routes them from either `apps` or `download_app_file` through the owned artifact delivery path. The integration service also blocks ordinary execution from returning a signed provider URL and supplies a fixed download instruction instead. Fetch a full Gmail message first to obtain its actual `message_id`, `attachment_id`, and file name. Downloading a sent attachment does not forward or send another email. [Gmail attachment tool](https://docs.composio.dev/toolkits/gmail), [Drive download tools](https://docs.composio.dev/toolkits/googledrive).

`IntegrationSession.download` and the server's `integrations.download` return `{name,mimeType,bytes}` only to trusted application code. The adapter validates exact arguments and the selected account, executes the reviewed operation, and accepts only the provider's completed file descriptor. HTTPS downloads have a 15 MB limit, a 30-second deadline, public-IP validation with the connection pinned to that address, and at most three checked redirects. No arbitrary model URL, local path, provider cookie or credential header is used. Pending Drive operations and missing/oversized files return a fixed failure instead of a fabricated attachment. The feature has a 35-second overall wait bound and rechecks account ownership/revocation before returning. The task layer separately fences artifact storage and delivery by its current revision.

`SLACK_DOWNLOAD_SLACK_FILE` remains outside the direct-read list: its current description says it converts a file to a publicly accessible URL. Slack file listing and metadata are direct reads; public sharing, upload, messages and unknown operations retain review. Native Slack/Notion file delivery through this download tool is not implemented. [Slack download behavior](https://docs.composio.dev/toolkits/slack).

## Verified account labels

Account names and email addresses come from authenticated provider responses, not guesses or credential metadata. Gmail uses `GMAIL_GET_PROFILE`, Calendar uses `GOOGLECALENDAR_GET_CURRENT_USER`, and Drive uses `GOOGLEDRIVE_GET_ABOUT` with only `user(displayName,emailAddress)` requested. Calendar returns a calendar identity label, which is not necessarily a full Google Account name. [Gmail tools](https://docs.composio.dev/toolkits/gmail), [Calendar tools](https://docs.composio.dev/toolkits/googlecalendar), [Drive identity guidance](https://docs.composio.dev/kb/guide/toolkits-googledrive).

Slack uses `SLACK_WHO_AM_I` for its user/workspace label. Notion uses `NOTION_WHO_AM_I` for its workspace and owner email when present; an integration name is not proof of a human identity. These are account-bound reads, and failed identity lookups do not invent labels. [Slack identity](https://docs.composio.dev/toolkits/slack), [Notion identity](https://docs.composio.dev/toolkits/notion).

The identity session binds the server-supplied owner, toolkit, account, and read action. It is deleted after inspection. Successful labels are cached for 15 minutes, failed checks for one minute, and concurrent checks share one request. Only validated name/email fields leave the adapter; aggregate mailbox counts, history IDs, provider log IDs, and response URLs are discarded.

Direct Google profile proxy requests remain a fallback for Google services only. Historical local checks with the then-configured API key denied direct proxy and direct-tool requests with 403 while Tool Router identity tools worked for the same active Gmail, Calendar, and Drive accounts. This was not a revoked Google grant and did not require reconnecting. It does not establish permissions for a new development or production key. If neither supported identity path works, the UI reports unavailable details. Sheets/Docs identity depends on the permitted profile/about proxy path and is not live-verified.

## Credential ownership and migration

Composio owns the connected-account tokens in its default cloud deployment, refreshes them, and injects them into provider API requests. Provider tokens are redacted from account responses by default. Composio can still use those tokens, and tool results can contain private user data. Its execution logs retain tool payloads by default; review the project's retention controls. This service is not the browser password vault. [Token custody](https://docs.composio.dev/docs/security/token-custody).

Account and session references are tagged with their provider. Additive migrations preserve existing connections and pending consent while assigning stable local connection IDs. A legacy row containing an active account and a second pending account becomes separate records. Session configuration version 3 recreates the execution session with all seven toolkits without deleting OAuth accounts. The older table migration also retains session and event rows.

Disconnect and revoke connections with the old provider before replacing its adapter. A replacement provider cannot reuse another provider's account or session IDs. New authorization and webhook setup are required; changing adapters does not transfer OAuth credentials. Browser-vault and saved-channel ciphertext are unaffected.

## Notifications

Supported watches are requested automatically for each account. The API reports unavailable when signed webhook configuration is missing and pending when provider subscription creation has not succeeded. The Apps page has no watch switch. Disconnecting an account removes its watch; an active subscription is not proof that an event has arrived.

Set up a signed project webhook and put its secret in `COMPOSIO_WEBHOOK_SECRET`. The handler is `/api/webhooks/composio`. Otto does not automatically overwrite a project's existing webhook destination. An enabled watch is not permission to notify on every event; Otto's relevance check, user preferences, quiet hours, and dispatch limits still apply.

New hosted watches set a per-trigger `egress_url` to `/api/webhooks/composio` on the operator's `OTTO_WEBHOOK_ORIGIN`, or the HTTPS public application origin when no override is configured. The tenant host validates the canonical origin and supplies the fixed URL to the adapter. Composio still uses the project's existing signing secret, payload version and enabled events. This lets separate hosted installations share a project without replacing each other's project destination. The adapter preserves the exact owner, selected account, trigger configuration and pinned toolkit versions. Local mode without an explicit internal destination keeps project-level delivery. [Per-trigger destination](https://docs.composio.dev/reference/api-reference/triggers/postTriggerInstancesBySlugUpsert).

Existing saved triggers are not recreated or rerouted at startup. After verifying the project's signing configuration, an operator can update only the intended trigger IDs with their exact owner and new `egress_url`, then read them back and verify a durable event receipt. Keep the project settings and other owners' triggers unchanged. Changing a tunnel or deploying this behavior alone does not update old trigger destinations. [Scoped trigger update](https://docs.composio.dev/reference/api-reference/triggers/patchTriggerInstancesManageByTriggerId).

For hosted development, start the gateway on port 4330, then run the relay and a tunnel in separate terminals:

```sh
node scripts/webhook-relay.mjs
cloudflared tunnel --url http://127.0.0.1:4331
```

Set the **development** Composio project's destination to `<tunnel-origin>/api/webhooks/composio` and use its matching signing secret in `.env.hosted.local`. The relay listens on `127.0.0.1:4331`, forwards the permitted webhook routes to `http://localhost:4330`, preserves original bytes/signature headers and strips cookies and caller identity headers. It does not expose login, account, chat, files or internal control. `OTTO_WEBHOOK_ORIGIN=<tunnel-origin>` supplies the origin for new hosted Composio watches and hosted channel callbacks; changing it does not register a Composio project webhook or migrate saved watches automatically. Without that tunnel origin, HTTP loopback development leaves Composio's project destination in effect. When a temporary tunnel changes, update only development provider destinations and use the [scoped trigger update](https://docs.composio.dev/reference/api-reference/triggers/patchTriggerInstancesManageByTriggerId) to read back and patch each affected saved watch's `egress_url` with its exact owner. Changing the project destination alone does not replace existing overrides. See [local webhook setup](development.md#receiving-real-webhooks-locally).

For production, configure a signed subscription in the production Composio project and supply its matching secret to the hosted gateway. A dedicated project can use `https://<application-host>/api/webhooks/composio` as its destination; preserve an existing shared project's destination and route new hosted watches through their instance overrides. The gateway verifies the signature, resolves the registered UUID owner and signs the request to that owner's runtime. The runtime verifies the original provider signature again and checks the owned account/subscription. The gateway does not route events for `local-development` into a hosted account. For ordinary single-owner local mode, the webhook handler instead lives on port 4310; keep that application private and use only a deliberately configured webhook forwarder.

Composio's API supports `composio.triggers.setWebhookSubscription({webhookUrl})`; this updates an existing project subscription, so a development test must never target the production project. [Receiving events](https://docs.composio.dev/docs/setting-up-triggers/subscribing-to-events).

Google watches use `GMAIL_NEW_GMAIL_MESSAGE` or `GOOGLECALENDAR_GOOGLE_CALENDAR_EVENT_SYNC_TRIGGER`, pinned to the selected account. Gmail watches the inbox; Calendar watches the primary calendar. Both use a 15-minute interval. These are polling integrations; do not promise immediate delivery or exact reminder timing. Shared managed OAuth can add about 15 minutes of latency. [Trigger setup](https://docs.composio.dev/docs/setting-up-triggers/creating-triggers), [Trigger latency](https://docs.composio.dev/docs/triggers).

Slack watches use `SLACK_DIRECT_MESSAGE_RECEIVED`; they cover DMs, not channel messages. This V2 trigger requires a Composio webhook ingress configured on the Slack OAuth app, including its signing secret and an app-level token for per-user private-event authorization. Otto does not create or overwrite that provider ingress. Missing ingress or permissions leave subscription creation pending. [Slack trigger setup](https://docs.composio.dev/reference/changelog), [Slack trigger guidance](https://docs.composio.dev/kb/guide/toolkits-slack).

Notion watches use `NOTION_PAGE_CONTENT_UPDATED` for content edits on pages available to the integration. They do not cover page creation, property changes, or every Notion event. Provider webhook configuration and page permissions still apply; edits may be aggregated before arrival. [Notion trigger catalog](https://docs.composio.dev/toolkits/notion), [Event delivery](https://docs.composio.dev/docs/triggers).

The adapter verifies the signature over the raw body with the SDK's default five-minute timestamp tolerance. The application checks the user, provider, account, trigger, and enabled state, then stores a unique event receipt. A retryable outbox passes a bounded summary to Otto's notification filter before the main agent runs. It excludes message bodies and provider credential fields. Event subjects remain untrusted private content. Queued events and interrupted processing events are discarded if their connection or trigger is no longer enabled. Every claim rechecks those conditions before delivery. Downstream work must also deduplicate by event ID because delivery across a process crash is at least once.

## Cost and limits

As published on 2026-09-24, managed OAuth includes 20,000 calls and 10,000 delivered trigger events per month; paid overages are $0.0005/call and $0.005/event. The free plan stops at its limits. Scale is $29/month with $29 in monthly usage credit. Using your own OAuth apps provides larger allowances and lower usage rates. Model, browser, hosting, and messaging-provider charges are separate. Customers signed up before 2026-08-15 retain their previous pricing through 2026-12-31; check the existing account's dashboard. [Pricing](https://composio.dev/pricing).

## Validation

Use a dedicated development project, development accounts and disposable database state for live checks. Give test mail subjects and calendar event titles a unique synthetic marker such as `Otto development test 2026-09-26 <run-id>`. Use a recipient you control, bounded read queries and explicitly created test events; do not use unrelated private messages as fixtures. Record environment, commit, connection/subscription identifiers, safe timestamps, received event ID and observed result without retaining message bodies, tokens or authorization URLs. Distinguish authorization, account verification, subscription creation, signed event receipt and actual assistant processing. Any test send or calendar mutation must be authorized, and cleanup should target only the created marker/ID.

On 2026-09-26, a separate live development Neon preflight created a temporary database, provisioned two restricted tenant roles/app/jobs schemas, dispatched pg-boss work, initialized private object storage and confirmed foreign/control-schema access denial. Temporary resources were removed. This validates those database boundaries on the development service; it does not prove Composio consent, Google access, webhook delivery or a production deployment.

Feature tests inject a replacement provider and use real disposable PostgreSQL schemas. They check consent ownership, multiple accounts, exact read/review boundaries, scoped watches, duplicate events, revocation during recovery and session upgrades. `integration-consent` uses the real SDK adapter with a transport fixture that reproduces Composio's pinned-account rejection; it checks temporary-session cleanup, preserved execution/account bindings, custom auth configuration, invalid links and private failure handling. `integration-apps` covers Slack/Notion and file-account binding; `integration-files` covers returned descriptors, network pinning, redirects, streamed size limits and cancellation. `connections-ui` covers visible per-app actions and cache/focus behavior. Adapter tests cover SDK validation, signed webhooks, failure envelopes, verified identity fields, and cleanup of account-scoped identity sessions. Run them with `TEST_DATABASE_URL` pointing at a local test database.

Live local checks on 2026-09-24 verified existing Gmail, Calendar, and Drive consent state and their read-only identity tools. Gmail label listing was also verified. These checks did not read email bodies, send messages, alter grants, or prove Calendar/Drive writes, Sheets/Docs account flows, trigger arrival, or production delivery. See [verification](verification.md) for the broader application record.

On 2026-09-26, the live second-account Gmail request reproduced HTTP 502 before the fix and returned HTTP 200 with a fresh consent link afterward. The link reached Google's account chooser after temporary-session deletion. The existing Gmail account remained unchanged. No account was selected, OAuth was not completed, and this does not verify a second active Gmail account or its tools. The focused integration, provider and Apps suite passed 37 checks with disposable database schemas.

The 2026-09-25 Slack/Notion addition is fixture-tested only. Official current catalogs and attachment response schemas were read without executing an account tool. No real Slack/Notion consent, action, webhook, private-file download or external message delivery was performed in this change.

On 2026-09-28, custom-client consent and bounded metadata reads passed for all five Google apps in development and at the Otto production origin. After the exact production Gmail/Calendar watch destinations were repaired, a read-only audit through 22:22:56 UTC confirmed three Gmail and 79 Calendar receipts delivered through the signature/ownership checks and classifier. This proves that observed ingress and processing path, not a user-visible notification or an external send. The [cutover record](testing/results/2026-09-28-otto-cutover.md#manual-release-webhook-receipts-and-remaining-recovery) separates the live results from fixtures and remaining Slack/Notion acceptance.
