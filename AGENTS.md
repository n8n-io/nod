# Nod

Setup, use and how the system works are in the docs site, whose pages live in `docs/src/content/docs` (start with [architecture](docs/src/content/docs/how-it-works/architecture.mdx) and [Trust and Vault](docs/src/content/docs/trust/index.mdx)). Development and checks are in [CONTRIBUTING](CONTRIBUTING.md).

## Rules

- Do not push, deploy or publish without explicit authorization.
- Keep keys, credentials and private user content out of Git, logs, prompts, test fixtures and client configuration. No tool returns a saved password, code or card to Pi.
- No code comments or JSDoc.
- Prefer deleting to patching ceremony. Breaking changes are fine; keep the code small.
- Keep prototypes, internal research, plans, review notes and validation artifacts outside the repository.
- Use synthetic data and disposable database schemas. Never reset the normal local database, and never call a live model, connected account or real recipient from a test.
- Analytics events follow [Change analytics](docs/src/content/docs/contribute/analytics.md): bounded values and no private content. Submitting About you explicitly sets bounded answers on the PostHog person profile under the installation ID while usage sharing is enabled, even without an email; typed answers stay out. An onboarding email submitted with its own consent to updates about Nod and other n8n products sets the `email` property on that same profile. Ordinary events do not create profiles; later events can link to a profile once it exists. Opt-out stops new sends; already stored contact data is deleted by request. Update the user-facing event list and any PostHog dashboard whose answer changes in the same change.
- Documentation lives only in `docs/`. When setup, behaviour or a safety rule changes, update the matching page in the same change and follow [Write docs](docs/src/content/docs/contribute/write-docs.mdx). Package READMEs stay short pointers to the docs.

## Architecture

- One thread per owner, shared by web, Telegram and WhatsApp: one sandbox workspace keyed by the thread ID, and sessions that share it. The chat is the session keyed by the thread ID, with a persistent Pi session; app events and source checks feed one observer session for the active thread, which keeps its Pi context only while the provider cache is warm (five minutes since its last request) and the context is no larger than compaction would keep. Its first instruction puts the stable request data first, then recent chat, and the saved matters, batch and time last; when it starts fresh and its previous request was under an hour ago, Anthropic requests keep the system prompt, the stable request data and recent chat in the one-hour cache, with the rolling breakpoint at five minutes and at most four breakpoints; a warm session keeps the normal five-minute cache. On Anthropic, curator calls (trust, attention, access) keep instructions sent within the last hour in the one-hour cache and never cache their one-off input. Each schedule fire has its own session, keyed by its first turn; a recurring schedule skips a fire while an earlier fire's session is queued, running or waiting on the owner, and a schedule fire can't create schedules. A recurring schedule may name `watch` connections that have a change signal (Gmail inbox polling, a change token or app triggers); each fire refreshes those signals without a model and skips the run when their fingerprint matches the one recorded at the last run and that run succeeded. The observer starts a separate task for work that needs an outside action or a wait.
- Every user message, schedule fire, observer batch and resume is a turn. Each turn belongs to one session (`turns.session_id`); a session runs one turn at a time, sessions run in parallel, and a resume continues the session that asked. `delegate` runs subagents inside a turn: in-memory Pi sessions with Nod's tools and their own browsers, run in parallel by Pi, whose answers return as untrusted tool results. Every write from a turn goes through `withTurnLock`, including schedule, limits, notification-setting and rules writes an agent makes, which run under the turn lock with the turn's signal so a Stop before the write refuses it. Stop ends a turn at once: the runtime races every tool call against the turn's signal and never waits for one that ignores it, and `withTurnLock` refuses its late writes. A message Nod is still handling when all work stops (from its arrival, or for a chat app from when Nod starts reading it) is saved with its turn already cancelled and withdrawn, and answers no confirmation, question or task; a recording the Stop control catches mid-transcription is cancelled before it's saved instead. A stopped confirmed app action is refused before provider dispatch, and a stopped workspace command ends every process the command started in the container, including a detached one. Turns and tool calls are never retried automatically, and app actions run with provider retries off; Pi and the memory model retry only failed model requests. In a chat or background session, a model request that fails, a provider refusal included, takes what it added since the last answered request out of the model context; the chat keeps the owner's message and the session's saved transcript keeps everything removed. A turn that carries owner words is withdrawn (`turns.withdrawn`) when its model request fails at the provider. When the owner's Stop, `/stop`, task Stop or reset cancels a queued, running or still-current waiting turn, the request it belongs to is withdrawn: that turn and its earlier turns in the same session, when any of them carries owner words. A waiting turn a later turn had already superseded, an agent's `task stop` and other cancellations withdraw nothing. A withdrawn turn's owner messages stay in the chat and Pi can still look them up with `history_search` or name one to `memory_learn`, but nothing else feeds them to a model (recent or related chat, memory recall, the trust check, the confirmation writer, memory learning's automatic reads), and the session's next turn gets `withdrawnRequest`, so it continues that request only when the owner asks again. A failed schedule run or task, including one Nod started, posts a failure that names the work. A task's next check resumes its own session when due, as a resume with that task's authority.
- Each session checks in when its model spend since the owner's last message to it passes the owner's task check-in ($5 by default, set in Usage or by telling Nod; plan usage counts at its API-price estimate). Its tools then refuse new work except reporting, the task actions that report, update, finish, list or stop saved work, and `ask_user`; task start and reply do not pass in any session. Helpers stop at their next step, and a turn that ends past its check-in without asking, or whose model keeps working, waits on the check-in notice as its question, so a task shows Needs you and the observer starts no new batch until the owner replies. The spend comes only from `model_usage`. Finishing onboarding saves a $200 monthly limit unless the owner already saved limits; removing it is never undone. Once the monthly limit is reached, a `user` turn (an owner message in chat or a reply to a task) still runs: its model calls and trust checks pass the limit, and its tools refuse everything except replies, `usage_get` and `limits_update`, with image analysis and memory preparation skipped. Every other turn fails before the model; work the owner started posts one notice that names the limit and links Usage, and event turns post nothing. Transcribing the owner's own voice message ignores the limit.
- Each chat and background session saves its Pi transcript and has its own browser, keyed by the session ID and opened on first use. The chat's Pi session stays open after a turn for Pi's idle cache warming while Nod allows it (current conversation, under the monthly limit), until the next turn or 30 minutes. Compaction summaries use the selected model at its lowest effort, and a turn that crosses the compaction line sends its reply first and compacts after it while the request still fits. Sessions and subagents run in parallel. Each subagent has its own run ID, browser, and output directory. When the browser container is full, a browser used in the last five minutes is never closed for another, but one idle for longer can be, even while its session or subagent still runs; a browser waiting on the owner is never closed for another during its 30-minute hold, after which it can be. A new browser waits for a free slot until its turn stops. Every agent-browser request has a deadline (60 s, or its own timeout plus 30 s, above agent-browser's own 30 s per-call limit); a browser that misses one, is interrupted or doesn't close within 5 s is killed with its Chromium process group and reopens fresh. A chat or background session can hand its browser to the user. Each handoff belongs to its waiting question, turn, and browser; a reply or Done continues that session, and Done posts no owner message. In Nod's browser every passkey request fails at once. Subagents return questions to the parent and cannot message the owner or connect apps. A background session's browser is deleted when the session ends without waiting, or is stopped or reset; a later turn of that session, such as a task the owner continues, starts a fresh browser. Only a reset conversation's browser is refused for good.
- One execution scope links thread, session, turn, run, parent run, and browser IDs. Execution and tool activity use `turn_events`. `model_usage` is the only cost ledger; each model request has one usage ID, and all totals come from its rows. Parent runs never record child costs again. Keep execution IDs internal.
- Pi-native tools (read, bash, edit, write, find, ls) run inside the sandbox through `WorkspaceSession.exec`. The pinned Pi web extension runs in the server process with its process permissions.
- Local files (`src/server/local-files.ts`) are the one host-file path: the built-in `files` tool runs `LOCAL_FILES_*` actions in the server process through the trust check, only in the desktop app (where the `Trash` port is Electron's `shell.trashItem` in the main process), and only in a turn whose lineage starts with an owner message or a schedule run with an owner instruction, with no proactive turn in it; anything else is refused before any path is touched. There is no folder list: paths must resolve into the home folder or a mounted volume (under `/Volumes` on macOS, a non-system drive on Windows), never into hidden entries, `Library`, `AppData` or `Backups.backupdb` anywhere below them, files named like secrets (keys, certificates, password databases and exports, `.env`, cloud credentials), Nod's data root, or a folder on the owner's keep-out list (`preferences.local_keep_out`). Nod adds to that list with `files keep_out` (up to 100 entries, in work the owner started, under the turn lock), which needs no trust check because it only restricts; only the owner removes an entry, through `DELETE /api/local-files/keep-out`. A home folder or volume root can be listed but never changed as a whole, and nothing that holds the data root or a kept-out folder is moved or trashed. Paths are checked as text first, resolved through links and checked before the trust check, so the checker and the owner see the real paths, and checked again when the action runs; the final file is opened without following links and must be the same file the check saw, and writes, edits and moves re-check the target's folder right before changing it. Listing is a read; opening a file (read, or import into the workspace) requires a quote of the owner's words, like a sign-in; writing, editing, moving, trashing and exporting a workspace file are actions. A subagent's file action that would ask is refused. Nothing is deleted outright: trash, overwrite and edit go through the `Trash` port and refuse before changing anything when none exists; the old version is trashed from its own path after a hard-link backup, and a failed trash step changes nothing. Moves never replace an existing item (exclusive link, copy, folder or symlink creation), no write, export, folder or move creates a program or shortcut name, except a move that keeps a program's own extension, a relative link moves only within its folder, executable files (mode bits, or program extensions) are never written or edited, executed paths must equal the paths the check saw, and written, edited and exported files are marked as downloaded (macOS quarantine, Windows `Zone.Identifier`), best effort.
- Provider keys never enter the sandbox or the browser. The Pi web extension, `create_audio` and apps run server-side; the web extension never reads local files or uses the server's own logins, such as a GitHub CLI session. The browser and the web extension reach only public addresses, checked when each connection opens, and Nod drops any proxy the model names or the extension's settings set for a web tool. An OpenAI-compatible model server is one the owner runs separately and names by address in local Nod or its `.env`; Nod sends model requests and that server's optional key only to that address. An Azure OpenAI key goes only to the endpoint the owner enters, over HTTPS unless it is on this computer, and an Amazon Bedrock key only to AWS in the Region the owner enters. An n8n instance the owner names by address on its setup page may also be local or private; Nod sends that connection's requests and token only to that address (loopback names on the same port count as one host), and any access path the model proposes stays a public HTTPS address. The setup page prefills n8n's default `http://localhost:5678` when its MCP metadata answers there, the only address Nod checks on its own; the owner still selects Connect.
- A connected CLI's credentials reach only a sealed install of the path's declared source, run as that CLI's own Linux user in group `nod-connected` with an environment built from scratch; nothing the sandbox user or another CLI can write runs with them.
- `src/server/composition.ts` is the only place that selects providers and runtime implementations. Capabilities are ports in `src/ports`; vendor SDKs stay in `src/providers`; product policy stays in `src/server`; `src/web` imports only web and shared code.

## Safety invariants

- Trust check (`src/server/trust.ts`): one checker decides every connected app action, every browser step that can commit (click, key press, choosing an option, ticking a box, drag, upload, accepting a page dialog, a page script with side effects; reads, typing and read-only scripts skip it, and a download aimed at a control instead of a link is checked as a click), and every sign-in or saved-session use before it runs, app reads included (tool discovery with `SEARCH_TOOLS` reads no app content, only connected account names, and skips it), and every change Nod makes to its own schedules, notification settings, the owner's rules, spending limits or memory (forgetting a note, turning memory on or off, clearing it); a scheduled run is checked against its schedule's instruction and an event turn against the owner's notification rule, their standing instruction. Saving a note follows the memory rules below, and only a turn started by an owner message can forget a note or clear memory. `NOD_TRUST_MODEL` selects `selected` (the default), `llm` or `decision`. `selected` uses the owner's selected model, or an audio model's visible same-connection text companion, at the lowest reasoning effort. `llm` checks always use a known small model. They prefer the selected connection, then another connected service, and never use the larger chat model as a fallback. Decision mode selects direct TypeSafe Jev 1.14, OpenRouter Jev 1.14, Perplexity Decider 1.2 through OpenRouter, then OpenAI Decisions directly or through OpenRouter. If none is available, it selects the same small LLM before the check starts. A failed lookup blocks the check. A failed or uncertain decision never switches the checker to an LLM. Jev combines native probabilities with a fixed monotonic classifier. Separate owner-only permission, nested-effect and typed time checks support its decisions. Providers are selected before a request and stay fixed for all steps of the check. There is no separate decision-model override. Confirmation writing and its fact check use the selected LLM or text companion. The checker sees the owner's configured time zone and only their recent messages (for a task, the chat's recent owner messages frozen when the task started, never later chat messages, plus the owner messages addressed to that task), the owner messages in its turn chain (the request and every answer to Nod's questions), and the message they answered (the one the owner replied to, or else the latest assistant message in that channel before it; a task's check sees it only when it is that task's own message), which shows what the reply answers and never proves what the owner saw or approved (a first task the owner tapped is Nod's wording, so it never counts as their message), or for a scheduled run the instruction that created its schedule and the run's time and time zone, or for work Nod starts on its own the current notification rule, plus the action's arguments as Nod sends them, never tool results; it always sees the whole request and the whole reply. A withdrawn turn's owner messages never count, not even in the turn chain, and when the message a reply answered was posted by a withdrawn turn the checker sees no answered message rather than an older one, so the owner authorizes that work again by asking again. Every check, in every kind of work, also sees the owner's rules (`preferences.rules`): their lasting words on what Nod may do without asking or must ask about first. Only then does the checker prompt gain its rules paragraph, so owners without rules get the same prompt as before. A rule to ask first, or not to act, makes the action ask even when other owner words cover it; a rule to go ahead counts as owner words for what it says and never covers Nod's own settings. The checker names a rule as the reason it asks only when the owner has rules. To run a non-read action the checker must quote, word for word, the owner words that allow it (a message it was shown, the schedule instruction, the notification rule or the owner's rules), or say "read"; opening a local file (`LOCAL_FILES_READ`, `LOCAL_FILES_IMPORT`) never counts as a read, like a sign-in; the server checks the quote appears in what it showed and otherwise asks, records the basis with each app action and Vault use, and Usage shows the quoted words while their message still exists. A rule change Nod makes shows the checker the current rules, so the owner's words must cover anything it adds; the owner's own edit in Usage needs no check. Work Nod starts on its own (event turns, activity checks included) gives it no owner words beyond that rule and the owner's rules, neither of which covers Nod's own settings, never the event, and a resume that traces back to no owner message, schedule or event gives it only the owner's rules. A notification rule change shows the checker the current rule, so the owner's words must cover anything it adds. It runs reads, drafts and actions the owner's words ask for, where words that ask for an outcome (buy this there, move that meeting and tell its people) cover the steps it needs on the target they name up to and including the commitment they name, and nothing past it; a general request to solve a problem or a supplied document does not choose an outside commitment, and a short reply inherits only a concrete proposed action or outcome on its target, never advice listing possibilities or a general offer to help; a browser step whose effect its control leaves unclear runs only inside such an outcome on that website, never for a question, lookup or summary, and only when its worst plausible effect stays within it, and cookie-banner choices count as reading, since they stay in Nod's own browser. Anything else waits for the owned yes/no confirmation, and a failed check asks; in scheduled and event work, a check that fails or gives no verifiable basis refuses the action with the reason instead of asking, while an answer that doesn't allow the action, uncertain decisions included, still asks. No stored list of recipients or past confirmations skips the check. Every confirmation is bound to the exact action and arguments and stays open while its turn waits; a turn, subagents included, has at most one open confirmation, approvals refuse a second, and no app or memory call issued after one that asks runs; a reply answers only the confirmation it was read against, never one asked while Nod was reading it, and a reply to one that is no longer pending is an ordinary message. The checker reads the owner's reply to a confirmation on its own, without the question or the action, and only a reply it reads as an unconditional yes approves. A reply it can't read leaves the confirmation open; any other reply closes it without running, and a direct reply to a background session's confirmation continues that session. Only questions are recorded. Confirmed actions run once; failed or interrupted ones become uncertain and are never re-run, and the resumed turn continues with the reason, as it does when a confirmed action can no longer run. When Stop or a failure ends that resumed turn first, each later turn of its session is told whether the approved action ran, may have run or did not run, until a turn of that session succeeds or waits for the owner. A recorded question fences its exact action for the rest of that request, even when the checker would now run it: once done, a repeat returns the recorded result; while pending, declined or uncertain, a repeat is refused; an expired one never ran and fences nothing. A browser step is described by agent-browser's own ref label or the accessibility tree, plus the method and address of the form a click or Enter would send (for Enter in a field, through the form's default button), read from that element's form in an isolated world, never page parsing, or unknown when the browser can't inspect the control or same-label controls send different forms; a confirmed step replays once only while the browser is on the same page, its refs still exist and the form it sends is unchanged, otherwise it does not run; subagents refuse steps that would ask. When a step asks, the confirmation writer and its fact check read the page's visible text as target details; the checker never sees page text.
- App, browser, web and codemode results that the model receives directly, confirmed-action results and failures, and connected-app event data (the whole event, with secret-named keys removed and email that gives account access hidden: each mail-shaped record is checked on its own by a decision model, or else the connection's smaller model, from its sender, subject, HTML link destinations and the start and end of its text; no decision is reused from an earlier read; a failed check hides it; downloaded mail files are not checked) reach Pi inside one `untrusted_tool_result` block with a data-not-instructions notice; tags inside the content are neutralised. Errors reach Pi unwrapped. Calls made by codemode scripts stay raw. A connected MCP server's tools also run as their own deferred Pi tools (`mcp__<server>__<tool>`), directly or from codemode, through the same trust check, ordering and wrapping as `apps`; each server's own instructions reach Pi inside one untrusted block. Nod's own confirmation notice is the only app result left unwrapped. Nothing scans content for injection phrases; the server limits what fooled text can do.
- Vault and sign-in: `sign_in` never returns a saved value. The one trust checker decides each sign-in and saved-session use from the owner's words (a sign-in the owner completes in the private form needs no check, because entering it is their consent); otherwise the owner's yes, bound to the exact origin and item, covers the rest of that task. A domain mention does not grant consent. The server claims a durable use before browser work. Pi selects the fields and submit control; the provider checks actual frame origins, enters and submits privately, then keeps the live page for Pi to inspect, and a saved-login entry returns that page inside its untrusted result. Known secret values (passwords, codes, card numbers and security codes, not usernames or the cardholder name) are removed from tool output and masked in screenshots. A saved login's authenticator key never leaves the server: when a page asks for a code without `emailCode`, the server generates the current code and enters it like any code, after the same trust check as that login, only for the login this task signed in with (without one, the login Pi names or the only keyed login for the origin), once per sign-in. 1Password logins reach Vault only when the owner picks one in the private form: the 1Password SDK runs in a separate helper process (on macOS the Electron Plugin helper, the only Nod process allowed to load 1Password's library), never in the server; it lists only the logins 1Password would fill on the request's exact origin and re-checks the picked item, and Nod saves an encrypted copy that then works like any saved login. Native side-effect checks permit read-only JavaScript without a reload; a document changed by Pi JavaScript requires a reload before entry. All normal Pi tools work after submission, except that page scripts pause on a document where Nod filled a private value until it reloads or navigates, and a reload of a page reached by a form POST, or whose navigation Nod can't read, re-opens its address with a GET rather than resubmitting. Failed entry keeps the observation lock until the filled document changes. Event turns carry only the notification rule, so their sign-ins and saved-session uses ask the owner unless the rule needs that website and, for a saved session, the website it belongs to; every schedule fire, event and subagent starts in its own fresh browser. Secure forms and payment requests bind owner, turn and origin, stay open while their turn waits, and close when a newer request or a newer turn starts in their session (a chat message never closes a background session's form); the waiting turn resumes in the transaction that records the entry. The server and destination website are trusted with submitted values; output redaction does not contain every transformation a website can make.
- Pi reads the page from the agent-browser snapshot and chooses login methods and fields. Do not add page-parsing scripts, snapshot regexes or field checks around the browser; leave the page to Pi, the model and agent-browser. Pi can run page JavaScript with browser evaluate. Tool output replaces known secret values. Keep site-specific cases in regression fixtures. Two exceptions: when a browser step asks the owner, the server reads the bound page's `document.body.innerText` with a read-only script for the confirmation question, which never reaches the checker; and before a click or Enter, the server reads the method and address of the form that the exact target element would send, through the form's own properties in an isolated world, for the checker.
- Before choosing a login method, check saved account metadata. Reuse a uniquely applicable login, which selects the password method because a saved login is a username and password, or the method the user chose. If the method remains ambiguous, offer the observed controls through `sign_in` with `kind: 'method'` so the owner chooses in the private panel. Ask in chat when the matching account remains ambiguous.
- Payments: `pay` binds one request to the shop, checkout document, actual card-field origins, submit control, amount, currency and selected card revision. The owner approves in Nod web or desktop with the card's security code, which Nod never stores. A chat-app task uses the desktop private form and resumes in its original channel. Private URLs and payment codes never pass through chat apps. The claim locks and reads the approved revision on an active turn. The provider uses field-bound private entry and submission, then keeps the live page and removes known secret values from observations. A durable use never runs twice; interrupted work is uncertain. Usage records card submitted, not paid. A payment from an event turn needs the owner's approval like any other. Stored PAN use does not enforce settlement at the issuer or establish PCI compliance.
- Secrets in chat: Pi is told never to ask for passwords, codes, card details or API keys in chat and to use `sign_in` or `pay`, which open private entry. Nothing filters the reply text. While a verification request is pending, only a message whose only letters or digits are the code, 4–8 digits 0–9, is the code; any other message with a number of three or more digits that ends it or doesn't follow a letter or digit, in any wording or language, is refused with a request to send the code by itself, so it reaches neither the website nor the model. While a payment request is pending, a card code sent by itself (3–4 digits) or one labeled CVV, CVC or security code is caught. A code sent as a reply to a closed request is refused, and a code by itself or ending a message is refused until ten minutes after a newer turn starts in that session. Other messages and any other secret the owner types reach the model.
- Pi never writes memory text. `memory_learn` works only in work the owner started (chat or a task) with an owner message: the server reads that message, the owner's last 10 messages in its conversation that aren't withdrawn and any older owner messages Pi names by ID (never a task-card title the owner tapped, a message over 4,000 characters or one with a secret), and only those messages and the memory index reach the memory model, which writes one declarative fact per note and may archive notes they make untrue; the server keeps only notes that quote a cited owner message and hold no secrets, saves them as confirmed and archives instead of deleting. Background memory learning reads only the owner's own user messages (up to 4,000 characters, no attachments, none with a memory-save approval, none withdrawn, never a task-card title the owner tapped), never assistant text or tool results; web content reaches memory only if the user pasted it. Learned entries stay tentative until a second message repeats them, and automatic changes archive active entries instead of deleting them. The archive itself is bounded, and only a user-requested forget deletes a note; when memory is full, the least recently used learned skill the owner hasn't edited is dropped. Sensitive topics (health, religion, politics and similar) are learned in the background only when the owner turns them on, and Pi is told to save them only then or when the owner explicitly asks. One exception: when Gmail connects, a background job reads the owner's own text from recent sent emails (quoted, forwarded and automated mail removed) and saves only their writing style, with no facts, names or quotes, as one capped `preferences` entry labelled "Learned from your sent email" that replaces its earlier version by archiving it. Learned skills are the one kind of memory Nod writes itself: Pi saves or patches one (`skills save`/`patch`) only in work the owner started (chat, a task or a schedule), never from event turns or subagents, and not while saving is off. The server redacts known secrets from each draft, then the memory model rewrites it as a procedure without personal data, as a model's best effort, dropping outside sends the flow didn't need. Skill text reaches Pi as untrusted data, never counts as owner words, and never reaches the trust checker, confirmation writer or fact check.
- Conversation traces: only while the owner's **Share conversation traces** switch is on, each Pi model request and its reply, with the model that actually handled it, except checks of account-access email and the memory, writing-style and skill writers, leaves through `src/server/traces.ts`, which replaces execution IDs, and Nod's IDs inside the content, with keyed hashes that change daily and on restart, replaces the home folder path with `~`, and removes known secrets, the names on the owner's connected app accounts and validated personal identifiers (`src/server/personal-data.ts`; `src/providers/pi/traces.ts` replaces images with `[image]` and drops the owner context, memory tool results and learned-skill reads, keeping only their action) before the n8n Nod Traces workflow forwards it to LangSmith. Traces are pseudonymised, not anonymous: what a conversation says can still identify the owner. Separate decision-model calls are not included. Turning the switch off stops sending at once. Nod never holds a LangSmith key; official desktop builds carry only the workflow's webhook token, from the release secret.
- File previews: artifact HTML renders only as `srcdoc` in an `allow-scripts` iframe without same-origin, behind a no-network CSP placed before the content, and the preview closes if the frame loads another document. Other formats render as text, canvas, React or a script-less sandboxed frame, never as HTML in the app's DOM. HTML, SVG and XML never get a local `blob:` preview.
- Owner isolation: every query and route is owner-scoped.
- Local access: loopback and Host are not identity, since containers reach host listeners. Every local `/api` request needs the owner key from `NOD_DATA_ROOT/access-key` (a cookie set from the printed `#access=` link, or the desktop header); only verified webhooks, OAuth callbacks with one well-formed state, the key exchange and the privacy notice go without it. Never mount the data root or pass the key to a container or prompt.

## Model policy

- Progress follows the shared rule in `src/shared/conversation-style.ts` in chat, tasks, compact prompts and the observer. Report a result only when the owner can use it now, a change affects their next step or they need to decide. Claims about created, updated or completed work need a confirmed tool result and an inspectable output. Routine checks and private record changes stay quiet. Spending check-ins state the cost and what continuing would do; include completed work only when useful for that decision and inspectable.
- Conversational confirmation and channel handoff text comes from the selected model, or an audio model's visible same-connection text companion, at its lowest reasoning effort through `src/server/communication.ts`, with recent owned messages as language-only context. No phrase lists or fixed confirmation templates. A separate model call checks confirmation claims against the frozen action without conversation context; arguments define proposed changes, while details may describe the current target. The server adds where the work comes from (its schedule or task, the owner's words that set it up, and whether a recurring schedule waits on the answer), never Pi's reasons; the question opens with it, never as proof the action is needed, and leaves out options that don't change the decision. A draft that isn't the requested JSON, or a rejected question, gets one fresh draft, checked the same way. Approvals recheck the turn before saving; failed generation or a second failed review leaves the action blocked. Response language comes only from the owner's own words, never from data such as email, and is English before they write; it is independent from region, clock format and time zone. What Nod reads in data is translated, keeping its original wording only in quotes, such as a button name.
- Pi does not ask before app actions, sign-ins, bookings or payments; the trust check and payment approval ask the owner when their words don't cover an action. Pi asks only when the account, target or action is unclear.

## Validation

Run only the checks needed for the files and behavior changed. Documentation and media changes need formatting, link, and visual checks. Do not run application lint, tests, integration tests, or builds for these changes. Build the docs site when its pages, configuration, or code change.

For application changes, start with focused tests. Run broader checks only when the change affects shared behavior or the focused checks cannot verify it. For capability eval changes, run `pnpm --dir evals run check` and `pnpm --dir evals test`. The evals themselves call live models, so run them manually (see [evals](docs/src/content/docs/contribute/evals.mdx)). Report fixtures, UI checks, and live checks separately.

## Tests

Keep only tests that would catch a real regression in:

- the core harness (one thread and Pi session per owner, sequential turns, stop, interruption, reset, session rebase);
- sandbox isolation (nothing on the host, no keys in the sandbox, contained paths);
- safety (approvals, uncertain actions, Vault and sign-in fencing, onboarding task cards);
- owner isolation (owner scoping, local access, URL guards, redaction);
- real integration contracts (channel delivery, schedule firing, downloads, OAuth completion).

No tautological tests, mocks that return what they were told, or tests of UI copy, wording, CSS, constants or configuration. Extend the existing file for an area instead of adding one.
