# Otto

Setup, use and how the system works are in the docs site, whose pages live in `docs/src/content/docs` (start with [architecture](docs/src/content/docs/how-it-works/architecture.mdx) and [Trust and Vault](docs/src/content/docs/trust/index.mdx)). Development and checks are in [CONTRIBUTING](CONTRIBUTING.md).

## Rules

- Do not push, deploy or publish without explicit authorization.
- Keep keys, credentials and private user content out of Git, logs, prompts, test fixtures and client configuration. No tool returns a saved password, code or card to Pi.
- No code comments or JSDoc.
- Prefer deleting to patching ceremony. Breaking changes are fine; keep the code small.
- Use synthetic data and disposable database schemas. Never reset the normal local database, and never call a live model, connected account or real recipient from a test.
- Documentation lives only in `docs/`. When setup, behaviour or a safety rule changes, update the matching page in the same change and follow [Write docs](docs/src/content/docs/contribute/write-docs.mdx). Package READMEs stay short pointers to the docs.

## Architecture

- One thread per owner, shared by web, Telegram and WhatsApp: one sandbox workspace keyed by the thread ID, and sessions that share it. The chat is the session keyed by the thread ID, with a persistent Pi session; every schedule fire and event is its own session, keyed by its first turn.
- Every user message, schedule fire, event wake and resume is a turn. Each turn belongs to one session (`turns.session_id`); a session runs one turn at a time, sessions run in parallel, and a resume continues the session that asked. `delegate` runs subagents inside a turn: in-memory Pi sessions with Otto's tools and their own browsers, run in parallel by Pi, whose answers return as untrusted tool results. Every write from a turn goes through `withTurnLock`. Turns and tool calls are never retried automatically, and app actions run with provider retries off; Pi and the memory model retry only failed model requests, and provider lookups (accounts, catalogs, schemas) may retry at the HTTP level.
- Every session has its own browser, keyed by the session ID and opened on first use. The browser container keeps at most four live, enough for the chat, `delegate`'s two parallel subagents and a scheduled run; a browser used in the last five minutes is never closed for another, but one idle for longer can be, even while its session or subagent still runs, unless it's handed to the user. A new browser waits up to two minutes for a free slot, then fails as busy. The chat's browser is the one handed to the user. A background session's browser is deleted when the session ends without waiting, or is stopped or reset.
- Pi-native tools (read, bash, edit, write, find, ls) run inside the sandbox through `WorkspaceSession.exec`. The pinned Pi web extension runs in the server process with its process permissions.
- Provider keys never enter the sandbox or the browser. The Pi web extension, `create_audio` and apps run server-side; the web extension never reads local files or uses the server's own logins, such as a GitHub CLI session. The browser reaches only public addresses.
- A connected CLI token reaches only a sealed install of the path's declared source, run as that CLI's own Linux user in group `otto-connected` with an environment built from scratch; nothing the sandbox user or another CLI can write runs with a token.
- `src/server/composition.ts` is the only place that selects providers and runtime implementations. Capabilities are ports in `src/ports`; vendor SDKs stay in `src/providers`; product policy stays in `src/server`; `src/web` imports only web and shared code.
- Hosted mode: a gateway authenticates Google sessions and routes to one immutable-owner tenant runtime per user. Never change the owner per request.

## Safety invariants

- Trust check (`src/server/trust.ts`): one checker decides every connected app action and every sign-in or saved-session use before it runs, reads included (tool discovery with `SEARCH_TOOLS` reads no app content, only connected account names, and skips it), and every change Otto makes to its own schedules or notification settings; a scheduled run is checked against its schedule's instruction and event turns ask. Memory tools follow the memory rules below, and only a turn started by an owner message can forget a note. It is the owner's selected model at its lowest reasoning effort. It sees only the owner's recent messages and the message they answered (a first task the owner tapped is Otto's wording, so it never counts as their message), or for a scheduled run the instruction that created its schedule, plus the action's arguments as Otto sends them, never tool results; it always sees the whole request and the whole reply. Work Otto starts on its own (event turns, activity checks included) gives it no owner words, and neither does a resume that does not trace back to an owner message. It runs reads, drafts and actions the owner's words ask for; anything else waits for the owned yes/no confirmation, and a failed check asks. No stored list of recipients or past confirmations skips the check. Every confirmation is bound to the exact action and arguments and stays open while its turn waits; a turn, subagents included, has at most one open confirmation, approvals refuse a second, and no app or memory call issued after one that asks runs; a reply to one that is no longer pending is an ordinary message. The checker reads the owner's reply to a confirmation on its own, without the question or the action, and only a reply it reads as an unconditional yes approves. Confirmed actions run once; interrupted ones become uncertain and are never re-run.
- App, browser, web and codemode results that the model receives directly, confirmed-action results and connected-app event data (the whole event, with secret-named keys removed and verification-code email hidden) reach Pi inside one `untrusted_tool_result` block with a data-not-instructions notice; tags inside the content are neutralised. Errors reach Pi unwrapped. Calls made by codemode scripts stay raw. Otto's own confirmation notice is the only app result left unwrapped. Nothing scans content for injection phrases; the server limits what fooled text can do.
- Vault and sign-in: `sign_in` never returns a saved value. The one trust checker decides each sign-in and saved-session use from the owner's words; otherwise the owner's yes, bound to the exact origin and item, covers the rest of that task. A domain mention does not grant consent. The server claims a durable use before browser work. Pi selects the fields and submit control; the provider checks actual frame origins, enters and submits privately, then keeps the live page for Pi to inspect. Known secret values (passwords, codes, card numbers and security codes, not usernames or the cardholder name) are removed from tool output and masked in screenshots. Native side-effect checks permit read-only JavaScript without a reload; a document changed by Pi JavaScript requires a reload before entry. All normal Pi tools work after submission, except that page scripts pause while a field Otto filled still holds its value. Failed entry keeps the observation lock until the filled document changes. Event turns carry no owner words, so their sign-ins and saved-session uses ask the owner; every schedule fire, event and subagent starts in its own fresh browser. Secure forms bind owner, turn, origin and expiry, and close when a newer turn starts in their session (a chat message never closes a background session's form); the waiting turn resumes in the transaction that records the entry. The server and destination website are trusted with submitted values; output redaction does not contain every transformation a website can make.
- Pi reads the page from the agent-browser snapshot and chooses login methods and fields. Do not add page-parsing scripts, snapshot regexes or field checks around the browser; leave the page to Pi, the model and agent-browser. Pi can run page JavaScript with browser evaluate. Tool output replaces known secret values. Keep site-specific cases in regression fixtures.
- Before choosing a login method, check saved account metadata. Reuse a uniquely applicable login; ask when several methods are available without a matching saved login, unless the user already chose. Ask when the matching account or method remains ambiguous.
- Payments: `pay` binds one request to the shop, checkout document, actual card-field origins, submit control, amount, currency and selected card revision. The owner approves in Otto web or desktop with a code or, after explicit card permission, yes. A chat-app task uses the desktop private form and resumes in its original channel. Private URLs and payment codes never pass through chat apps. The claim locks and reads the approved revision on an active turn. Code retention never restores revoked permission. The provider uses field-bound private entry and submission, then keeps the live page and removes known secret values from observations. A durable use never runs twice; interrupted work is uncertain. Activity records card submitted, not paid. Turning `payment_setting` on requires an owned confirmation for the exact card; turning it off takes effect at once. Hosted mode refuses PAN storage and payment use. A payment from an event turn needs the owner's approval like any other. Stored PAN use does not enforce settlement at the issuer or establish PCI compliance.
- Secrets in chat: Pi is told never to ask for passwords, codes, card details or API keys in chat and to use `sign_in` or `pay`, which open private entry. Nothing filters the reply text. While a verification or payment request is pending, a code the owner sends by itself (4–8 digits for verification, 3–4 for a card), or one card code labeled CVV, CVC or security code inside a message, is caught before Pi sees it; a labeled verification code inside other text is refused with a request to send it alone. Unlabeled numbers in other messages, a code sent after its request ended and any other secret the owner types reach the model.
- Pi saves memory only as the owner's complete current message, word for word (`memory_learn`), never as its own text. Background memory learning reads only the owner's own user messages (short, no attachments, none with a memory-save approval), never assistant text or tool results; web content reaches memory only if the user pasted it. Learned entries stay tentative until a second message repeats them, and automatic changes archive active entries instead of deleting them. The archive itself is bounded, and only a user-requested forget deletes. Sensitive topics (health, religion, politics and similar) are learned in the background only when the owner turns them on, and Pi is told to save them only then or when the owner explicitly asks. One exception: when Gmail connects, a background job reads the owner's own text from recent sent emails (quoted, forwarded and automated mail removed) and saves only their writing style, with no facts, names or quotes, as one capped `preferences` entry labelled "Learned from your sent email" that replaces its earlier version by archiving it.
- Owner and tenant isolation: every query and route is owner-scoped; tenants get their own SQL role and schemas and never receive control or auth credentials.
- Local access: loopback and Host are not identity, since containers reach host listeners. Every local `/api` request needs the owner key from `OTTO_DATA_ROOT/access-key` (a cookie set from the printed `#access=` link, or the desktop header); only verified webhooks, OAuth callbacks with one well-formed state, the key exchange and the privacy notice go without it. Never mount the data root or pass the key to a container or prompt.
- Internal gateway-to-tenant requests use signed HMAC envelopes binding owner, environment, generation, method, target, body, nonce and expiry. Keep replay and expiry checks.

## Model policy

- Pi does not ask before app actions, sign-ins, bookings or payments; the trust check and payment approval ask the owner when their words don't cover an action. Pi asks only when the account, target or action is unclear.
- Activity checks are quiet event turns: while a notification rule is set, each connected account without app events gets at most one every 30 minutes, never two running at once. Each reads what arrived since the previous check for the same account started; a check waiting on the owner counts as done. A queued check whose rule or account is gone ends without running. They carry no owner words, so the trust check runs reads and drafts and asks before anything else.
- The first-chat task cards are prepared without a turn from the owner's setup answers and, when Gmail is connected, one read of recent inbox subjects and snippets that drops verification-code mail; the owner's selected model sees that mail only as data, and its cards are validated or replaced by fixed ones. **Do it** sends exactly the visible card title as a normal owner message.

## Validation

Run focused tests while editing, then `pnpm run check`, `pnpm run test:integration` and `pnpm run build`. For capability eval changes also run `pnpm --dir evals run check` and `pnpm --dir evals test`. The evals themselves call live models, so run them manually (see [evals](docs/src/content/docs/contribute/evals.mdx)). For deployment changes also run `pnpm --dir deployment/cloudflare run check`, `pnpm --dir deployment/cloudflare test` and both Wrangler dry runs (see [Cloudflare](docs/src/content/docs/deploy/cloudflare.mdx)). For docs changes run `pnpm --dir docs build`, which fails on a broken link. Report fixtures, UI checks and live checks separately.

## Tests

Keep only tests that would catch a real regression in:

- the core harness (one thread and Pi session per owner, sequential turns, stop, interruption, reset, session rebase);
- sandbox isolation (nothing on the host, no keys in the sandbox, contained paths);
- safety (approvals, uncertain actions, Vault and sign-in fencing, onboarding task cards);
- owner and tenant isolation (gateway, signed envelopes, owner scoping, URL guards, redaction);
- real integration contracts (channel delivery, schedule firing, downloads, OAuth completion).

No tautological tests, mocks that return what they were told, or tests of UI copy, wording, CSS, constants or configuration. Extend the existing file for an area instead of adding one.
