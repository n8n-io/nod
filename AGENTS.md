# nod

Setup, use and how the system works are in the docs site, whose pages live in `docs/src/content/docs` (start with [architecture](docs/src/content/docs/how-it-works/architecture.mdx) and [Trust and Vault](docs/src/content/docs/trust/index.mdx)). Development and checks are in [CONTRIBUTING](CONTRIBUTING.md).

## Rules

- Do not push, deploy or publish without explicit authorization.
- Keep keys, credentials and private user content out of Git, logs, prompts, test fixtures and client configuration. No tool returns a saved password, code or card to Pi.
- No code comments or JSDoc.
- Prefer deleting to patching ceremony. Breaking changes are fine; keep the code small.
- Use synthetic data and disposable database schemas. Never reset the normal local database, and never call a live model, connected account or real recipient from a test.
- Analytics events follow [Change analytics](docs/src/content/docs/contribute/analytics.md): bounded values only, no content, and the user-facing event list and any PostHog dashboard whose answer changes are updated in the same change.
- Documentation lives only in `docs/`. When setup, behaviour or a safety rule changes, update the matching page in the same change and follow [Write docs](docs/src/content/docs/contribute/write-docs.mdx). Package READMEs stay short pointers to the docs.

## Architecture

- One thread per owner, shared by web, Telegram and WhatsApp: one sandbox workspace keyed by the thread ID, and sessions that share it. The chat is the session keyed by the thread ID, with a persistent Pi session; every schedule fire and event is its own session, keyed by its first turn.
- Every user message, schedule fire, event wake and resume is a turn. Each turn belongs to one session (`turns.session_id`); a session runs one turn at a time, sessions run in parallel, and a resume continues the session that asked. `delegate` runs subagents inside a turn: in-memory Pi sessions with nod's tools and their own browsers, run in parallel by Pi, whose answers return as untrusted tool results. Every write from a turn goes through `withTurnLock`. Stop ends a turn at once: the runtime races every tool call against the turn's signal and never waits for one that ignores it, and `withTurnLock` refuses its late writes. Turns and tool calls are never retried automatically, and app actions run with provider retries off; Pi and the memory model retry only failed model requests, and provider lookups (accounts, catalogs, schemas) may retry at the HTTP level.
- Each session checks in when its model spend since the owner's last message to it passes the owner's task check-in ($5 by default, set in Usage or by telling nod; plan usage counts at its API-price estimate). Its tools then refuse new work except reporting and `ask_user`, helpers stop at their next step, and a model that keeps working ends the turn failed. The spend comes only from `model_usage`.
- Each chat and background session saves its Pi transcript and has its own browser, keyed by the session ID and opened on first use. Sessions and subagents run in parallel. Each subagent has its own run ID, browser, and output directory. When the browser container is full, a browser used in the last five minutes is never closed for another, but one idle for longer can be, even while its session or subagent still runs; a browser waiting on the owner is never closed for another during its 30-minute hold, after which it can be. A new browser waits for a free slot until its turn stops. Every agent-browser request has a deadline (60 s, or its own timeout plus 30 s, above agent-browser's own 30 s per-call limit); a browser that misses one, is interrupted or doesn't close within 5 s is killed with its Chromium process group and reopens fresh. A chat or background session can hand its browser to the user. Each handoff belongs to its waiting question, turn, and browser; a reply or Done continues that session, and Done posts no owner message. In nod's browser every passkey request fails at once. Subagents return questions to the parent and cannot message the owner or connect apps. A background session's browser is deleted when the session ends without waiting, or is stopped or reset; a later turn of that session, such as a task the owner continues, starts a fresh browser. Only a reset conversation's browser is refused for good.
- One execution scope links thread, session, turn, run, parent run, and browser IDs. Execution and tool activity use `turn_events`. `model_usage` is the only cost ledger; each model request has one usage ID, and all totals come from its rows. Parent runs never record child costs again. Keep execution IDs internal.
- Pi-native tools (read, bash, edit, write, find, ls) run inside the sandbox through `WorkspaceSession.exec`. The pinned Pi web extension runs in the server process with its process permissions.
- Provider keys never enter the sandbox or the browser. The Pi web extension, `create_audio` and apps run server-side; the web extension never reads local files or uses the server's own logins, such as a GitHub CLI session. The browser and the web extension reach only public addresses, checked when each connection opens, and nod drops any proxy the model names or the extension's settings set for a web tool. An OpenAI-compatible model server is one the owner runs separately and names by address in local nod or its `.env`; nod sends model requests and that server's optional key only to that address. An Azure OpenAI key goes only to the endpoint the owner enters, over HTTPS unless it is on this computer, and an Amazon Bedrock key only to AWS in the Region the owner enters. An n8n instance the owner names by address on its setup page may also be local or private; nod sends that connection's requests and token only to that address (loopback names on the same port count as one host), and any access path the model proposes stays a public HTTPS address. The setup page prefills n8n's default `http://localhost:5678` when its MCP metadata answers there, the only address nod checks on its own; the owner still selects Connect.
- A connected CLI's credentials reach only a sealed install of the path's declared source, run as that CLI's own Linux user in group `nod-connected` with an environment built from scratch; nothing the sandbox user or another CLI can write runs with them.
- `src/server/composition.ts` is the only place that selects providers and runtime implementations. Capabilities are ports in `src/ports`; vendor SDKs stay in `src/providers`; product policy stays in `src/server`; `src/web` imports only web and shared code.

## Safety invariants

- Trust check (`src/server/trust.ts`): one checker decides every connected app action, every browser step that can commit (click, key press, choosing an option, ticking a box, drag, upload, accepting a page dialog, a page script with side effects; reads, typing and read-only scripts skip it, and a download aimed at a control instead of a link is checked as a click), and every sign-in or saved-session use before it runs, app reads included (tool discovery with `SEARCH_TOOLS` reads no app content, only connected account names, and skips it), and every change nod makes to its own schedules, notification settings, the owner's rules, spending limits or memory (forgetting a note, turning memory on or off, clearing it); a scheduled run is checked against its schedule's instruction and an event turn against the owner's notification rule, their standing instruction. Saving a note follows the memory rules below, and only a turn started by an owner message can forget a note or clear memory. It is always the owner's selected model at its lowest reasoning effort; a decision model (GPT Decisions with an OpenAI API key, TypeSafe Jev through OpenRouter or with `TYPESAFE_API_KEY`) may only read the owner's reply to a confirmation or check whether an email gives account access; it never decides whether an action runs or checks a confirmation question. The checker sees only the owner's recent messages (for a task, the chat's recent owner messages frozen when the task started, never later chat messages, plus the owner messages addressed to that task), the owner messages in its turn chain (the request and every answer to nod's questions), and the message they answered (the one the owner replied to, or else the latest assistant message in that channel before it; a task's check sees it only when it is that task's own message), which shows what the reply answers and never proves what the owner saw or approved (a first task the owner tapped is nod's wording, so it never counts as their message), or for a scheduled run the instruction that created its schedule and the run's time and time zone, or for work nod starts on its own the current notification rule, plus the action's arguments as nod sends them, never tool results; it always sees the whole request and the whole reply. Every check, in every kind of work, also sees the owner's rules (`preferences.rules`): their lasting words on what nod may do without asking or must ask about first. Only then does the checker prompt gain its rules paragraph, so owners without rules get the same prompt as before. A rule to ask first, or not to act, makes the action ask even when other owner words cover it; a rule to go ahead counts as owner words for what it says and never covers nod's own settings. The checker names a rule as the reason it asks only when the owner has rules. To run a non-read action the checker must quote, word for word, the owner words that allow it (a message it was shown, the schedule instruction, the notification rule or the owner's rules), or say "read"; the server checks the quote appears in what it showed and otherwise asks, records the basis with each app action and Vault use, and Usage shows the quoted words while their message still exists. A rule change nod makes shows the checker the current rules, so the owner's words must cover anything it adds; the owner's own edit in Usage needs no check. Work nod starts on its own (event turns, activity checks included) gives it no owner words beyond that rule and the owner's rules, neither of which covers nod's own settings, never the event, and a resume that traces back to no owner message, schedule or event gives it only the owner's rules. A notification rule change shows the checker the current rule, so the owner's words must cover anything it adds. It runs reads, drafts and actions the owner's words ask for, where words that ask for an outcome (buy this there, move that meeting and tell its people) cover the steps it needs on the target they name up to and including the commitment they name, and nothing past it; a browser step whose effect its control leaves unclear runs only inside such an outcome on that website, never for a question, lookup or summary, and only when its worst plausible effect stays within it, and cookie-banner choices count as reading, since they stay in nod's own browser. Anything else waits for the owned yes/no confirmation, and a failed check asks. No stored list of recipients or past confirmations skips the check. Every confirmation is bound to the exact action and arguments and stays open while its turn waits; a turn, subagents included, has at most one open confirmation, approvals refuse a second, and no app or memory call issued after one that asks runs; a reply to one that is no longer pending is an ordinary message. The checker reads the owner's reply to a confirmation on its own, without the question or the action, and only a reply it reads as an unconditional yes approves. A reply it can't read leaves the confirmation open; any other reply closes it without running, and a direct reply to a background session's confirmation continues that session. Only questions are recorded. Confirmed actions run once; failed or interrupted ones become uncertain and are never re-run, and the resumed turn continues with the reason, as it does when a confirmed action can no longer run. A recorded question fences its exact action for the rest of that request, even when the checker would now run it: once done, a repeat returns the recorded result; while pending, declined or uncertain, a repeat is refused; an expired one never ran and fences nothing. A browser step is described by agent-browser's own ref label or the accessibility tree, plus the method and address of the form a click or Enter would send (for Enter in a field, through the form's default button), read from that element's form in an isolated world, never page parsing, or unknown when the browser can't inspect the control or same-label controls send different forms; a confirmed step replays once only while the browser is on the same page, its refs still exist and the form it sends is unchanged, otherwise it does not run; subagents refuse steps that would ask. When a step asks, the confirmation writer and its fact check read the page's visible text as target details; the checker never sees page text.
- App, browser, web and codemode results that the model receives directly, confirmed-action results and failures, and connected-app event data (the whole event, with secret-named keys removed and email that gives account access hidden: each mail-shaped record is checked on its own by a decision model, or else the connection's smaller model, from its sender, subject and start; a failed check hides it; downloaded mail files are not checked) reach Pi inside one `untrusted_tool_result` block with a data-not-instructions notice; tags inside the content are neutralised. Errors reach Pi unwrapped. Calls made by codemode scripts stay raw. A connected MCP server's tools also run as their own deferred Pi tools (`mcp__<server>__<tool>`), directly or from codemode, through the same trust check, ordering and wrapping as `apps`; each server's own instructions reach Pi inside one untrusted block. nod's own confirmation notice is the only app result left unwrapped. Nothing scans content for injection phrases; the server limits what fooled text can do.
- Vault and sign-in: `sign_in` never returns a saved value. The one trust checker decides each sign-in and saved-session use from the owner's words (a sign-in the owner completes in the private form needs no check, because entering it is their consent); otherwise the owner's yes, bound to the exact origin and item, covers the rest of that task. A domain mention does not grant consent. The server claims a durable use before browser work. Pi selects the fields and submit control; the provider checks actual frame origins, enters and submits privately, then keeps the live page for Pi to inspect. Known secret values (passwords, codes, card numbers and security codes, not usernames or the cardholder name) are removed from tool output and masked in screenshots. A saved login's authenticator key never leaves the server: when a page asks for a code without `emailCode`, the server generates the current code and enters it like any code, after the same trust check as that login, only for the login this task signed in with (without one, the login Pi names or the only keyed login for the origin), once per sign-in. 1Password logins reach Vault only when the owner picks one in the private form: the 1Password SDK runs in a separate helper process (on macOS the Electron Plugin helper, the only nod process allowed to load 1Password's library), never in the server; it lists only the logins 1Password would fill on the request's exact origin and re-checks the picked item, and nod saves an encrypted copy that then works like any saved login. Native side-effect checks permit read-only JavaScript without a reload; a document changed by Pi JavaScript requires a reload before entry. All normal Pi tools work after submission, except that page scripts pause on a document where nod filled a private value until it reloads or navigates, and a reload of a page reached by a form POST, or whose navigation nod can't read, re-opens its address with a GET rather than resubmitting. Failed entry keeps the observation lock until the filled document changes. Event turns carry only the notification rule, so their sign-ins and saved-session uses ask the owner unless the rule needs that website and, for a saved session, the website it belongs to; every schedule fire, event and subagent starts in its own fresh browser. Secure forms and payment requests bind owner, turn and origin, stay open while their turn waits, and close when a newer request or a newer turn starts in their session (a chat message never closes a background session's form); the waiting turn resumes in the transaction that records the entry. The server and destination website are trusted with submitted values; output redaction does not contain every transformation a website can make.
- Pi reads the page from the agent-browser snapshot and chooses login methods and fields. Do not add page-parsing scripts, snapshot regexes or field checks around the browser; leave the page to Pi, the model and agent-browser. Pi can run page JavaScript with browser evaluate. Tool output replaces known secret values. Keep site-specific cases in regression fixtures. Two exceptions: when a browser step asks the owner, the server reads the bound page's `document.body.innerText` with a read-only script for the confirmation question, which never reaches the checker; and before a click or Enter, the server reads the method and address of the form that the exact target element would send, through the form's own properties in an isolated world, for the checker.
- Before choosing a login method, check saved account metadata. Reuse a uniquely applicable login or the method the user chose. If the method remains ambiguous, offer the observed controls through `sign_in` with `kind: 'method'` so the owner chooses in the private panel. Ask in chat when the matching account remains ambiguous.
- Payments: `pay` binds one request to the shop, checkout document, actual card-field origins, submit control, amount, currency and selected card revision. The owner approves in nod web or desktop with the card's security code, which nod never stores. A chat-app task uses the desktop private form and resumes in its original channel. Private URLs and payment codes never pass through chat apps. The claim locks and reads the approved revision on an active turn. The provider uses field-bound private entry and submission, then keeps the live page and removes known secret values from observations. A durable use never runs twice; interrupted work is uncertain. Usage records card submitted, not paid. A payment from an event turn needs the owner's approval like any other. Stored PAN use does not enforce settlement at the issuer or establish PCI compliance.
- Secrets in chat: Pi is told never to ask for passwords, codes, card details or API keys in chat and to use `sign_in` or `pay`, which open private entry. Nothing filters the reply text. While a verification request is pending, a message that ends with its only number, 4–8 digits 0–9, is the code in any wording or language, and a message with another number of three or more digits is refused with a request to send the code alone. While a payment request is pending, a card code sent by itself (3–4 digits) or one labeled CVV, CVC or security code is caught. A code sent as a reply to a closed request is refused, and a code sent by itself is refused until ten minutes after a newer turn starts in that session. Other messages and any other secret the owner types reach the model.
- Pi never writes memory text. `memory_learn` works only in work the owner started (chat or a task) with an owner message: the server reads that message, the owner's last 10 messages in its conversation and any older owner messages Pi names by ID (never a task-card title the owner tapped, a message over 4,000 characters or one with a secret), and only those messages and the memory index reach the memory model, which writes one declarative fact per note and may archive notes they make untrue; the server keeps only notes that quote a cited owner message and hold no secrets, saves them as confirmed and archives instead of deleting. Background memory learning reads only the owner's own user messages (up to 4,000 characters, no attachments, none with a memory-save approval, never a task-card title the owner tapped), never assistant text or tool results; web content reaches memory only if the user pasted it. Learned entries stay tentative until a second message repeats them, and automatic changes archive active entries instead of deleting them. The archive itself is bounded, and only a user-requested forget deletes a note; when memory is full, the least recently used learned skill the owner hasn't edited is dropped. Sensitive topics (health, religion, politics and similar) are learned in the background only when the owner turns them on, and Pi is told to save them only then or when the owner explicitly asks. One exception: when Gmail connects, a background job reads the owner's own text from recent sent emails (quoted, forwarded and automated mail removed) and saves only their writing style, with no facts, names or quotes, as one capped `preferences` entry labelled "Learned from your sent email" that replaces its earlier version by archiving it. Learned skills are the one kind of memory nod writes itself: Pi saves or patches one (`skills save`/`patch`) only in work the owner started (chat, a task or a schedule), never from event turns or subagents, and not while saving is off. The server redacts known secrets from each draft, then the memory model rewrites it as a procedure without personal data, as a model's best effort, dropping outside sends the flow didn't need. Skill text reaches Pi as untrusted data, never counts as owner words, and never reaches the trust checker, confirmation writer or fact check.
- Conversation traces: only while the owner's **Share conversation traces** switch is on, each request to the owner's selected model and its reply, except checks of account-access email, leaves through `src/server/traces.ts`, which replaces execution IDs with keyed hashes that change daily and on restart and removes known secrets, the owner's name and validated personal identifiers (`src/server/personal-data.ts`; `src/providers/pi/traces.ts` replaces images with `[image]` and drops the owner context) before the n8n nod Traces workflow forwards it to LangSmith. Turning the switch off stops sending at once. nod never holds a LangSmith key; official desktop builds carry only the workflow's webhook token, from the release secret.
- File previews: artifact HTML renders only as `srcdoc` in an `allow-scripts` iframe without same-origin, behind a no-network CSP placed before the content, and the preview closes if the frame loads another document. Other formats render as text, canvas, React or a script-less sandboxed frame, never as HTML in the app's DOM. HTML, SVG and XML never get a local `blob:` preview.
- Owner isolation: every query and route is owner-scoped.
- Local access: loopback and Host are not identity, since containers reach host listeners. Every local `/api` request needs the owner key from `NOD_DATA_ROOT/access-key` (a cookie set from the printed `#access=` link, or the desktop header); only verified webhooks, OAuth callbacks with one well-formed state, the key exchange and the privacy notice go without it. Never mount the data root or pass the key to a container or prompt.

## Model policy

- Conversational confirmation and channel handoff text comes from the selected model through `src/server/communication.ts`, with recent owned messages as language-only context. No phrase lists or fixed confirmation templates. A separate model call checks confirmation claims against the frozen action without conversation context; arguments define proposed changes, while details may describe the current target. A rejected question gets one fresh draft, checked the same way. Approvals recheck the turn before saving; failed generation or a second failed review leaves the action blocked. Response language comes only from the owner's own words, never from data such as email, and is English before they write; it is independent from region, clock format and time zone.
- Pi does not ask before app actions, sign-ins, bookings or payments; the trust check and payment approval ask the owner when their words don't cover an action. Pi asks only when the account, target or action is unclear.
- A finished task or scheduled run gets a quiet receipt under its last message (its non-read app actions and cost from `model_usage`) that opens Usage filtered to that session; each recurring schedule shows its projected monthly cost from its recent finished runs.
- The notification rule is empty until the owner asks for updates; connecting an app does not enable periodic activity checks. After a chat or task that connected or used an app with messages or events the rule doesn't cover, Pi offers once per app with `follow_up` and saves a rule only on a yes. Activity checks are quiet event turns: while a notification rule is set, each connected account without app events gets at most one every 30 minutes, never two running at once. Each reads what arrived since the previous check for the same account started; a check waiting on the owner counts as done. A queued check whose rule or account is gone ends without running. They carry only the notification rule, so the trust check runs reads, drafts and what the rule asks for, and asks before anything else. After the owner approves an action from background work that will come up again, Pi offers once, at the end of its result, to add it to the rule; after one in chat or a task, it offers once to add it to the owner's rules.
- The setup interview follows one skill file, `src/server/onboarding-interview.md`; the code adds the reply contract, the data-not-instructions notice, a cap of three questions and refuses replies that `unsafe` flags, and the client falls back to one fixed opening or hand-off question when the model fails. The owner's selected model writes each message from the chat so far and, while Gmail is connected and it is ready, the inbox brief, and ends early once it knows enough. Only the owner's own answers are saved, word for word, as one memory note. The first-chat task cards are prepared without a turn from the owner's setup answers. When Gmail connects, a background job prepares a brief from up to 40 recent conversation threads, excluding mail that gives account access, trimming quotes and masking URLs, email addresses, keys and long numbers. The brief is stored only alongside the first cards and cleared after posting or expiry; the setup questions also read it as data to open with what the inbox shows; without it, preparation can read up to 15 recent subjects and snippets, again excluding mail that gives account access. The owner's selected model sees mail only as data and proposes one immediate and two ongoing cards, each at most 10 words. Cards are checked for shape, allowed source and distinct titles; one repair is allowed before invalid cards are replaced with fixed ones. **Do it** sends exactly the visible card title as a normal owner message.

## Validation

Run focused tests while editing, then `pnpm run check`, `pnpm run test:integration` and `pnpm run build`. For capability eval changes also run `pnpm --dir evals run check` and `pnpm --dir evals test`. The evals themselves call live models, so run them manually (see [evals](docs/src/content/docs/contribute/evals.mdx)). For docs changes run `pnpm --dir docs build`, which fails on a broken link. Report fixtures, UI checks and live checks separately.

## Tests

Keep only tests that would catch a real regression in:

- the core harness (one thread and Pi session per owner, sequential turns, stop, interruption, reset, session rebase);
- sandbox isolation (nothing on the host, no keys in the sandbox, contained paths);
- safety (approvals, uncertain actions, Vault and sign-in fencing, onboarding task cards);
- owner isolation (owner scoping, local access, URL guards, redaction);
- real integration contracts (channel delivery, schedule firing, downloads, OAuth completion).

No tautological tests, mocks that return what they were told, or tests of UI copy, wording, CSS, constants or configuration. Extend the existing file for an area instead of adding one.
