# Server features

`composition.ts` constructs adapters and binds feature factories. `index.ts` serves the app and owns process signals. Other server modules use `../ports` and explicit dependencies; do not import vendor SDKs or concrete runtime/provider implementations. Signal shutdown must attempt application cleanup and database closure independently, return a failing exit status if either fails, and keep raw cleanup errors out of console output. Retain the tenant lease until cleanup finishes so its existing expiry watchdog can terminate pending cleanup. Repeated signals must not extend that deadline.

`integrations.ts` keeps the Apps catalog and saved account provider ID. New Notion and Linear attempts use the direct MCP adapter; saved Composio Notion accounts still route to Composio. Direct tool discovery receives only active saved account IDs. Chat consent attempts bind owner, task and revision; a callback can resume only the current waiting task. The Apps route returns to the configured app origin. Keep direct tokens inside the trusted Vault and adapter boundary, and preserve account-specific revocation and read policy. `direct_oauth_accounts` holds metadata; startup moves older ciphertext to `vault_app_grants`.

`discovered-connections.ts` owns model-proposed public HTTPS MCP, HTTP API, and installed CLI paths. `vault-app-grants.ts` owns their encrypted grants and pending OAuth state. Connection rows hold path and account metadata only. Startup moves legacy saved grants into Vault and clears their old ciphertext. An HTTP path needs a valid GET test address before the secure form opens. A path change needs a new sign-in or token check. Route all non-read calls through the current approval service. Provider adapters keep OAuth discovery, PKCE, DNS checks, address pinning, HTTPS and redirect limits outside the feature. Do not pass tokens into Pi, the shell, browser or approval arguments. Apps also lists saved website logins as browser paths from Vault. Removing one from Apps removes the same Vault login. Browser session cookies stay in the private browser profile. A saved CLI path sends one Vault token to the selected program through a separate computer user. The ordinary shell has no Vault read path. A selected CLI can send or save its token, so use only a trusted program. Cloudflare computer mode cannot accept CLI proposals.

Deployment drain is separate from process shutdown. `work-admission.ts` admits pending starts synchronously; `tenant-drain.ts` pauses normal HTTP ingress and registered pg-boss consumers without aborting accepted tasks. Stop each consumer by its exact worker ID with `wait:true`; a late stop must never target a replacement worker. Track detached integration refreshes, watch/event processing, Vault retries and channel batches through admission. Already accepted queue callbacks finish naturally, including callbacks blocked before their model controller exists. Queued work remains durable for resume or the next process. A tenant receipt requires stopped consumers and zero admitted work before its absolute deadline. HTTP response or client disconnect alone cannot release a handler still running. Lease renewal and signed deployment control remain available; existing read-only SSE streams do not prevent drain. Timeout or stop failure leaves admission paused. Only the same nonce, release and deadline may resume; exact successful resume is retryable, and cannot reopen a newer drain. `stopTasks` still aborts on shutdown, including a start that races its controller registration. For E2B, the optional computer lifecycle pauses the shared owner sandbox only after natural work drain, and adds `computerPaused:true` only after acknowledged pause. Abort waits for any pending pause before resuming that same computer and then its consumers; uncertainty keeps ingress paused. Ordinary shutdown sends the fixed generation-bound private computer stop acknowledgement only after both runtime capabilities dispose successfully. A tenant drain receipt does not prove confirmed hosting-container stop; Cloudflare computer checkpoint/stop proof remains separate.

`outcomes.ts` owns bounded semantic route preparation and the outcome/pending-input schema. Supply same-owner, exact-channel, current-generation recent conversation, including explicit null outcome provenance, without repeating messages already in candidate transcripts. Read only persisted conversation messages, never secure-entry values. Partition the latest eight outcomes into eligible and blocked context; failed tasks and recovery waits cannot continue. A blocked continuation, including an explicit reply or task ID, returns a fixed 409 before changing messages, jobs, revisions or receipts in web submissions; channel submissions use the atomic refusal flow below. Recheck the latest outcome task under the conversation lock without falling back to an older successful task, including when an explicit target names older work. `createUserMessageService` prepares outside transactions; both web and channel ingress apply the prepared decision under that lock. Explicit replies and current waiting-question answers take precedence. Persist related inputs behind an active session, then consume them in order only after a safe idle/question state. Credentials, approvals and manual control keep queued inputs held until their dedicated resume. Failed work retains pending inputs. Cancel/reset discard pending inputs. A router failure uses conversation-only fallback only when no blocked context exists; otherwise it returns a fixed 503 without accepting work. Semantic matching is not a security proof. Keep legacy task rows unclassified.

Create tasks/jobs and source mappings in one transaction. Preserve source IDs, channel identity, and revision checks. Keep one visible conversation while tasks remain internal. A short answer follows the latest visible question in its channel; an explicit message reply must reference an owned message in that channel. A bounded method answer such as Use Google can also continue when that exact option appears in the stored sign-in question. It must not borrow an unrelated question or override channel, explicit-reply or forced-new boundaries. Credential and manual-control waits require their secure path. Action confirmations consume an exact yes/no reply to the stored question in the same owned channel before ordinary conversation routing. Persist waiting states and release workers. Do not replay uncertain external actions.

Channel inbox rows retain the server-generated accepted user message ID. Pass it through composition as `clientMessageId`, including queued inputs. Intercept exact verification codes before inbox persistence. A recognized verification conflict atomically stores a masked discarded receipt, a fixed taskless guidance message and its explicit outbox route; never route the code to a model or create a task for the notice. Other hook or database failures return a fixed 503 without acknowledging the receipt. Schedule creation derives its delivery route from trusted task/message provenance or an inherited scheduled-task route, never model recipient arguments. Preserve that route on edits. Dispatch the new task and its `channel_task_routes` entry in one transaction. Outbox delivery uses the original receipt and rechecks message owner, account/sender access and provider reply windows without inventing a new inbound event or retrying uncertain sends.

Channel submission catches only `TaskReviewRequiredError` for blocked work. Roll back its submission savepoint before atomically discarding the exact owned inbox row and creating one taskless fixed refusal with its original outbox route. Recheck channel access before committing; generic conflicts and unknown failures stay pending for retry. A known refusal must not hold later inbox messages or outbox replies behind it.

Web submissions use `clientMessageId` as their persisted message UUID. Under the conversation lock, accept exact retries only when normalized text, ordered attachment IDs, reply target, owner, channel and current generation match. Return the original accepted message/session without repeating routing or dispatch; reject reused IDs with changed content. Queued inputs retain the same ID.

An accepted user execution failure persists one fixed assistant reply in the failure transaction, identified by task and revision. Preserve owner, running-state and current-generation checks; cancellation and stale completions cannot publish. Background failures stay quiet. Private failure diagnostics are best-effort and cannot hold the worker.

Elapsed time never inserts a canned progress reply. The agent can send a concrete useful update through the normal reply path; cancellation and revision checks apply. Web typing/deltas show only direct-user tasks in the exact `web` channel. Internal delta events carry immutable owner/channel identity; `/api/events` independently verifies both and removes routing metadata before writing bytes. Web state task metadata also excludes external channels. Preserve background web replies through persisted state and refresh events; `channel-stream-isolation` exercises the actual task-to-SSE path. Background work stays quiet unless it has a useful result. Supply the saved IANA preference timezone or the explicit Europe/Lisbon default to runtime; never derive it from the host timezone. `task-progress` covers these boundaries with fake clocks and disposable PostgreSQL.

User reactions to assistant messages create a quiet event only when a non-null value changes and a model is configured. Removing or repeating a reaction does not wake work. Assistant reactions use `createAgentReactionService` and target only owned user messages visible to the active direct-user web segment. Recheck source/target owner, exact channel, current conversation generation and task revision under the conversation lock. Persist one reaction per message and a five-minute cooldown across concurrent segments and restarts; removal does not reset that history. They never create another event. Telegram and WhatsApp reactions are not implemented. Source message IDs are available only for the persisted current user-authored instruction, not synthetic resumes or reactions.

Reset archives the web conversation by advancing its persisted revision and cancelling its active tasks. It never deletes messages, saved context, accounts, Vault entries, goals or schedules, and does not reset other channels. Filter visible chat, routing, runtime history and history search through `currentConversationSql`. New tasks inherit the current channel revision; archived tasks cannot continue or publish. Carry `conversationRevision` through state, stream events and optional message/onboarding requests so late client responses cannot restore archived chat. Validate one emoji grapheme with the shared emoji helper; legacy like, dislike and heart values retain their glyphs and dedupe equivalently.

Validate personal mutations through `personal.validateReview` before deciding whether to execute or confirm, and again in execution preflight. Use the write schemas and owned-target/timing checks, preserving normalized defaults in the reviewed payload. Invalid or obsolete local proposals must not enter uncertain execution. Goal creation supports an explicit next action, status and progress, defaulting to an empty next action, active status and zero progress.

`action-policy.ts` gives exactly five reversible local plan operations a direct path: goal create/update and schedule create/update/cancel. They require the exact current owned user message, current task revision and successful normal preflight; preserve target ownership, timing validation and idempotency. Do not require an English command phrase. The agent must use read tools for requests that only review/list/suggest, respect explicit no-change or draft-only instructions and ask about missing or ambiguous details before proposing a mutation. This is delegated local planning authority, not a semantic or prompt-injection guarantee. Background events, onboarding and synthetic resumes do not gain that authority.

Bind every connected-app write to the selected owned `connectionId`. `action-policy.ts` retains an exact ordinary-operation catalog and conservative phrase/scope matching of the current user instruction for external and other personal writes. This matching can still require confirmation for valid unfamiliar wording; it is not general language understanding. Clear ordinary requests execute without another permission step; unknown, destructive or ambiguous actions persist a specific chat question and exact action/account/arguments snapshot. Draft-only requests cannot transmit. These checks are conservative scope checks, not general semantic or prompt-injection proof. Recheck it at execution; missing or revoked accounts must fail without fallback. Keep watch intent separate from active subscriptions. Verify event owner, account, subscription, and raw signature before dispatch.

After one confirmed discovered-app write, retain the original owned user message only for that task's next revision. A later write in the same task must still pass account preflight and receive its own confirmation. Do not treat the confirmation reply or provider result as a new instruction. An unrelated task or later user message must not inherit this provenance.

`action-presentation.ts` formats readable confirmation questions from allowlisted human fields. Discovered external writes also show a bounded, redacted request body or tool input so the owner can review the requested action. Do not show credentials or internal identifiers. `approvals.ts` resolves owned goal/schedule titles for updates before formatting. Confirmation questions resolve account labels through `integrations.describeApproval` using the stored connection ID, owner, active provider and action toolkit. Use only the service name and verified cached account name/email; never include provider account IDs, callback values or credentials. This metadata does not grant execution permission.

Onboarding inspects connected apps and proposes useful work without connected-data writes or profile questionnaires. The shared app catalog is `shared/integrations.ts`, and `integration-policy.ts` lists reviewed reads explicitly. Downloads use the owned account and the dedicated file boundary; no model-provided URL or filesystem path is accepted. Supported watches are always requested; missing webhook configuration remains unavailable. Connection links belong in chat and never grant write approval.

Connect and Add account use a temporary provider session with no connected-account overrides. A pinned execution session cannot create another account link for that toolkit. Keep its cached/persisted selection unchanged while creating consent, preserve configured auth overrides, and attempt temporary-session deletion on success and failure. Store the new account attempt and expiring callback state before returning its link. Cleanup failure must not replace a valid consent result or expose provider details. Never delete, revoke or reconnect an existing account to obtain a second consent link. `integration-consent` reproduces the actual provider rejection through the SDK transport with a disposable database.

`email-code.ts` owns conservative email-code matching. Composition binds `integrations.emailCode` directly to Vault, outside model tools and provider-result recording. Require one owned active Gmail connection whose verified identity equals the encrypted selected login and the recipient observed on the current OTP page. Accept one authenticated sender within the site's registrable domain, using the public suffix list with private tenants, and one recent numeric code of the observed length. Bound lookup to eight seconds and messages to the current successful credential entry plus thirty seconds of clock skew, within five minutes. Reserve one lookup per selection; recheck the task revision, selection, fresh OTP inspection and account under the injection transaction. Expired, ambiguous, missing or failed reads fall back to chat. Never store mail, codes or transient `emailCode` inspection metadata, and never call the general integration executor for this path. `submitChatCode` consumes the exact request ID, owned task and one-use private token; ingress must mask the message before persistence.

Each subscription attempt claims a new `watch_revision`. Reclaimed attempts must fence both successful saves and failure/retry writes to that revision. A stale success removes its unused provider subscription; it cannot overwrite the current trigger.

Derive personal-data provenance from persisted owned user messages, never model arguments. Automatic learning accepts only the supported matching quotes/statements; other changes follow the requested-action policy. External event text cannot choose its own trust level.

Secure forms and channel setup send values directly to trusted services, never model context. Verification codes may arrive through chat only for an owned current OTP wait; chat-verification.ts intercepts exact code replies before ordinary routing or plaintext persistence, stores a fixed acknowledgement, and calls the Vault with the exact request ID. Preserve current channel/generation/revision/expiry checks, explicit reply targeting and ambiguity rejection. Reserve the masked message before injection so repeated delivery cannot replay an uncertain action. Expose only bounded request IDs, task IDs and expiry to the UI; never selectors, tokens, recipients or codes. Expose status/metadata only. Polling acknowledges an update after inbox persistence; transport changes drain active delivery and recheck the current owner binding. Telegram verification is read-only. Persist the encrypted desired configuration with `registration_pending` before applying its transport or registering the webhook, then mark it registered only after both succeed. Keep that configuration on activation or confirmation-write failure; restoring the old secret could disagree with Telegram. Composition retries pending registration after constructing the channel transport on startup. Failed recovery stays visible and contains no provider payload. Disconnect removes pending ciphertext and prevents recovery.

Return fixed public errors without provider payloads or secrets. Keep schema additions compatible with existing local data. Use disposable schemas for duplicate dispatch, cancellation, restart, stale forms, account migration, and provider replacement tests; see [development](../../docs/development.md).

The owned, inspector-gated screen endpoint returns HTTP 409 with a fixed code/message for recognized `BrowserActionError` failures. Do not expose raw provider messages or relax public-destination checks for browser error pages.

Inspector records are private developer data, not public error logs or telemetry. Mask and bound them before storage. Preserve task ownership, revision fencing, disabled capture, retention and combined timestamp/ID pagination. Unknown prices remain null; do not infer tool fees from model usage. Keep secure broker values outside these events. `inspector.recordFailure` captures accepted failed execution segments in the same private store, including failures before a model opens. Preserve the fixed public error; normalize only Error name/message/code/stack and bounded Error causes, redact before storage, and never copy response bodies or arbitrary error properties. Fence by owner, current conversation and exact failed revision, deduplicate per segment, bound pending capture, and drain it before closing the inspector pool.

Composition initializes prompt and provider-usage tables plus their initial owned retention cleanup through the main migration pool. Runtime inspection keeps its separate pool with a 10-second connection-handshake budget, 500 ms statement timeout and 750 ms query timeout. Do not run schema creation through those short recording deadlines. Prompt snapshots and provider usage remain nonblocking, with bounded pending writes; runtime observation waits retain their independent one-second limit. `inspector-initialization` proves a delayed PostgreSQL handshake, startup without a recording connection, owned retention and actual slow-query cancellation.

`inspector-work.ts` reads current owned executions grouped by outcome, pending input counts, enabled schedules and the last 24 hours of background decisions. Preserve current-conversation filtering for active work, typed review/event sources, redacted bounded labels and total counts before display limits. It reads persisted next occurrences and actual scheduler registration; never fabricate a next heartbeat or expose full task prompts/event summaries. Redacted task titles can be derived from the beginning of a user request. This endpoint does not enqueue work or invoke a provider.

Manual control first bumps the owned task revision, aborts its worker and waits for runtime tools to drain before taking the browser lease. Serialize each task's start, input and resume operations. Recheck owner, waiting reason and exact revision before manual input or resume. Release stale adapter leases when status checks detect cancellation, reset, ownership loss, revision changes or expiry, including before rejecting a new acquisition for a terminal task. Keep cleanup in the same per-task queue as reacquisition; failed release remains retryable. Release browser control before atomically requeueing an inspect-first continuation. Failed acquisition or resume leaves the task paused. Do not persist or log manual input values.

Provider usage stores bounded labels and numeric metrics plus a strict conversation-routing failure code and optional HTTP status. With Inspector disabled, accept only failed/cancelled `relevance/conversation_route` records carrying that validated metadata and no task/tool references, including inherited async context. Keep other capture disabled and all Inspector endpoints gated. This private owner-scoped exception shares the nonblocking 128-pending-write limit and seven-day retention. Never capture provider arguments, outputs, raw errors, causes, keys or prompts there. Stop channel delivery and agent work before closing metering, then drain accepted records before closing its database pool. Keep unknown costs null and distinguish metered operations from provider billing.

Saved profile fields, memories and active goals belong to the owner across approved channels. Task context also includes at most twenty current-generation messages from other owned channels, with provider-only channel labels and no actionable message IDs. Same-channel routing and visible reply/reaction IDs remain separate. History search retains ownership and archive filters and reports channel provenance.

Supply profile and goals through `RuntimeContext.personalContext`, independently of the thirty memory facts. Keep the user's timezone separate. A full memory list must not truncate saved identity, preferences or active goals.

Channel media resolution accepts persisted artifact UUIDs only and rechecks owner plus task. Read the fixed private artifact path without symlinks, bound reads to the stored file size, and cap one delivery at ten files and 15 MiB total. Recheck the channel binding after resolution. A failed read blocks delivery; an uncertain or partially accepted provider send is never automatically replayed. Unsupported transports return local-app attachment guidance.

The Vault broker rejects a form when its fresh inspection finds neither login fields nor methods; never fall back to a stale model-requested kind on such a page. Runtime method choices happen in chat before provider selection or Vault entry. The private form does not provide a second provider chooser. A successful credential injection is not proof the website accepted it. Keep the task/owner/origin-bound staged login through its original ten-minute expiry so identifier-first websites can continue without asking for the same login twice. Saved-identifier injection uses the same bounded association. Rejected website steps consume their old form; a new revision-bound form handles fresh input.

Vault stores separate named entries for the same exact origin. Bare-domain normalization applies only to manual saving, never trusted browser inspection. Secure password submission requires the user's label. Composition calls `fillSelected` before unambiguous automatic reuse. A blocked, expired or missing selection must not silently fall back to another account.

Saved-login viewing uses the UI-only POST routes `/api/vault/:id/details` and `/api/vault/:id/password`. Payment cards use the separate `vault_cards` table and `otto-vault-card-v1` owner/record binding. Integration callbacks keep `apps` or `onboarding` in the owned consent row, never trust a callback return URL, and redirect with a fixed `connection` outcome. Event workers claim only their owner's events. Channel settings authenticate ciphertext against owner and provider; hosted messaging receives a global `ChannelAccountRegistry` before registering or activating a bot. A foreign bot claim must fail before `setWebhook`. Persist each attempted global claim in `channel_account_claims` before contacting the registry. Reconcile that ledger against committed channel settings after changes and on startup; retain failed releases for retry, including lost claim responses. Cleanup cannot change a committed save into a failed response or release the currently configured account. Each claim advances a durable per-owner/provider/account revision; cleanup marks that revision inactive without deleting its counter. The control registry retains revision tombstones and serializes account transitions with the runtime lease, so a delayed claim cannot resurrect a released revision and a delayed release cannot remove a newer claim. Hosted webhook URLs come from the server's signed tenant route factory, never from form input. Channel inbox rows carry owner identity and all inbox/outbox claims and status counts must stay scoped. `hosted-integrations` covers these boundaries with disposable schemas and synthetic providers.

`account.ts` exposes fixed Google sign-in, session, account settings and guarded sign-out routes through the authentication port. Authenticated same-origin `POST /api/account/prepare` prepares the server-selected computer for the cookie owner; completing onboarding through `PATCH /api/account` must await the same preparation and recheck the session before saving. Google identity creation, public session reads and appearance changes remain independent of computer availability. Composition binds E2B to one `E2B_COMPUTER_TEMPLATE` and one `computer` allocation per owner; initialization migrates the role constraint without deleting or adopting legacy browser/workspace rows. Old split-template configuration and retained legacy allocations require explicit operator migration. Provider preparation is lazy and must never contact E2B merely because a synthetic tenant process boots. Account mutations use the cookie principal and reject a mismatching `X-Otto-Account`; the header never selects an owner. Account display name and appearance are distinct from the conversational personal profile. The avatar route requires the same cookie owner in its query, rechecks revocation after provider reads, serves bounded raster bytes with private caching and never exposes the provider image URL. `preferences.ts` persists `quietHoursEnabled` independently of the saved interval; false bypasses the quiet-time constraint during both classification and dispatch. Partial PATCH and legacy PUT omission preserve unspecified values. Migration defaults existing rows to enabled.

`privacy.ts` exposes only operator-authored public Markdown at `GET /api/privacy` in gateway and local mode. Composition loads the UTF-8 file selected by `OTTO_PRIVACY_NOTICE_FILE` before database initialization. Missing configuration returns `content:null`; a configured missing, empty, invalid or oversized file fails with a fixed error that reveals neither its path nor content. Keep the bounded 128 KiB read, 32,000-character trimmed limit and canonical Host/Origin guards. This route must not look up a session, read account data or start a tenant. Do not infer notice text from environment credentials, users or provider state; publishing and maintaining accurate deployment-specific content belongs to the operator.

`createArtifactService` binds metadata queries and byte storage to an immutable owner. Hosted composition injects `PrivateObjectStore` into artifacts and Pi; local compatibility exports retain existing filesystem metadata. Upload acknowledgement follows durable byte storage and metadata insertion. Downloads, range responses, workspace import and channel delivery re-read owned metadata and bounded bytes through the service rather than opening `storage_path`. Remote metadata uses `object:artifacts/<UUID>` and local metadata retains its exact private path; switching storage requires explicit migration. Inject the same service into app/task/channel paths and `Workspace.writeArtifact` into tasks so a remote workspace receives uploads before execution.

Browser-file publication passes the held task transaction client to `storeArtifact`: ownership checks, artifact metadata and message insertion share one connection and commit, serializing cancellation/reset without exhausting the four-connection tenant pool. Byte storage precedes the SQL commit; do not delete files after uncertain commit or failed refresh acknowledgement. Keep concurrent publication, cancellation/reset ordering and metadata rollback covered in `browser-download-delivery`.

`request-body.ts` bounds streamed service bodies independently of Fastify. Gateway ingress applies 4 KiB to tenant channel control and 256 KiB to provider webhooks before parsing; the service handlers enforce the same bounds. Tenant control validates the signed envelope before querying the lease, then checks generation, nonce, body hash and the atomic registry lease guard. `verifyRuntimeSignature` verifies the envelope only; use `createRuntimeVerifier` for generation and replay checks.

`runtime-auth.ts` verifies the complete tenant body before parsing and exposes its bytes through a request-scoped, one-use accessor. `multipart.ts` parses those verified bytes for uploads and transcription, validating the complete form before any artifact or speech call. Preserve the 16 MiB signed-body limit and one-file, five-field, 15 MiB file limits. A configured tenant reader must reject missing verified bytes; only local mode uses `request.file()`. Do not replace `request.raw` or defer signature checks until after multipart handling.

Channel revision migration adds revision `0` to existing global claims and journal rows; subsequent setup attempts advance the counter. Control requests require an explicit revision. Drain and confirm termination of old gateway/tenant processes before switching this protocol; do not run older unversioned registry writers beside it. Retries may repeat the same active claim or release; a released/failed claim needs a new revision, which the settings factory allocates automatically. Retain counters and tombstones across restarts and backups; do not prune or reset either side independently.
