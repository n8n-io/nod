# Project operations

Identify the project, source systems, reporting period and intended decision. Read the current tasks and latest source records. A chat mention can be a proposal rather than assigned work. A closed issue can still have an unresolved dependency.

Use stable source IDs to connect tasks, documents and communication. Before creating a task, check whether the action already exists. Keep source links and the reason for the action. Similar titles are not a reliable duplicate test.

Separate committed work, proposed work, blocked work and completed work. An owner's estimate is not a deadline agreed by the team. Do not assign owners or dates from a guess. Ask only where the missing decision prevents progress.

For a plan, check dependencies and actual capacity. Identify the next useful milestone and the evidence required to complete it. Do not call a percentage complete merely because the same percentage of subtasks closed; their scope can differ.

For a status report, compare with the previous snapshot. Explain changed scope, deadlines and blockers. Link evidence for reported completion. Keep the report short enough to support a decision. For follow-up drafts, check for a newer reply before chasing an overdue item.

After authorized task changes, read the destination records and check assignee, project, status and date. Report what changed and what remains proposed. Creating a checklist does not complete onboarding. A recurring status report needs a real schedule with a clear source scope and useful output condition.
